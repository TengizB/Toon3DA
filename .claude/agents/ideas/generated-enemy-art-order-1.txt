OVERVIEW
--------
Puts the first two generated enemies into the game and builds everything the later orders reuse:
a data-driven EnemyType -> generated-texture binding, the run-game `spawn` step that lets a sprite be
judged in the engine, and the art-direction section that makes the style lock binding. The two sprites
are already approved by the owner (D3, D4) and committed in assets/textures/enemies/generated/, so
this order makes no art decisions - it wires, verifies and documents.


SCOPE
-----
IN
  - render/GeneratedEnemySprites: a registry of EnemyType -> texture path (register() rows, a bootstrap,
    no switch). Rows: ACID_DRONE -> generated/warden.png, SHELL_BRUTE -> generated/harvest_tick.png.
  - EnemyRenderer: after it builds its current regions, every registered row REPLACES that type's
    region with a full-frame region of its generated texture, loaded through EnemySpriteSheets.get
    (cached, Nearest, alpha-cut - harmless on binary alpha). One loop over the registry.
  - EnemyConstants: ENEMY_GENERATED_DIR plus one path constant per generated sprite, and the fallback
    colour each row passes to EnemySpriteSheets.get.
  - run-game capture driver: the `spawn:TYPE:FORWARD:RIGHT` step (spawns an EnemyType FORWARD tiles ahead
    and RIGHT tiles to the side of the player via EnemyManager.spawnEnemy, depth 1), documented in the
    run-game SKILL.md step table. A dev hook, never game logic.
  - docs/art-direction.txt: new section 16 GENERATED ENEMY ART (the style lock, canvas, family ink
    table, the pipeline, the approval gate, the registry); section 9 notes that generated sprites are
    binary-alpha and pass through the same conditioning.
  - .claude/CLAUDE.md: the enemy-art skill in the "Where to Find Info" table and GeneratedEnemySprites in
    the project structure list (render/).

OUT (deliberately not doing now)
  - Renaming ACID_DRONE / SHELL_BRUTE to Warden / Harvest Tick (G10, AS1, AS2).
  - Any other enemy's texture (orders 2-6).
  - Deleting the old textures or the 2x2 sheet region code - the other types still use them (order 7).
  - Animation frames (AS3), the emissive glow layer (order 7), a Java port of the kit (AS4).
  - Changing any heightMultiplier, stat, ability, sound or ORA line.
  - Editing the two approved sprites. If they look wrong in a mood, report it to the owner; do not
    "fix" them silently.

RULES
-----
  R1  A type with a GeneratedEnemySprites row is drawn ONLY from its generated texture; a type without
      one is drawn exactly as before (byte-for-byte the same region).
  R2  The registry is the single place a type is bound to generated art. No `if (type == ...)` anywhere.
  R3  Every texture the registry names exists under assets/textures/enemies/generated/ and is a direct,
      unedited output of .claude/skills/enemy-art/bestiary.py (G2).
  R4  All renderer overlays (hit flash, health bar, name tag, matchup words, contact shadow, muzzle light,
      the mood grade at GRADE_STRENGTH_ENEMY) apply to generated sprites unchanged (G9).

TECHNICAL NOTES
---------------
  - New class render/GeneratedEnemySprites (render package: it names texture paths for a renderer).
    API: register(EnemyType, String path, float fallbackRed, float fallbackGreen, float fallbackBlue),
    a read-only iteration over rows, bootstrap() holding the rows, idempotent like the other bootstraps.
  - EnemyRenderer constructor: inside the existing EnemySpriteSheets.beginLoadBatch()/endLoadBatch()
    bracket, after textureRegions is built: for each row, textureRegions.put(row.type,
    new TextureRegion(EnemySpriteSheets.get(row.path, ...))). Textures are owned by the
    EnemySpriteSheets cache (disposed by Main.dispose -> disposeAll), so the renderer keeps no field.
  - Load-time only; no allocation in render() (critical rule).
  - The capture step lives in .claude/skills/run-game/capture/src/main/java/capture/CaptureLauncher.java
    (reflection on Main.world -> player position/direction, CELL_SIZE, enemyManager.spawnEnemy). A
    working version was written and used in the 2026-10-21 session; re-create it from the description
    above. Re-run setup.sh after editing capture/.
  - No persistence, no story strings, no tile symbols, no balance file.

EDGE CASES
----------
  - Generated PNG missing on disk: EnemySpriteSheets' existing fallback (procedural tinted sheet) is
    used with the row's fallback colour - the game never crashes.
  - App pause / GL context loss: same path as every other enemy texture (unmanaged, Pixmap-built).
  - World rebuilt per run: the cache is static; the registry bootstrap is idempotent.
