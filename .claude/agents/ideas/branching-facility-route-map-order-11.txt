DELIVERABLE 3 — THE EXTENSIBILITY RECIPES (the product owner's core ask, made copy-pasteable)
============================================================================================
Section 11 of the doc must contain these exact, tested recipes so future work is trivial:

  ADD A NEW LEVEL GENERATOR TO THE MAP:
    1. Implement ILevelGenerator (as today).
    2. GeneratorRegistry.register("my_generator", (seed, config) -> new MyGenerator(seed, config)).
    3. Add "my_generator" to the standard pool and/or the relevant region's generatorWeights.
    => It now appears on random combat floors. No World/overlay edits.

  ADD A NEW NODE TYPE:
    1. Add the RouteNodeType constant (+ NodeTypeDefinition: weight, tier, accent, hint,
       levelProfileId, iconPainterId).
    2. Write its NodeLevelProfile; register it. Write its IconPainter; register it.
    3. Add its pool weight (+ region weights). Add a NODE CATALOG row to the doc.
    => It joins the random pool at its weight. No World/overlay/generator edits.

  ADD A NEW SPECIAL LEVEL (for an existing or new node): per order-7's recipe.
  ADD A NEW REGION: per order-10's RegionRegistry recipe.
  ADD A NEW ROUTE EVENT: FacilityEventRegistry.register(event) + a NODE CATALOG note.

Each recipe ends with the invariant: "if you had to edit a switch statement in World or the
overlay, the registries are being bypassed — fix that instead."


DELIVERABLE 4 — THE UPDATE CONTRACT (make "each implemented idea updates the doc" enforceable)
=============================================================================================
Put this contract at the TOP of docs/route-map-system.txt and restate it here as the rule:
  "Any change to the route map subsystem MUST update this document in the same commit:
     - new/changed node type -> update the NODE CATALOG table + registries section;
     - new/changed generator -> update the extensibility recipe list of generators;
     - new region / event / affix / mystery outcome -> update the relevant catalog/table;
     - visual/interaction changes -> update the overlay/interaction sections.
   The `branching-facility-route-map-order-N` idea files each carry a LIVING DOC CONTRACT footer
   naming exactly which section they own; when an order is implemented, its STATUS flips to
   IMPLEMENTED and its owned section here is written. A code review that adds route content without
   a doc update should be treated as incomplete."
This mirrors the existing STRICT RULE pattern for tile-symbols.txt (single-commit doc+code), which
the team already follows — so the enforcement style is familiar to every agent.

Because a PostToolUse hook already runs code-reviewer on every .java write, consider adding (in a
later settings change, NOT required here) a reviewer note: "if the diff touches …toon3d.route or
RouteMapOverlayRenderer and does not touch docs/route-map-system.txt, flag it." Logged as a
suggestion; the human/settings owner decides.
