OVERVIEW
--------
The owner-directed render-quality follow-up to visual-identity orders 1-2 (checkpoint file
.claude/checkpoints/visual-identity-render-quality.md, commits 4e6f86a / dc8a37f / f3696dc) made FULL HD
the default and raised the floor/ceiling backdrop from 480x270 to 960x540. Since then the game has
stopped feeling smooth on the phone. This idea first MEASURES where the frame goes, then makes the
floor/ceiling and wall passes cheap without lowering the quality the owner asked for: FULL HD stays
the default, and the floor and ceiling come out sharper than they are now, not blurrier.

  WHAT THE OWNER SAID: "Full HD default + more detailed floor/ceiling made the game lag; investigate,
  optimise floor, ceiling and walls, fix the lag; a little texture quality may go, but keep it."
  WHAT IS NEEDED: the frame time at the Full HD default back to (or under) what the old HD default
  cost, mainly by taking the floor/ceiling off the CPU, with measured proof and side-by-side
  screenshots per lighting mood showing no visible loss. One sentence: "make Full HD cost what HD used
  to cost, and prove it with numbers and pictures."

WHAT THE CODE SAYS (the suspected causes, ranked; CP2 confirms or re-ranks them by measurement)

  C1  CPU floor casting at 9x the pixels. FloorCeilingRenderer.fillRows (FloorCeilingRenderer.java:320-421)
      shades every backdrop pixel on the CPU. At FULL_HD the backdrop is 960x540 (RenderResolution.java:36
      DEFAULT = FULL_HD; RenderConstants.FLOOR_BACKDROP_SCALE_DIVISOR_FULL_HD = 2) = 518,400 pixels =
      259,200 floor/ceiling pixel PAIRS per frame, vs 57,600 pixels at the old HD 320x180 - 9x. Each pair
      does two MathUtils.floor calls, one Level.getTileBrightness (Level.java:433: a getCell lookup and,
      on an 'f' tile, GameMath.flickerMultiplier = a hash and TWO sines, GameMath.java:1812) and two
      packed-shade evaluations with three clamps each (GameMath.applyRgbShadeToPackedRGBA, :1291). The
      per-row alert factors (1 + pulse*boost, 1 - pulse*dampen) are recomputed per pixel although they
      are constant per frame.
  C2  A 2 MB texture upload every frame. FloorCeilingRenderer.render (:300-305) copies the whole int[]
      backbuffer into the Pixmap's ByteBuffer and calls backdropTexture.draw(pixmap) = glTexSubImage2D of
      960*540*4 = 2,073,600 bytes per frame (~124 MB/s at 60 fps through the phone's shared memory bus),
      on the GL thread, after the fill barrier - it cannot overlap anything. HD uploaded 230 KB.
  C3  The result is STILL nearest-upscaled. The 960x540 image is stretched over the whole 1280x720 view
      (:310), so all that CPU work buys a 1.33x-upscaled floor. The quality the owner wanted is bounded
      by the backdrop, not by the materials.
  C4  Thread contention and serialisation. FloorCeilingRenderer and WallRenderer each own a fixed pool
      of up to 3 extra threads (FloorCeilingRenderer.java:145-157, WallRenderer.java:253) and each blocks
      on its own Phaser barrier (:287), so the floor fill and the wall DDA run back-to-back, never
      together, with 6 worker threads plus the GL thread competing for a phone's big.LITTLE cores.
      Sustained near-100% CPU is also what triggers thermal throttling on phones ("it lost its
      performance" over a session).
  C5  1.5x more wall columns. 1920 ray columns (RenderConstants.RENDER_RESOLUTION_FULL_HD_COLUMNS) =
      1920 DDA casts + 1920 SpriteBatch quads in the base pass (WallRenderer.java:2234-2264), plus the
      muzzle-light additive pass (:2266-2296). SpriteBatch blending is left ON for the opaque wall base
      pass, and every change of wall texture between neighbouring columns is a batch flush (one draw
      call each) because every wall sprite is its own Texture.
  C6  Billboard texture ping-pong. EnemyRenderer interleaves, PER COLUMN, the enemy slice and
      SpriteOccluderBuffer.redrawInFront (EnemyRenderer.java:758, SpriteOccluderBuffer.java:106-122): an
      enemy standing behind a prop alternates two textures every column = up to ~2 draw calls per
      column, now over 1.5x more columns. PropRenderer's keycard aura per-column loop (:570-581) does the
      same with a blend switch around it.
  C7  Load-time double allocation. Every floor builds FloorCeilingRenderer at HD (:64, :131-133) and then
      immediately reallocates at FULL_HD in setRenderResolution (:167-180): an extra Pixmap + Texture +
      int[] pair per floor (a GC spike on Android at floor arrival).
  C8  Smaller, to be measured: full-screen blended quads (FloorCeilingRenderer's own quad with blending
      on, ViewVignetteRenderer, hit/status vignettes) cost fill-rate on a phone; per-frame allocations
      anywhere in a render() path would show as GC stutter, which reads as "not smooth" even when the
      average frame time is fine.

THE CORE FIX (decided, see RULES R1-R9): draw the floor and ceiling as GPU-sampled HORIZONTAL SPANS
through the SpriteBatch DEFAULT shader. A horizontal row of floor is at one constant depth, so its
world-space texture coordinates are LINEAR across the screen - exactly what the GPU interpolates for
free. Each backdrop row becomes a few textured quads (split where tile brightness changes) whose UVs
are tile coordinates on a GL_REPEAT material texture. The CPU does a few thousand operations per frame
instead of a quarter of a million pixels, nothing is uploaded per frame, the floor is sampled at the
phone's NATIVE horizontal resolution (sharper than today), and the vertical look is identical to today
(same rows, same per-row distance, tint, fog, mip level). No custom ShaderProgram, so visual-identity
series rule V2 is kept.

RULES
-----
FLOOR / CEILING - the span pipeline

  R1  ROWS. The renderer keeps today's row model: the floor half has backdropHeight/2 rows (FULL_HD 270,
      HD 90; i.e. the tier's existing backdrop height 540 / 180), row r covering world Y
      [r*k, (r+1)*k) with k = WORLD_HEIGHT / backdropHeight (FULL_HD 1.333, HD 4.0), and the ceiling row r
      covering the mirrored band [720-(r+1)*k, 720-r*k). Each row's distance, tint (rowTintTable),
      muzzle-light falloff (rowLightFalloffTable) and mip level (rowMipLevelTable) come from the SAME
      tables and formulas as today (FloorCeilingRenderer.rebuildRowTintTable), so the vertical look is
      unchanged. The exact-horizon row (when present) is one flat quad in mood.horizonFloorPacked(), as
      today (:293-298).
  R2  SPANS. For each row, the world-space segment from the left ray hit to the right ray hit (the same
      origin/step GameMath.floorOriginTileComponent / floorStepTileComponent produce today, evaluated at
      screen x = 0 and x = WORLD_WIDTH) is walked across the tile grid. Consecutive tiles with the SAME
      Level.getTileBrightness value merge into one span; a change of brightness starts a new span at the
      exact crossing point. Each span is drawn as one quad of the row's height, with the span's start/end
      tile coordinates as its left/right UVs (identical for the quad's bottom and top edges - the row is
      flat, as today).
  R3  UV RANGE. Every quad's UVs are rebased by subtracting floor() of its left UV (integer shifts do not
      change GL_REPEAT sampling), and a span longer than RenderConstants.FLOOR_SPAN_MAX_TILES (= 8 tiles)
      is split. This keeps every texture coordinate small enough that the default shader's mediump
      varying stays sub-texel on phone GPUs.
  R4  MATERIALS. Each surface (floor, ceiling) is realised per floor as SURFACE_MATERIAL_MIP_LEVELS (4)
      Textures - levels 64/32/16/8 from SurfaceMaterialRegistry.getPixels(id, level), the existing box-
      filtered chain - each with wrap Repeat/Repeat and filter Nearest/Nearest (no GL mipmaps: the
      per-row level choice of today is kept, which also avoids GLES2 mip-completeness rules). Texel
      (column, row) of the registry array maps to UV (column/size, row/size) exactly as the CPU path
      indexed it - the material is not flipped or rotated relative to today. A row draws with the texture
      of its rowMipLevelTable level. Rows are monotonic in level, so a frame binds at most 4 textures per
      surface.
  R5  COLOUR. A span's colour is computed by the SAME expression the CPU path uses for a texel factor:
      adjustedShade = min(shade * tileBrightness, MAX_LIGHTING_SHADE), times the row tint, through the
      alert terms (floor: ALERT_WALL_RED_BOOST / ALERT_WALL_GB_DAMPEN; ceiling: ALERT_CEILING_TINT_STRENGTH
      / ALERT_WALL_GB_DAMPEN). That factor expression moves into one GameMath method (one home for the
      formula; applyRgbShadeToPackedRGBA becomes its packed-pixel caller or is deleted if unused).
  R6  FACTORS ABOVE 1.0. Mood tints exceed 1.0 per channel (e.g. MOOD_AMBER_HOT_NEAR_R = 1.10,
      MOOD_CORE_WHITE_VIOLET_FAR_B = 1.85) and the CPU path let the factor exceed 1 before the final
      clamp. A SpriteBatch colour cannot exceed 1. So each channel factor f is split: the base pass draws
      min(1, f); the ADDITIVE pass (blend SRC_ALPHA, ONE) draws max(0, f - 1) PLUS the row's muzzle-light
      add. texel*min(1,f) + texel*(f-1) = texel*f, so the composed result equals the CPU formula to
      within 8-bit rounding of two passes. The additive pass draws only spans whose add is non-zero, and
      is skipped entirely when no row needs it.
  R7  MUZZLE LIGHT (visual-identity-order-2 R8) keeps its exact meaning: added to the factor AFTER the
      alert maths, never clamped with it, final channel clamped by the framebuffer.
  R8  WHAT GOES AWAY. FloorCeilingRenderer no longer owns a backbuffer int[], a backdrop Pixmap, a backdrop
      Texture, an ExecutorService, workers or a Phaser. Nothing is uploaded to the GPU per frame. The
      batch is one pre-allocated SpriteBatch sized for the worst-case span count (cap 8191, the
      SpriteBatch maximum; it auto-flushes beyond that) plus one pre-allocated float[] vertex scratch -
      no allocation in render().
  R9  TIERS. HD and FULL_HD differ only in row count (180 vs 540 rows - today's backdrop heights) and the
      wall column count. The backdrop WIDTH stops existing; RenderResolution keeps only what is used and
      its docs say so.

THE PERFORMANCE PROBE (dev tool, not a test)

  R10 A render-package class (name it RenderPerformanceProbe) times each World.render pass on the GL thread
      (floor/ceiling, walls, props, shop machine, enemies + attack effects, vignette, weapon, mini-map,

      (= 120) frames plus the worst frame in the window.
  R11 Enabled by the system property toon3d.perfProbe (cpu = timing only; sync = additionally glFinish

      owner flips it to true for a measurement build). When off: no GLProfiler, no nanoTime calls, no

  R12 When on, it writes one line to Gdx.app.log every RenderConstants.PERF_PROBE_LOG_INTERVAL_SECONDS

WALLS AND BILLBOARDS

  R16 OPAQUE BASE PASS. When EnvironmentTextureSet realises a level's textures it records whether every
      wall, column and door texture the WallRenderer can draw is fully opaque (every texel alpha 255) -
      one boolean per level, computed once at load. If true, the wall BASE pass runs with blending
      disabled (re-enabled before the additive pass and before batch.end returns state). If false,
      behaviour is unchanged. Pixel-identical by construction.
  R17 W-ATLAS (conditional). If the investigation's median wall-pass draw calls across P1-P3 exceed
      RenderConstants.WALL_DRAW_CALL_ATLAS_THRESHOLD (= 12), the level's wall + column textures are packed
      into one per-level atlas page inside EnvironmentTextureSet (nearest filtering, 1-texel source
      columns, so no bleeding) and the WallRenderer's char-indexed arrays hold atlas regions instead of
      Textures; door textures join the page. Must be pixel-identical. If the threshold is not tripped,
      this is NOT built and the checkpoint file says so.
  R18 W-MERGE (conditional). If the investigation shows the WallRenderer's GL-thread draw submission
      (base pass, cpu mode) above 25% of its total pass time, adjacent columns whose results are EXACTLY
      equal (same texture, texColumn, srcY, srcHeight, drawBottom, drawTop and colour) are submitted as
      one wider quad. Pixel-identical by construction. Otherwise NOT built.
  R19 BILLBOARD ORDER. EnemyRenderer draws an enemy's column slices first and THEN the occluder redraws
      for those columns (and the muzzle-light pass after that, unchanged), instead of interleaving per
      column. Columns are disjoint x-ranges, so the result is pixel-identical; the enemy costs O(1)
      texture switches instead of up to 2 per column. PropRenderer's per-column blended loops get the
      same treatment where they interleave textures or blend modes. Draw order BETWEEN sprites
      (far-to-near) is unchanged.
  R20 ALLOCATIONS. Every allocation the investigation's GC log / allocation sampling attributes to a
      render() path is removed (pre-allocate or reuse). The AFTER GC count over P2+P3 must not exceed B0's;
      zero is the goal.
  R21 STOP RULE. If after CP6 the AFTER FULL_HD numbers miss A1/A2 below, the orchestrator does NOT lower
      the column count, the row count or the default tier. It records the numbers and the remaining
      ranked costs in the checkpoint file and reports to the owner with options.

EDGE CASES
----------
  - Player on the edge of the map / looking out of bounds: Level.getTileBrightness / getCell already handle
    out-of-range tiles; the span walk must terminate (bounded by FLOOR_MAX_VISIBLE_DISTANCE_CELLS * 2 * tan
    span and by the row's crossing count) - never loop on a degenerate direction (a ray component of 0 =
    no crossings on that axis).
  - Mid-animation (MOVING/ROTATING): non-cardinal direction vectors every frame - spans must be correct for
    any direction, not just the four cardinals.
  - Rows past the 15-tile clamp: identical spans every row (same distance) - correct, matches today.
  - A checkerboard of lit/unlit tiles: worst-case span count; the batch cap (8191) auto-flushes, never
    overflows; measure it in P1 if such a room exists, else note it.
  - Muzzle light at zero intensity / no grade (null AtmosphereGrade): the additive pass carries only the
    R6 excess, or is skipped.
  - Resolution switched in settings mid-run: tables rebuilt, no texture realloc, no frame with a stale row
    count (rebuilt before the next render, on the GL thread).
  - Floor transition / World dispose and rebuild after death: the per-floor material Textures are disposed
    with the renderer; the probe survives only as long as its World.
  - App paused / GL context loss on Android: material Textures are Pixmap-backed managed Textures (LibGDX
    reloads them) - no per-frame texture exists any more to lose.
  - Title screen (no run): no floor renderer runs; the probe still times the frame if on.
  - Probe on + hard-pause overlays: it keeps timing (overlay frames are frames).

RISKS AND UNKNOWNS
  - SpriteBatch.draw(Texture, float[] vertices, offset, count) with arbitrary UVs on a GL_REPEAT texture
    is standard LibGDX, but confirm the first thing in CP4 with one row drawn on screen before building
    the rest.
  - mediump varyings on phone GPUs: mitigated by R3; if the owner's phone shows shimmering in the far
    floor, lower FLOOR_SPAN_MAX_TILES (a constant, no redesign).
  - llvmpipe does GPU work on the same 4 CPUs, so moving the floor to the GPU will look SMALLER in the
    container than it is on a phone (where the GPU is separate). The container proves the CPU side; the
    OWNER CHECK proves the phone.
  - The two-pass R6 split doubles the 8-bit rounding: A9's +-4/255 allows for it; if a mood exceeds it,
    the cause is reported, not hidden by widening the tolerance.
  - If the investigation shows the floor is NOT the dominant cost (C1-C3 small), CP3-CP4 still ship (the
    upload and the threads are a phone cost the container under-reports) but the CP2 note must say where
    the frame actually goes, and R17/R18 decisions follow the numbers.

ASSUMPTIONS
-----------
  AS1  FULL HD stays the default - the owner asked for it and this idea's job is to make it affordable.
  AS2  Target on the phone: a steady 60 fps (<= 16.7 ms avg) at FULL_HD, with headroom for thermal
       throttling; the container target is "Full HD costs no more than HD did" (A1), because absolute
       container numbers do not transfer to a phone.
  AS3  No custom ShaderProgram (series rule V2 kept). The span approach is chosen precisely because it
       needs only SpriteBatch's default shader.
  AS4  "A little quality loss is OK" is NOT spent: the plan aims for zero visible loss vertically and a
       gain horizontally; tolerances (A9 +-4/255) only absorb 8-bit rounding.
  AS5  Today's 540 / 180 row counts are kept so the vertical look and every row table stay byte-for-byte
       the same; finer rows are a later polish idea.
  AS6  Today's per-row material LOD (render-quality Q3) is kept instead of switching to GPU mipmaps -
       identical look, no GLES2 mip-completeness risk, max 4 texture binds per surface.
  AS7  FLOOR_SPAN_MAX_TILES = 8 is enough for mediump varyings; it is a constant if the phone disagrees.
  AS8  The wall atlas and column merge are built only if measured to matter (R17/R18 thresholds 12 draw
       calls / 25% submit share) - not speculatively.
  AS9  The probe stays in the codebase, off by default, so the owner can measure a phone build by flipping
       one constant; it is a dev tool, not a test, and adds no dependency (GLProfiler is LibGDX core).
  AS10 The investigation baseline is HEAD-before-this-idea at FULL_HD (B0) and at HD (B1); the older
       57abdbc state is not rebuilt - B1 differs from it only by the material LOD (+0.3 ms measured in the
       render-quality checkpoint).
  AS11 P5/P6 are best-effort in the container (floor 1 is random); not being able to stage them does not
       block the idea, but must be written down.
  AS12 HD keeps its 1280 columns and 180 rows; after this idea it is simply the lighter tier, not a
       different look.
  AS13 The stale fromOrdinal comment and the HD-then-FULL_HD per-floor reallocation are fixed here
       because they live in the files being rewritten; nothing else is tidied.
  AS14 Non-continuous rendering / idle frame caps are out (battery is a separate idea).
  AS15 Desktop timings are reported as a proxy only, everywhere, per the run-game skill.
