WHAT THIS SERIES IS
===================
A staged refactor that DECOUPLES a level-file symbol from the sprite it renders, so the game
can grow an essentially unlimited library of walls, columns, props and whole ROOMS while the
finite symbol alphabet (95 printable ASCII chars, docs/tile-symbols.txt) never runs out.

Today the binding is 1:1 and GLOBAL: the wall symbol 'x' is ALWAYS the plain-wall texture, 'Z'
is ALWAYS the cryo wall, and so on. Every new piece of wall/environment art needs its own new
symbol, and docs/tile-symbols.txt reports only 10 free chars remain. That is the wall we are
about to hit. This series removes it.

THE CORE INSIGHT (the product owner's idea, restated as the design contract)
============================================================================
1. A SYMBOL is not an identity — it is a SLOT in a fixed CATEGORY (wall / column / solid-prop /
   decal / ...). Its category/meaning never changes; WHICH sprite fills it is assigned PER LEVEL.
       - Example: the column symbol 'P' ALWAYS means "column" (fixed gameplay meaning), but a
         given level may render it as a round column OR a new square column — any sprite in the
         COLUMN category. Same symbol, different art, per level.
2. No level loads the whole art library. A level uses a SUBSET — as many distinct sprites as it
   has free symbols — drawn from a large registered POOL. Per level: small palette. Across all
   levels: huge variety.
3. Two tiers of symbols:
       FIXED    — reserved, permanent meaning AND sprite (player start 'p', exit '>', doors,
                  keycards, pickups, ammo, enemy spawns, hazards). Never reassigned.
       FLEXIBLE — the wall/decor visual symbols. Their category is fixed; their sprite is
                  assigned per level by a rule-governed allocator (never random-chaos).
4. Signature rooms (MEDICAL_BAY, ARMORY, CRYO_CHAMBER, SERVER_ROOM, ...) keep their EXACT
   identity — architecture AND look. But they are registered "room blueprints" that CLAIM a set
   of symbols only when the room is actually placed in that level.
5. When a signature room is NOT placed on a level, the symbols it would have claimed are FREED
   and reused — NOT to reskin that room, but to spawn a COMPLETELY NEW, unique generated room
   and to add visual variety to the generic rooms and halls.
6. ARCHITECTURE: adding a new wall sprite, a new prop, a new column, or a new ROOM must be ONE
   REGISTRATION LINE — no edits to the level generator, renderers, or Level. This mirrors the
   blessed precedent already in this codebase: route/RouteRegistries.bootstrap() ("never a
   switch statement"). The whole point of the series is that future content is registered, not
   wired.

THE ORDER LIST (implement strictly in sequence)
===============================================
Each order is a small, reviewable, ideally-compilable step. Headless orders (no LibGDX) ship
with unit tests. Every order flips its own STATUS to IMPLEMENTED and updates the living doc
(see LIVING DOC CONTRACT below).

  order-1  Tile categories + environment-sprite registry (the art CATALOG). Headless data model:
           TileCategory, EnvironmentSpriteDefinition, EnvironmentSpriteRegistry,
           TilesetRegistries.bootstrap(). Registers every EXISTING wall/column/prop/decal as a
           sprite definition. No behaviour change.
  order-2  Symbol budget: FIXED vs FLEXIBLE. SymbolClass, the reserved/flexible split of the
           alphabet, SymbolBudget. Pure config the allocator will consume. Revises the
           tile-symbols.txt rule.
  order-3  LevelPalette: the per-level (symbol -> category + sprite) binding, carried on Level.
           Ships a LEGACY default palette that exactly reproduces today's fixed mapping, so
           nothing breaks before renderers switch over. Headless.
  order-4  SymbolAllocator: the deterministic per-level assignment engine. Fixed symbols keep
           their sprite; placed signature rooms get their required sprites; remaining flexible
           symbols get rule-governed variety; freed symbols are reclaimed. Headless, seeded,
           unit-tested. THE HEART of the series.
  order-5  RoomBlueprint + RoomBlueprintRegistry. Wrap every EXISTING RoomType as a registered
           SIGNATURE blueprint declaring its symbol/category demand. Behaviour identical; the
           generator's room switches move behind the registry.
  order-6  Per-level texture realization: TextureGeneratorRegistry (sprite id -> procedural
           texture generator) + EnvironmentTextureSet that realizes ONLY the sprites this
           level's palette uses, and disposes them on teardown. The "subset per level" mechanism.
  order-7  Rewire WallRenderer / PropRenderer / Level to read the LevelPalette + Environment
           TextureSet instead of the static char tables. Visual variety now reaches the screen.
  order-8  LevelGenerator integration: pick room blueprints from the registry, ask the allocator
           for the palette, paint generic rooms/halls with rule-driven variety. Proves the
           requirements: a NEW generated room from freed symbols, and the square-column ('P' ->
           square sprite) case.
  order-9  Extensibility proof + docs. New doc docs/environment-tileset-system.txt; add ONE new
           wall sprite and ONE new room by registration alone (zero generator/renderer edits) as
           the acceptance test; CLAUDE.md + tile-symbols.txt + docs INDEX updates; hand-crafted
           level migration notes.

GLOSSARY (use these names verbatim across the series)
=====================================================
  TileCategory              — the fixed semantic class of a symbol (WALL, COLUMN, SOLID_PROP,
                              FLOOR_DECAL, ...). Answers "what does this symbol MEAN".
  EnvironmentSprite(Def)    — one concrete piece of art in a category (e.g. "plain wall",
                              "square column"). Registered; addressed by a stable string id.
  EnvironmentSpriteRegistry — category -> weighted list of sprite definitions. Where new art
                              registers.
  SymbolClass               — FIXED or FLEXIBLE.
  SymbolBudget              — the flexible symbols available to a level + the fixed reservations.
  LevelPalette              — the per-level binding: char -> (TileCategory, EnvironmentSpriteId).
  SymbolAllocator           — builds a LevelPalette deterministically from a seed + the rooms
                              actually placed + the registries.
  RoomBlueprint             — a registered room (SIGNATURE or GENERIC) declaring its symbol/
                              category demand + its architecture builder.
  EnvironmentTextureSet     — the per-level realized textures for exactly the sprites the palette
                              uses; disposed on level teardown.

CROSS-CUTTING RULES (apply to EVERY order)
==========================================
* The …toon3d.tileset package is HEADLESS — no com.badlogic.gdx.graphics.* imports, unit-testable
  without a GL context (same rule the route package follows). Sprites/colours are referenced by
  string id; the render layer resolves them.
* NOTHING downstream may switch on a hardcoded wall/prop/room list. It must ask a registry. This
  is the single most important rule (identical to the route series' load-bearing rule).
* No inline formulas — every non-trivial formula (palette seed, weighted pick) goes in
  GameMath.java with the mandatory Formula/Derivation/Edge-cases comment block.
* No hardcoded values — new numbers go in a Constants* file (order-2 adds TilesetConstants.java).
* Determinism: a given run/floor seed must always produce the same LevelPalette (permadeath
  fairness + seed sharing). Salt the palette seed so it never collides with floor/route seeds.
* Backward compatibility: hand-crafted assets/levels/*.txt use FIXED symbols and must render
  identically. The LEGACY default palette (order-3) guarantees this until, and after, the switch.

ACCEPTANCE CRITERIA (the whole series is done when ALL hold)
============================================================
[ ] Adding a new wall/prop/column SPRITE = one register() line, no renderer/generator/Level edits.
[ ] Adding a new ROOM = one RoomBlueprint register() line, no generator edits.
[ ] The 'P' column symbol can render as a round OR square column depending on the level's palette.
[ ] Two freshly generated levels visibly differ in their wall/environment sprites.
[ ] Every existing signature room still looks and plays exactly as it does today.
[ ] A brand-new generated room appears on levels where a signature room's symbols were freed.
[ ] Same seed => identical LevelPalette (headless test).
[ ] All hand-crafted assets/levels/*.txt render unchanged.
