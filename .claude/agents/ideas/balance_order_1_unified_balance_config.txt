=== PROBLEM ===

The game's balance numbers are scattered across at least 5 files:

  util/GameBalance.java      — XP, melee damage, ability magnitudes, credits,
                               enemy depth scaling, stat-system rates.
  util/EnemyConstants.java   — enemy HP, attack damage, range, move cadence.
  util/WeaponConstants.java  — weapon damage, clip size, range, falloff, ammo
                               box sizes, reload ticks, crit multiplier.
  util/ItemConstants.java    — player max HP/armour, medkit heal, ammo caps,
                               ammo box sizes, credit spawn weights.
  util/LevelGenConstants.java— per-room spawn chances, enemy density, ammo
                               drop chance, depth bonuses, loot room chances.

CONSEQUENCE: there is no single screen a designer can open to see "how hard is
this game and where do resources come from." Enemy HP lives in one file, the
weapon that kills it in another, the ammo that feeds the weapon in a third, and
the drop rate that supplies the ammo in a fourth. You cannot balance what you
cannot see in one place. This is the root cause of "the game is not balanced."

GameBalance.java is already 627 lines but — ironically — does NOT contain the
three numbers that matter most for difficulty: raw enemy HP, raw enemy damage,
and raw weapon damage. Those are in EnemyConstants and WeaponConstants.


=== GOAL ===

ONE file, `util/BalanceConfig.java`, that holds every number the difficulty
curve and resource economy depend on. Every other class references it. A
designer tunes the entire game from this one file. Rendering/cosmetic constants
(colors, sprite offsets, HUD geometry, shake magnitudes, bob speeds) STAY where
they are — they are not balance.

THE TEST: "If I change this number, does the game get easier, harder, more or
less generous with resources?" If yes -> it belongs in BalanceConfig. If it
only changes how something looks -> it stays in its current Constants file.


=== DESIGN ===

Create `util/BalanceConfig.java`. It is the canonical balance file. Two valid
implementation strategies (pick one in the rule-system idea, idea 2):

  STRATEGY A (recommended, low-risk): BalanceConfig becomes the single home for
    raw balance numbers. EnemyConstants/WeaponConstants/ItemConstants keep only
    cosmetic + structural fields and re-export balance fields FROM BalanceConfig
    (e.g. `EnemyConstants.PLAGUE_HULK_MAX_HEALTH = BalanceConfig.HULK_HP;`).
    Game code keeps compiling; nothing moves except the literal numbers. This is
    a mechanical refactor, not a behavior change — safe to do in one commit.

  STRATEGY B (bigger): fold GameBalance.java INTO BalanceConfig and delete the
    split entirely. Cleaner end state, larger blast radius. Defer to idea 2.

Organize BalanceConfig into clearly-labeled sections. Every field keeps a
one-line comment stating WHAT it controls and the realistic tuning range.

=== WHAT STAYS OUT (cosmetic — do NOT move) ===
  - All *_SHAKE_MAGNITUDE, *_FIRE_SHAKE, blast/arc visual spreads
  - All COLOR / RED / GREEN / BLUE / ALPHA fields
  - HUD geometry, face box, bar widths, font scales
  - Sprite offsets, bob speeds, texture paths/sizes
  - Animation durations that are purely visual (NOT move/rotate duration —
    those affect turn economy and ARE balance; see idea 4)
