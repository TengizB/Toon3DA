OWNS
====
The ART CATALOG: the fixed set of tile CATEGORIES and the registry of every environment SPRITE the
game can draw. This part introduces NO per-level binding, NO allocator, NO renderer change — it is
pure data + registration so later parts have a stable catalog to select from. It must compile and
be unit-testable headless (no LibGDX render calls).

Crucially, order-1 REGISTERS EVERY EXISTING wall, column, solid prop, and decal as a sprite
definition. After this order the code has a complete, enumerable inventory of today's art — the
thing that is currently scattered across WallRenderer's table and PropRenderer's switches — with
zero behaviour change. Nothing reads the registry yet; it just exists and is correct.

WHY A REGISTRY (the load-bearing decision)
==========================================
Today the art inventory is implicit and duplicated:
  * WallRenderer.wallTextureTable[char] (field ~line 135; filled ~lines 267-340) knows the wall
    textures.
  * PropRenderer.propHeightMultiplier(char) (~line 47) + its per-char draw dispatch know the props.
  * Level.isWall()/isPropSolid()/... know the categories.
Nobody can ask "what wall sprites exist?" without reading three files. Every new sprite edits all
of them. The fix is one authoritative, data-driven registry keyed by a stable sprite id, exactly
like route/GeneratorRegistry and route/NodeTypeRegistry. Adding a sprite becomes one registration
line; the allocator (order-4) and renderers (order-7) READ the registry and never hardcode a list.
This is the single most important rule of the whole series: nothing downstream switches on a
hardcoded sprite/category list — it asks a registry.

NEW PACKAGE
===========
Create `…toon3d.tileset` (new sub-package; documented in CLAUDE.md Package Rules in the order-9
doc pass). Rationale: the tileset system is its own subsystem (categories + sprites + budget +
allocator); it depends on nothing render-specific and is depended on by `level`, `world`, and
`render`, so a dedicated HEADLESS package keeps the dependency direction clean. Keep it free of
`com.badlogic.gdx.graphics.*` — same discipline as the `route` package.

CLASSES (all in …toon3d.tileset)
================================

1. TileCategory  (enum)
   The FIXED semantic class a symbol belongs to — "what a symbol MEANS", never varies per level.
   v1 members (one per existing Level predicate group):
     WALL            (Level.isWall)         — solid, blocks movement + raycasting, drawn as a stripe.
     COLUMN          (Level.isColumn)        — sub-cell cylinder/pillar (ray-circle), 'P' today.
     SOLID_PROP      (Level.isPropSolid)     — billboard that blocks movement (barrels, terminals…).
     FLOOR_DECAL     (Level.isPropDecal, non-pickup) — walkable flat billboard (corpses, stains…).
   Each member carries METADATA (not behaviour) so consumers stay data-driven:
     - id (stable string, e.g. "wall").
     - rendersAsStripe (bool) — WALL/COLUMN true; billboard categories false. Lets the renderer
       route a sprite to the wall pipeline vs the billboard pipeline without a hardcoded char check.
     - blocksMovement (bool) — WALL/COLUMN/SOLID_PROP true; FLOOR_DECAL false.
   NOTE ON SCOPE: order-1 covers ONLY the four FLEXIBLE-eligible visual categories above. Doors,
   pickups, keycards, ammo, hazards, enemy spawns, player-start, and exit are FIXED symbols with
   permanent meaning (order-2 formalises this) and are NOT part of the sprite registry — they keep
   their existing dedicated handling. Do not register them here.

2. EnvironmentSpriteDefinition  (immutable value object; Builder)
   One concrete piece of art. Fields:
     - id (stable string, e.g. "wall_plain", "wall_cryo", "column_round", "prop_locker",
       "decal_blood"). Stable ids so palettes/seeds stay reproducible across code changes.
     - category (TileCategory).
     - displayName (e.g. "Cryo Wall") — for tooling/logging only.
     - heightMultiplier (float) — for billboard categories, the current per-char height (e.g.
       locker 0.90, crate 0.50); 1.0 for WALL. Copy today's values from PropRenderer /
       tile-symbols.txt so nothing changes when order-7 reads them.
     - occluder (bool) — writes to the z-buffer (mirrors Level.isPropOccluder). Solid props true;
       flat floor stains false.
     - textureGeneratorId (string) — which procedural texture generator draws it (order-6 defines
       the generator registry). For v1 this equals the sprite id; kept separate so several sprites
       could share one generator later.
     - themeTags (Set<String>, optional) — coherence hints the allocator uses (order-4), e.g.
       "clinical", "industrial", "frost", "gore", "generic". Empty allowed.
   Built once at startup and registered. No LibGDX types anywhere in this class.

3. EnvironmentSpriteRegistry  (singleton, populated once at startup)
     - register(EnvironmentSpriteDefinition def)
     - get(String spriteId) -> EnvironmentSpriteDefinition (never null for a registered id).
     - allInCategory(TileCategory category) -> List<EnvironmentSpriteDefinition> (the pool the
       allocator draws variety from).
     - contains(String spriteId) -> boolean.
   Idempotent registration guard (double-register of the same id is a no-op or a clear throw —
   pick one and document it; route registries throw on duplicate, follow that).

4. TilesetRegistries  (bootstrap hub — the twin of RouteRegistries)
     - static EnvironmentSpriteRegistry sprites() — the shared singleton.
     - static void bootstrap() — idempotent; registers ALL v1 sprite definitions. Invoked once
       from the World.create() path, right next to RouteRegistries.bootstrap() (World.java ~338).
     - Private registerWalls()/registerColumns()/registerSolidProps()/registerDecals() helpers,
       each a flat list of builder+register lines. This is the human-readable inventory of the
       game's environment art.

WHAT ORDER-1 DELIBERATELY DOES NOT DO
=====================================
- Does not touch WallRenderer, PropRenderer, Level, or LevelGenerator. The static tables/switches
  stay exactly as they are; they remain the runtime authority until order-7. order-1 only ADDS the
  parallel registry so it can be validated against the existing tables.

TECHNICAL NOTES
===============
- Keep the whole package free of GL/render imports; heights and flags are plain floats/booleans,
  colours are NOT stored here (they live in the texture generators, order-6).
- Registration is startup-only; allocate freely. No render() involvement, so no allocation concern.
- A sanity unit test may assert the registry's WALL/COLUMN/SOLID_PROP/FLOOR_DECAL counts match the
  count of chars in the corresponding Level predicate today — a cheap guard that the inventory is
  complete and nothing was dropped.
