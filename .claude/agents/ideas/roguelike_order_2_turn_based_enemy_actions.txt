CATEGORY: Systems
TITLE: Turn System & Per-Tick Enemy Actions
---

OVERVIEW
========
The turn system is the heartbeat of the whole game: every player action that
"costs time" advances the world by exactly one tick, and on that tick every
enemy perceives, decides, and acts exactly once. This document specifies how the
world tick collects all enemy AI decisions and executes them after the player
acts, integrating cleanly with the existing IDLE -> MOVING / ROTATING player
state machine and the already-implemented TickEventBus.

It belongs here because without it enemies are inert billboards. Movement,
combat, hazards, reloads — every dynamic system hangs off "one player action ->
one world step." This is roguelike pillar "the world only moves when you do."

NOTE ON CURRENT STATE: the dispatch spine (TickEventBus / TickSubscriber /
EnemyTurnSubscriber) is already IMPLEMENTED — see global-tick-event-system.txt
(STATUS: IMPLEMENTED) and enemy_system.txt (STATUS: IMPLEMENTED, which defines
EnemyManager.takeTurn, perception, chain-alert, melee/ranged resolution, and
tile pathfinding). This doc is the UMBRELLA SPEC that ties those together and
fills the remaining gaps: deterministic action ordering, the wall-blocked /
rotation tick rules, and the (future) animated-enemy-turn gate. Where this doc
and the two implemented docs disagree, the implemented docs win — flag conflicts
in review.

GAMEPLAY LOOP
=============
A turn-consuming action is: a completed tile MOVE (W/S/Q/E that actually moved),
a completed ROTATE (A/D), a FIRE, or any USE/LOOT verb. A wall-blocked move that
never started does NOT consume a turn (per global-tick-event-system.txt).

ONE FULL TICK, step by step:
1. Player is IDLE. PlayerController.pollInput() reads input and starts an action
   (MOVING / ROTATING / FIRING / INTERACTING). Input is locked during animation.
2. The action animates (lerp over PLAYER_MOVE_DURATION etc.). NO enemy logic runs
   during the animation.
3. finishAction(causesTick, cause) runs on completion. If causesTick, it calls
   tickEventBus.fireTick(playerColumn, playerRow, player, cause).
4. fireTick() dispatches subscribers IN REGISTRATION ORDER (the deterministic
   action-ordering contract):
     (1) WeaponReloadSubscriber  — advances reload countdown.
     (2) EnemyTurnSubscriber     — runs the full enemy simulation (takeTurn).
     (3) [future] HazardSubscriber, then DeathCheckSubscriber (order-1) LAST.
5. EnemyManager.takeTurn() processes ALL enemies synchronously in spawn-index
   order (deterministic): PERCEPTION (alert by radius or LOS) -> CHAIN-ALERT
   (BFS scream propagation) -> ACTION (alerted enemies only). See enemy_system.txt
   for the exact per-enemy resolution.
6. Per enemy in ACTION phase:
     - If Chebyshev distance to player == 1 and the enemy can attack: ATTACK
       (melee always lands if adjacent; ranged needs LOS). Damage routes through
       Player.applyDamage (order 3).
     - Else if ranged and within range and has LOS: RANGED ATTACK (no move).
     - Else CHASING: step one tile toward player via greedy cardinal pathfinding
       (see PATHFINDING). If no legal step, hold.
7. fireTick() returns. PlayerController is already back in IDLE; the player may
   act again on the next update(). The player is STRUCTURALLY unable to act until
   every enemy finished, because the enemy sim runs synchronously inside
   finishAction() inside the same update() frame.

PLAYER EXPERIENCE
=================
The felt rule is the Doom RPG / DCSS contract: "I did one thing, the monsters did
one thing." Every step is a tactical commitment — advance into a melee bruiser,
retreat and reload, or round a corner to break a ranged sightline. Because
turning costs a turn too, reorienting under pressure is a real decision. The
world is fully legible: the player can always reconstruct the exact sequence that
led to a hit or a death, which is the precondition for permadeath feeling fair.

PATHFINDING (tile space, cardinal only)
=======================================
Movement is cardinal only, so enemy chase steps are a greedy 1-tile pick toward
the player, NOT full A*:
- Compute differenceColumn = playerColumn - enemyColumn, differenceRow =
  playerRow - enemyRow.
- Prefer the axis with the larger absolute difference; try that cardinal step
  first (sign of the difference). If blocked (wall, closed door, occupied by
  another enemy or the player), try the other axis. If both blocked, hold.
- Occupancy: an enemy may not step onto a tile occupied by another living enemy
  or the player. Maintain this via EnemyManager's per-tile occupancy check.
- LOS uses tile-space Bresenham / DDA against Level.isWall (no float, cosmetic
  3D ignored). Closed doors block LOS; open doors do not.
Greedy chase is sufficient for v1 and keeps zero-allocation. A* with a scratch
frontier is a later upgrade for smarter flanking (lurker-crawler doc territory).

TECHNICAL NOTES
===============
DEPENDENCIES (must exist first):
- global-tick-event-system.txt (IMPLEMENTED): TickEventBus, TickSubscriber,
  TickContext, EnemyTurnSubscriber, WeaponReloadSubscriber.
- enemy_system.txt (IMPLEMENTED): EnemyManager.takeTurn + perception + AI.
- order 3 (player health/damage): the ATTACK branch calls Player.applyDamage.

This doc adds/clarifies, it does NOT rebuild the bus:
- Action-ordering contract: subscriber registration order in World's constructor
  IS the turn-order policy. Document it inline. Reload before enemies; a future
  death-check / hazard subscriber slots in explicitly.
- USE / LOOT verbs (from inventory-loot-ransack-system.txt): route through
  finishAction(true, cause) so they fire exactly one tick — same path as MOVE.
  Add TickCause values if needed (e.g. USE, LOOT) or reuse MOVE semantically;
  recommend extending the TickCause enum so subscribers can branch if they ever
  must. Flag as a small enum change to global-tick-event-system.txt.
- Animated-enemy-turn gate (FUTURE): when enemy turns become animated, add a
  boolean worldBusy owned by World/bus; PlayerController.pollInput() early-returns
  while worldBusy, and the enemy subscriber clears it when its animation queue
  drains. The bus dispatch point is the single place to add this gate. Until then
  enemy turns resolve instantly inside fireTick().
- Re-entry guard: optionally add a `boolean dispatching` flag in TickEventBus that
  throws if a subscriber triggers another tick (recommended once >3 subscribers).

Zero-allocation guarantee (preserved from the implemented bus): subscribers in a
pre-sized array, iterated by int index (no Iterator); one reused TickContext;
EnemyManager.takeTurn is already allocation-free.

Constants (most already exist via the implemented docs):
- MAX_TICK_SUBSCRIBERS = 16 (exists)
- ALERT_RADIUS_TILES, CHAIN_ALERT_RADIUS_TILES, VORTEX_EYE_RANGE_TILES (exist in
  enemy_system.txt)
- Add only if introducing USE/LOOT TickCause variants.

VISUAL DESIGN
=============
No new visual output of its own. The tick system is plumbing. It must add zero
draw calls and run entirely inside update(deltaTime), never inside render().
Visible consequences (enemy steps, attacks) are drawn by EnemyRenderer; the
red-alert wall pulse (emergency-red-alert-pulse.txt) is triggered when any enemy
wakes inside the enemy subscriber.

BALANCE NOTES
=============
- Dispatch ORDER is a balance lever: reload advances before enemies act, so a
  reload completing on a tick re-arms the weapon a hair "before" monsters move —
  cosmetic, since the player can't act until next tick. Insert future
  hazard-before-enemy effects accordingly. Flag any order change in review.
- Greedy pathfinding can let enemies bunch at corners; this is acceptable v1
  behavior and a natural difficulty governor (a corridor funnels a pack into
  single-file). Upgrade to flanking AI only if encounters feel too exploitable.
- Rotations costing a turn is the key tension knob: if turning feels too punishing
  in melee, that's a balance discussion for enemy_system, NOT a turn-system change.

INTERACTIONS
============
1. Enemy system (enemy_system.txt): EnemyManager.takeTurn is invoked by the enemy
   subscriber in a fixed slot; chain-alert, LOS, melee/ranged untouched.
2. Health & damage (order 3): the enemy ATTACK branch is the primary caller of
   Player.applyDamage; death is checked AFTER the full tick (order 1).
3. Weapon reload (global-tick-event-system.txt): reload advances on every tick
   (move OR fire) via the reload subscriber.
4. Doors: door open is a NON-tick interaction; door settle + keycard pickup happen
   in advanceMove BEFORE the tick fires, so enemies see the updated world on the
   same tick. Preserve that order.
5. Hazards (hazard-chain-reactions): a future HazardSubscriber ticks fire spread /
   toxic clouds once per turn with no World or PlayerController change.
6. Inventory loot/use (order 5): USE and LOOT each spend exactly one tick through
   the same finishAction path.

OPEN QUESTIONS
==============
- Should TickCause gain USE / LOOT variants now, or stay MOVE/FIRE until a
  subscriber actually needs to branch on them? Recommendation: add them when the
  first subscriber needs the distinction.
- Does FIRE consume a turn even when the shot hits a wall and nothing happens?
  global-tick-event-system.txt says YES; confirm before adding a "dry-fire is
  free" exception.
- When animated enemy turns land, does the player input buffer the next key (feel
  snappier) or hard-drop it (cleaner)? Recommend hard-drop for v1.
- Should two enemies ever resolve attacks simultaneously, or strictly in
  spawn-index order? Spawn-index order for determinism; revisit only if it creates
  unfair "first enemy always wins" patterns.
