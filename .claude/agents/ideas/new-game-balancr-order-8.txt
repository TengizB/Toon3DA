================================================================================
NEW GAME BALANCE — ORDER 8 of 8
PROOF: A TURN-EXACT RUN SIMULATOR + TELEMETRY + THE REGRESSION GATE
================================================================================
Requires: orders 1–7. This order closes the loop the knowledge doc warns about
on every page: "verified by harness only — NEVER playtested" (problem 1). A
green BalanceReport proves numbers are self-consistent; it cannot prove the
game PLAYS the way the model claims. Because the game is strictly turn-based
(one action = one turn, no physics, no aim skill), it is fully SIMULABLE —
almost no roguelike gets this lucky, and the balance system should exploit it.

--------------------------------------------------------------------------------
DESIGN
--------------------------------------------------------------------------------
A) THE RUN SIMULATOR (core test source, headless, no LibGDX):
   sim/BalanceSimulator: plays whole runs turn by turn through the REAL
   systems — real LevelGenerator floors, real EncounterBudgetPlanner rosters,
   real EnemyManager AI turns, real damage pipeline, real drops/economy/XP —
   with a scripted player POLICY instead of touch input. Determinism: seeded
   master RNG end to end (the generator and roller are already seed-driven;
   the sim asserts NO call site uses unseeded randomness — itself a
   worthwhile audit).

   POLICIES (deliberately simple heuristics, not AI):
     NAIVE     attacks nearest enemy, never guards, ignores hazards, heals at
               <30% HP, never switches weapons, walks the shortest route.
     TACTICAL  keeps range, breaks cardinal lines vs ranged, guards telegraphed
               spikes, herds through hazards, manages ammo across weapons,
               buys the shop backstop, takes upgrades.
     HOARDER-START-WEAPON  TACTICAL but never equips a new weapon (the user's
               boss-cheese reproduction, as a permanent regression case).

   OUTPUTS per (policy, seed): death depth, per-floor HP drain, ammo S
   experienced vs modelled, levels vs expected, boss fight turns, softlocks.
   Aggregated over SIM_SEED_COUNT (200) seeds into distributions.

B) THE BEHAVIORAL BANDS (the model's claims, tested against play):
   Registered in BalanceSchema like every other rule, run in a separate,
   slower gradle task (`./gradlew balanceSim`) with results checked by
   BalanceAuditTest against recorded summaries:
     S-GATE      HOARDER-START-WEAPON policy: 0% of 200 seeds clear the first
                 boss. (The original bug can never return.)
     S-FAIR      TACTICAL: median death depth in
                 [SIM_TARGET_DEPTH_MIN, MAX] = [8, 14]; >= 90% of deaths
                 preceded by a telegraphed hit or a resource state below 25%
                 (deaths are readable, not ambushes).
     S-SKILL     NAIVE dies meaningfully earlier than TACTICAL (median gap
                 >= 3 depths) — playing well must matter. This gap IS the
                 game's difficulty range: one fixed difficulty (order 7),
                 skill decides depth.
     S-ECONOMY   experienced S within ±0.08 of the modelled S per depth;
                 emergency rule triggers in < 5% of TACTICAL floors and 0% of
                 disciplined-ammo floors.
     S-SOFTLOCK  zero seeds end in "cannot damage anything" states.
   Bands are BalanceConfig SECTION 18 values — tunable targets like all others.

C) LIVE TELEMETRY (the human half — simulators can't feel fun):
   RunStats/StatsStore extended to record per real run: death depth &
   cause, per-floor HP drain, ammo starvation events, heals used, upgrades
   taken vs offered, boss fight turn counts, level vs expected level.
   Death screen gains a compact RUN AUTOPSY block (existing death overlay,
   ~6 lines) so playtesters can report "died depth 7, starved of shells,
   2 levels behind" without instrumentation builds. A dev dump (log print of
   the same stats each run end) closes the loop for tuning sessions.
   The tuning workflow becomes: telemetry says it FEELS wrong -> adjust the
   band/target -> dials re-derive -> simulator confirms the model -> humans
   confirm the feel. Numbers chase feel; the schema keeps them honest.

D) THE REGRESSION GATE (process, made mechanical):
   - `./gradlew test` (fast, every commit): all schema/audit rules, orders 1–7.
   - `./gradlew balanceSim` (slow, on balance changes + CI nightly): the
     behavioral bands above.
   - docs/game-balance-authority.txt gains the final section: THE CHANGE
     PROTOCOL — any BalanceConfig change ships with (1) green audit,
     (2) green sim, (3) updated living tables, (4) one sentence in the doc's
     CHANGELOG saying which dial moved and why. The knowledge doc's workflow
     (its SECTION 21) is superseded by this protocol; update the pointer.

--------------------------------------------------------------------------------
TECHNICAL NOTES
--------------------------------------------------------------------------------
  - The sim needs World's tick pipeline WITHOUT renderers: if World currently
    constructs renderers unconditionally, split a WorldSim core (managers +
    tick bus only) that World composes — an architecture win regardless
    (java-architect scope). No LibGDX imports anywhere in the sim path
    (Gdx.files use in LevelLoader may need a headless file source seam;
    generated levels avoid it entirely).
  - Policies are ~100-line heuristic classes implementing a PlayerPolicy
    interface (chooseAction(WorldView) -> TouchAction-equivalent); they reuse
    the same action entry points PlayerController calls — no parallel rules.
  - Runtime budget: 200 seeds x 3 policies (single difficulty — order 7) must
    finish < 10 min on CI; if not, trim seeds per policy (keep 200 for
    S-GATE — it is the headline guarantee).
  - Sim summaries written to build/reports/balance-sim/ as plain text tables;
    BalanceReport learns to inline the latest summary into the living tables.

--------------------------------------------------------------------------------
ACCEPTANCE CRITERIA
--------------------------------------------------------------------------------
  [ ] Full sim matrix runs headless and deterministically (same seed = same
      run) under `./gradlew balanceSim`.
  [ ] All five behavioral bands pass; S-GATE at exactly 0/200.
  [ ] Run autopsy visible on the death screen; dev dump logged at run end.
  [ ] CHANGE PROTOCOL section exists in docs/game-balance-authority.txt; the
      knowledge doc's workflow section points to it.
  [ ] A deliberate sabotage (e.g. double starting-shotgun damage locally)
      turns S-GATE red — the gate demonstrably catches the original bug class.

DEPENDENCIES: orders 1–7. This order completes the series: values in one
place, rules enforced, progression essential, resources scarce-but-fair,
threats priced honestly, bosses gated, one single fair difficulty — and
PROOF that it plays the way the math says.
