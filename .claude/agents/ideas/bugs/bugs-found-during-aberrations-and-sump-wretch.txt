OVERVIEW
--------
Four pre-existing or side-effect bugs found while building generated-enemy-art-order-5 and
sump-wretch-acid-death. None was fixed there, because each was out of that work's scope. One of them
(B1) can CRASH THE GAME in normal play. The other three are small. Each bug is independent and can
ship on its own; they are collected here so none is lost.

  B1  CRASH   EnemyManager's chain-alert queue overflows when enemies added after floor start wake.
  B2  LEVEL   LevelLoader's spawn-character list is missing '}' (Verdant Spiresower).
  B3  LEVEL   Linear-corridor floors can put four of one archetype in a room (the cap is three).
  B4  VISUAL  A closed door next to a dying Sump Wretch still shows an acid-splash burst.

Recommended order: B1 first (a crash), then B3, B2, B4.


SCOPE
-----
IN
  - B1: the chain-alert queue never overflows, however many enemies the floor gains after it starts.
  - B2: '}' in a hand-made level spawns a Verdant Spiresower (D1): add '}' to LevelLoader's list.
  - B3: EncounterPlacer never puts more than GROUP_ROOM_MAX_SAME_TYPE of one archetype in one room,
    on every generator, including linear_corridor.
  - B4: no splash burst is drawn on a closed-door tile.

OUT (deliberately not doing now)
  - Any change to the alert rules themselves (radius, line of sight, chain radius). B1 is a capacity
    bug only; who wakes stays exactly the same.
  - Placing the Spiresower or any new enemy in hand-made level files. B2 fixes the loader only.
  - Retuning GROUP_ROOM_MAX_SAME_TYPE or any other balance number. B3 makes the existing cap hold.
  - Changing who the death splash POISONS. B4 is cosmetic: the status logic in
    HazardManager.splashAcid is correct and stays as it is (a host standing in an OPEN doorway is
    still splashed, by design).


GAMEPLAY LOOP
-------------
No gameplay changes. After the fixes:
  1. B1: a Blight Corruptor summons, the HUNTED trail hunter arrives, or a boss summons minions;
     several of those new enemies wake on the same turn -> they alert and chain-alert normally, and
     the game does not crash.
  2. B2: a hand-made level containing '}' spawns a Verdant Spiresower.
  3. B3: every generated room holds at most three of one archetype.
  4. B4: a wretch dies beside a closed door -> bursts on the floor tiles only, none on the door.


RULES
-----
  R1  (B1) The chain-alert queue holds at least as many entries as there are enemies in the list at
      the moment alerting runs. It never relies on the floor's STARTING enemy count.
  R2  (B1) Each enemy enters the queue at most once per alert pass (it already does: an enemy is
      queued only when it changes from not-alerted to alerted). The fix must keep that true.
  R3  (B1) No allocation per turn. Grow the array only when the enemy count exceeds its length
      (amortised, rare), or size it once from a fixed upper bound.
  R4  (B3) The per-room cap is enforced at PLACEMENT, for every generator; the density audit V7 then
      passes without any waiver.
  R5  (B4) The burst skip is for closed doors (and any solid, non-walkable cell); open doorways keep
      their burst because a host can stand there.


PLAYER EXPERIENCE
-----------------
B1 is the only one a player can feel today, and they feel it as the app closing in the middle of a
fight. After the fix nothing is visible; the fight simply continues. B2-B4 are invisible or nearly so.


TECHNICAL NOTES
---------------
B1  CRASH — enemy/EnemyManager.java
    - The queue is allocated once, in the constructor (~line 286):
          this.chainAlertQueue = new int[Math.max(1, enemyCount)];
      where enemyCount = the enemies built from the level's spawn points.
    - Enemies are added later by spawnEnemy() (~line 904, enemies.add at ~929: summons, the HUNTED
      trail hunter, test spawns) and by the boss path (~line 1932).
    - The alert pass (~lines 1749-1778) writes chainAlertQueue[chainQueueSize++] for every newly
      alerted enemy, then again for every chain-alerted one. With more enemies in the list than the
      array's length, it throws ArrayIndexOutOfBoundsException.
    - Reproduced twice with the run-game skill: spawn two dormant enemies, let them wake on the same
      turn -> "ArrayIndexOutOfBoundsException: Index 1 out of bounds for length 1" (a floor whose
      start count was 1). Workaround used in testing: wake spawns one by one (alert:INDEX).
    - Fix: before the alert pass, if chainAlertQueue.length < enemies.size(), replace it with an
      array of at least enemies.size() (e.g. double it). That is a rare reallocation, not a per-turn
      one (R3).
    - Also check SimWorld: it uses the same EnemyManager, so the balance sim gets the fix for free.

B2  LEVEL — level/LevelLoader.java (~line 65)
    - The spawn test lists '1' '2' '3' '4' '5' '!' '$' '^' '~' 'z' 'K' 'V' '*' '(' '{' '[' 'n' 'o'
      but not '}'. EnemyManager.buildInitialEnemies DOES map '}' -> VERDANT_SPIRESOWER, and
      docs/tile-symbols.txt lists '}' as a spawn marker.
    - EncounterBudgetPlanner's comment says the Spiresower is "placed by its own systems", so the
      omission may be deliberate for GENERATED floors. In a HAND-MADE level, '}' is currently left in
      the grid as an unknown character instead of becoming an enemy.
    - Fix (D1): add '}' to the list and to the comment.

B3  LEVEL — level/EncounterPlacer.java (~lines 150-180)
    - The placer merges a group into a room only while
      region.mergedMaximumSameArchetype(group) <= GROUP_ROOM_MAX_SAME_TYPE, but on linear_corridor
      floors a room can still end up with four of one archetype.
    - Found when adding SUMP_WRETCH to the spawn pool shifted rosters: BalanceSchema density rule
      "linear_corridor COMBAT d1 room variety (V7)" went to 4.00 (band 0..3). It went back in band
      only because the wretch's TP was tuned; the underlying hole is still there and any future roster
      change can reopen it.
    - Likely cause to check first: linear_corridor's "rooms" are corridor segments, and a group placed
      across two segments (or a fallback path that ignores the cap when no region fits) bypasses the
      merged-count check.
    - Fix in the placer, not in the audit. Re-baseline LevelGeneratorSnapshotTest if the digest
      moves (an existing test; legitimate behaviour change).

B4  VISUAL — hazard/HazardManager.java, splashAcid (~line 235)
    - Neighbours are skipped only when Level.isWall(cell). A closed door is not a wall cell, so it gets
      an AcidSplashListener call and EnemyVisualLayer.onAcidSplash draws a burst on the door.
    - Fix: skip the LISTENER call (only the listener call) for a closed door / non-walkable cell.
      Whether a door is closed lives in DoorManager, not the cell; HazardManager may need a small
      query seam, or the check can move to World's listener lambda, which already sees the door state.
      The poison application must not change.
