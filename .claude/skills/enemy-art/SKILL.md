# Enemy art kit — enemy textures generated in code

Every enemy texture in toon3D is being replaced by sprites **generated by a script**, never painted
by hand and never made by an image model. The series that does it is
`.claude/agents/ideas/generated-enemy-art.txt` (+ `-order-1..7`). This skill is the tool.

It is a **dev tool**, like `run-game`: Python 3 + numpy + Pillow (both are pre-installed in the cloud
container), outside the Gradle build, never shipped. The game ships only the PNGs it writes.

## Files

| File | What it is |
|---|---|
| `kit.py` | The renderer. Shapes → per-layer height fields → normals → shading → palette → outline → cleanup. |
| `bestiary.py` | ONE function per sprite + the `ENEMIES` table. A new sprite = one function + one row. |
| `sheet.py` | Contact sheet of a folder of sprites, nearest-neighbour upscaled, on the game's near-black. |

Shipped textures: `assets/textures/enemies/generated/<sprite>.png` (160x240, binary alpha).

```bash
cd .claude/skills/enemy-art
python3 bestiary.py ../../../assets/textures/enemies/generated            # all sprites, shipping form
python3 bestiary.py /tmp/preview --halo warden                            # presentation form (soft glow)
python3 sheet.py /tmp/preview /tmp/preview/sheet.png 3
```
Output is deterministic (every noise source is seeded): the same script writes byte-identical PNGs.

## The rules every sprite obeys (the style lock)

1. **Originality.** Never open, trace, recolour or "improve" an existing enemy texture in
   `assets/textures/enemies/` (outside `generated/`). They were made by image models, they do not fit
   the game, and they are not reference material — not for shape, not for palette, not for pose. A sprite
   is designed from: the family's place in `story/00-premise.md`, the archetype's `role()` and
   `tacticalVerb()`, and ORA's bestiary line in `assets/story/story-strings.properties`.
2. **Canvas.** Regular enemies 160x240 (2:3, the aspect the renderer already draws), feet on row ~232,
   centred on x = 80. Bosses 240x360. A floating enemy whose type the renderer does NOT hover bakes the
   hover into the canvas (empty rows under it, like the Warden); a type the renderer hovers
   (`EYE_TYRANT`) stands on the canvas floor.
3. **One light rig, never per sprite.** Key light upper-left-front, FACILITY_CYAN rim from the right
   ("lit by the machine"), wrap shading, cavity occlusion, layer cast occlusion, Blinn specular per
   material. Changing `LIGHT`/`RIM` changes every enemy — that is the point.
4. **Palette.** Only `MATERIALS` ramps (6 steps, hue-shifted: cool shadows, warm lights). Add a
   material rather than tinting a sprite by hand. Semantic colours stay sacred (art-direction V5):
   no pure red / green / blue / purple / yellow as decoration. Family glow inks: MACHINE = `cyan`
   (the Organization's), INSECT + ABERRATION = `ichor` (harvested planet tissue), GOLEM = `magma` (and
   elemental variants), others decided by their order.
5. **Silhouette first.** Readable as a black shape at two tiles; distinct from every other enemy of its
   family; the size reads the role (chaff small, soldier medium, bruiser heavy, mini-elite spiked, boss
   huge). The attack is visible on the body (a ranged enemy shows its emitter, a charger its battering front).
6. **One story detail.** Each sprite carries at least one thing that ties it to the premise — an
   Organization tag, a harvest port, a shackle, a serial stencil (`stencil()`).
7. **Binary alpha.** `EnemySpriteSheets` alpha-cuts at 0.50, so shipped sprites are rendered WITHOUT
   the `--halo` glow; glow belongs to the emissive layer (series order 7), never baked translucency.
8. **Owner approval.** No sprite is wired into the game before the owner has seen its contact sheet
   AND an in-engine screenshot and said yes. The approval is written into the order file's DECISIONS.

## How a sprite is built (kit.py API)

A sprite is a list of LAYERS, back to front. Inside a layer every shape is a signed height field and
shapes are merged with a smooth maximum (`k` = blend radius in px), so limbs grow out of bodies instead
of being glued on. Between layers there is a hard edge with occlusion: put a limb in its own layer when
it must read as IN FRONT.

| Call | Shape |
|---|---|
| `blob(cx, cy, rx, ry, mat, depth=, angle=)` | ellipsoid dome |
| `limb(x1, y1, x2, y2, r1, r2, mat)` | tapered capsule |
| `chain([(x, y), ...], r1, r2, mat)` | bent limb: capsules with a tapering radius |
| `slab(points, mat, bevel=, slope=, tilt=)` | bevelled plate (armour, stone) |
| `mirror(shapes, axis)` | bilateral symmetry — design one half |
| `stencil(img, "W-07", x, y, colour)` | 3x5 pixel serial stencil, painted after render |

Shape options: `op="union"` (default) / `"add"` (raised detail painted in its own material: veins,
rivets, eyes, blisters) / `"carve"` (grooves, panel seams); `prio` biases which material wins where
shapes overlap; `k` the blend radius (0 = hard union).

## Lessons already paid for

- **Stacked rectangular slabs read as bricks.** The first golem (Mantle Sentinel) was built from flat
  polygon slabs over a glowing backing and the owner rejected it as the weakest. Mineral bodies need
  sculpted, irregular masses (blobs with grain, carved fractures), not rectangles.
- **Emissive intensity comes from the shape's OWN height**, not the layer's merged height — otherwise a
  glowing part sitting on a big body burns flat white. (Fixed in `kit.py`; do not regress it.)
- **Glow is easy to overdo.** Keep emissives to eyes, sacs, emitters and seams; a sprite that is mostly
  glow loses its form.
- **Bayer dither on flat areas turns into stipple.** Dither is 0.08; surface variety comes from
  material grain, not dither.
- **Mock-ups lie.** Pasting sprites onto a screenshot ignores the mood grade, fog, contact shadow and
  name tags. Judge in the engine (below).

## Seeing a sprite in the real game

Use the `run-game` skill. Until series order 1 wires a sprite to its `EnemyType`, preview it by
copying it over the texture of an existing type of similar height (in the WORKING TREE only — restore
with `git checkout -- assets/textures/enemies/` afterwards, never commit the swap), and spawn that type
in front of the player with the capture driver's `spawn:TYPE:FORWARD:RIGHT` step (added to
`run-game/capture` by series order 1). Two tiles ahead is the standard judging distance; also capture
one non-default mood (`--mood amber_hot`).
