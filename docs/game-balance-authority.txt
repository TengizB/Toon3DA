================================================================================
GAME BALANCE AUTHORITY — SINGLE SOURCE OF TRUTH + ENFORCED, TUNABLE SCHEMA
================================================================================
This document is the balance CONTRACT for toon3D — the replacement for the
old, deleted contract doc (balance-rule-system). It is the single source of truth for HOW
balance is governed; the factual map of the current balance STATE lives in
docs/game-balance-knowledge.txt (read that first for context and the known
problems). Created by new-game-balancr order 1; orders 2-9 register their rules
into the same schema.

CONTRACT: update this document in the SAME COMMIT as any change to
util/BalanceSchema.java, any new/changed band in util/BalanceConfig.java, or any
waiver. After any BalanceConfig change, re-run BalanceReport and paste its
output over SECTION 6 below.

--------------------------------------------------------------------------------
SECTION 1 — THE THREE LAYERS
--------------------------------------------------------------------------------
LAYER 1 — VALUES (tunable):        util/BalanceConfig.java
  EVERY gameplay-affecting number lives here, organised into 16 numbered
  sections (1-14 as before, plus 15 WEAPON ABILITY MAGNITUDES and 16 SHOP
  ECONOMY, both consolidated by order 1; shared status magnitudes joined
  SECTION 8, boss stats + boss AI tactic weights joined SECTION 14). Change a
  value -> the game gets easier/harder/more generous, and NOTHING else changes.
  The other *Constants files only RE-EXPORT these values under their old names
  (shims), so call sites never churned. EffectConstants now holds ONLY cosmetic
  values (colors, particle counts, screen shake); EnemyConstants keeps only
  cosmetic boss values (accent colors, sprites, telegraph visuals).

LAYER 2 — RULES (the schema):      util/BalanceSchema.java
  A declarative registry of every constraint the values must satisfy. Rules are
  DATA — registered subjects + bands evaluated through GameMath — never switch
  statements (the route/RouteRegistries discipline). A rule = (subject, formula
  via GameMath, band, waiver?). The schema also owns the content REGISTRIES the
  living tables print from: rangedWeapons(), telegraphAttacks(), healPickups(),
  scarcityRows(), the role-band maps, and the item classifications.

LAYER 3 — ENFORCEMENT:             core/src/test/.../util/BalanceAuditTest.java
  A plain JUnit test (pure JVM, no LibGDX) that runs every registered rule and
  FAILS THE BUILD on any unwaived violation. `./gradlew test` is the gatekeeper.
  One test method per rule kind, so a failure names the exact subject, value,
  and band. util/BalanceReport.java stays the human-readable table printer — a
  VIEW of the schema (its WEAPONS / ENEMIES / TELEGRAPH / WAIVERS tables iterate
  the schema registries), but the report can only WARN; the test GATES.

TUNABILITY IS PRESERVED BY CONSTRUCTION: designers tune LAYER 1 freely; the
schema only constrains values to their declared bands. A value that must
deliberately sit outside its band needs an explicit WAIVER (SECTION 4) —
visible, reasoned, auditable — never a silent exception.

--------------------------------------------------------------------------------
SECTION 2 — THE FOUR PRIMITIVES + DERIVED SCORES (pointers, not re-derivations)
--------------------------------------------------------------------------------
All formulas live in util/GameMath.java as pure static methods with
Formula/Derivation/Edge-case blocks. Full walkthrough: knowledge doc SECTION 2.

  eHP  effectiveHitPoints(...)         (rawHP + armor) * dodge * flat-reduction terms
  DPT  sustainedDamagePerTurn(...)     (clip * dmg) / (clip + reloadTicks)
       ammoEfficiency(...)             damagePerShot / ammoPerShot
  TTK  turnsToKill(...)                ceil(target.eHP / attacker.DPT)
  TP   threatPoints(...)               enemyDPT * survivalTurns * positionalMult

  weaponPowerScore(...)  = sustainedDPT * sqrt(ammoEff / 40)
  goldenRatio(...)       = turnsToDie / turnsToKill (TTK at the SUSTAINED
                           reference DPT — contract decision)
  depthThreatScale(...)  = healthScale^(d-1) * damageScale^(d-1)
  playerPowerAtDepth(...)= 1 + budgetPP * levelsPerDepth * (d-1) / 100
  depthCouplingRatio(...)= playerPower / enemyThreat
  survivalTurnsBought(...)= healValue / averageIncomingDamagePerTurn

  REFERENCE ANCHORS (BalanceConfig SECTION 9): REFERENCE_PLAYER_DPT = 25,
  REFERENCE_PLAYER_EHP = 205 (MARINE start), REFERENCE_AMMO_EFFICIENCY = 40.

--------------------------------------------------------------------------------
SECTION 3 — THE SCHEMA RULES (kind, band, and WHY the band is shaped so)
--------------------------------------------------------------------------------
R-WEAPON (RuleKind.WEAPON_POWER)
  Every ranged weapon is registered in BalanceSchema.rangedWeapons() with a
  ROLE; its weaponPowerScore must land in the role band:
    sidearm 8-14 | workhorse 12-18 | burst/specialist 18-26 | heavy/charge 24-32
  WHY: the bands overlap deliberately so roles form a ladder, not silos; higher
  rarity never raises a band — rarity buys ABILITIES, not raw DPT. Crediting
  notes (data on each spec): Railgun scored at full charge; Grenade Launcher on
  centre splash; Arc Cannon on the primary bolt (lateral chain uncredited);
  Incinerator as impact + one full burn application per shot (DoT is damage and
  counts toward TTK — an acknowledged muzzle-style over-credit, like falloff).

R-ENEMY (RuleKind.ENEMY_THREAT_POINTS + ENEMY_GOLDEN_RATIO)
  Every non-boss archetype (EnemyType.values(), role() as designer data) must
  land its threatPoints in the role TP band:
    chaff 16-34 | soldier 36-66 | bruiser 70-120 | mini-elite 160-310
  and (SOLDIER/BRUISER only) its golden ratio in band:
    soldier [3, 8] | bruiser [2, 4]
  WHY: TP is the currency the encounter budget spends; a mis-priced archetype
  corrupts every floor. Golden ratio below band = swingy/unfair, above =
  damage sponge. CHAFF is pack-exempt (budgeted by pack TP, a lone unit reads
  ~9-14); MINI_ELITE deliberately reads UNDER the duel band (a spike you avoid
  or spend heavies on). BOSS is exempt from both — governed by the SECTION 14
  boss ruleset instead.

R-CARD (RuleKind.CARD_BUDGET)
  Every level-up card (UpgradeCard.values(), estimatedPowerPoints()) must price
  into LEVEL_UP_BUDGET_PP (12) ± LEVEL_UP_BUDGET_TOLERANCE (15%) => [10.2,13.8].
  WHY: budget-equal cards make total player power build-independent
  (L * 12 PP at level L), which is what keeps every build on the
  depth-coupling curve.

R-HEAL (RuleKind.HEAL_PRICING)
  Every heal/armour pickup (BalanceSchema.healPickups()) is priced in SURVIVAL
  TURNS BOUGHT = value / averageIncomingDamagePerTurn on the model floor:
    small pickups ('+' stim, 'a' shard):  [2, 6] turns
    large pickups ('H' medkit, 'A' vest): [8, 16] turns
  WHY: under band = worthless filler; over band = removes the resource decision
  (a pickup should buy part of a fight, never a full reset). Current values:
  stim 5.0, shard 2.2, medkit 14.1, vest 9.7.

R-TELEGRAPH (RuleKind.TELEGRAPH)
  Registered attack list: BalanceSchema.telegraphAttacks(). No UN-readable
  (readable=NONE) attack may exceed TELEGRAPH_MAX_UNTELEGRAPHED_HIT_FRACTION
  (25% of reference eHP ~= 51 dmg) in one hit; NO boss attack may exceed
  BOSS_HARD_SINGLE_HIT_FRACTION (35% ~= 72 dmg), telegraphed or not.
  WHY: a death must feel like "I made a mistake", never a dice roll. Readable
  kinds: TELE (wind-up), LANE (cardinal-line tell), FACE (positional counter).
  NOTE: any NEW attack path must be added to the registered list — the audit
  only checks attacks it knows about.

R-DEPTH (RuleKind.DEPTH_COUPLING)
  depthCouplingRatio must hold [0.9, 1.2] for every depth 1..15.
  WHY: below = the compound enemy curve outran the linear player curve
  (unfair-hard); above = trivial-easy. A compound curve always outruns a linear
  one eventually — depths beyond 15 are accepted "graceful degradation" and are
  NOT audited (18/20 currently read 0.88/0.83 by design).

R-SCARCITY (RuleKind.SCARCITY)
  On the model floor (BalanceConfig SECTION 10): floor-wide S = SUPPLY/DEMAND
  in [0.75, 0.95]; every single weapon's share < 0.60; heal net-drain fraction
  in [0.05, 0.15] of reference eHP. Every AmmoType must have a registered
  scarcity row (coverage).
  WHY: scarcity is what turns a shooter into a roguelike — supply lands just
  below comfort so "shoot or save?" stays a real question; the per-weapon cap
  forces diversification; the net drain keeps HP precious without starving.

R-DOT (RuleKind.DOT_UNIQUENESS)
  Exactly ONE definition per status: the unified bases are
  BalanceConfig.BURN_DAMAGE_PER_TURN (4) and POISON_DAMAGE_PER_STACK (2).
  INCENDIARY_BURN_PER_TURN_BASE must BE the unified burn base (it references
  it). Structurally, every field in a shim class (GameBalance, EffectConstants,
  EnemyConstants, WeaponConstants, ItemConstants, LevelGenConstants, Constants)
  that shares a name with a BalanceConfig field must re-export it byte-for-byte
  — reflection catches any re-introduced divergent literal.
  HISTORY: two divergent BURN definitions coexisted (ability base 3 vs applied
  4); unification kept the EffectConstants value (4) because it was the one the
  game actually applied.

R-FLAGS (RuleKind.FLAGS)
  No live test/debug flags: every static boolean whose name contains TEST or
  DEBUG (scanned by reflection across all constant files) must be false, plus
  the explicitly-named GameBalance.START_ROOM_ANY_TIER_ENABLED.
  WHY: START_ROOM_ANY_TIER_ENABLED=true shipped legendaries into the start room
  for weeks; RouteMapConstants.BOSS_TEST_ALWAYS_CLICKABLE=true let testers skip
  regions. Both were set false by order 1; this rule makes the leak class
  structurally impossible to repeat.

COVERAGE (RuleKind.COVERAGE) — the anti-"shipped unpriced" rule
  The audit iterates the game's own content enums and FAILS if any entry is
  unclassified:
    - every WEAPON ItemType is RANGED (registered spec), MELEE, or
      AMMO_FALLBACK (WEAPON_PISTOL: no weapon class exists; picking it up
      grants bullets — see PlayerController);
    - every CONSUMABLE ItemType is a priced heal or declared UTILITY
      (STIMPACK is a temporary buff, not an HP resource);
    - every non-boss EnemyRole has a registered TP band;
    - every AmmoType has a scarcity row.
  WHY: the necrotic faction shipped un-priced and silently corrupted every
  floor budget for weeks. New content that skips pricing no longer produces a
  green build.

SECTION 4 — WAIVER POLICY + LIVE WAIVERS
--------------------------------------------------------------------------------
A waiver is the ONLY way a value may sit outside its band without failing the
build. Register it in BalanceSchema's static block via
  waive(kind, subject, reason, expiryCondition)
and mirror it HERE in the same commit. A waiver must state a real reason and a
condition under which it expires; BalanceReport prints all active waivers so
they can never fade into folklore. Never weaken a band to make a test pass.

LIVE WAIVERS (exactly one):
  [WEAPON_POWER] Railgun (full charge) — power score 45.0 vs heavy band 24-32.
    reason:  gated by slug scarcity, not raw damage; the 90-per-slug
             elite-buster hit is the heavy role's identity and supply
             (~1.1 slugs/floor, tightest reserve banking ~1.0 floor) is the
             real limiter. Nerfing the raw 90 would make the weapon worthless
             rather than merely scarce.
    expires: when the order-3 scarcity audit proves the slug gate in real play.

--------------------------------------------------------------------------------
SECTION 5 — NEW-CONTENT CHECKLIST
--------------------------------------------------------------------------------
1. Add the tuning numbers to util/BalanceConfig.java FIRST (correct section),
   then reference them from the matching *Constants shim if call sites need the
   old name.
2. Declare the content's role/band in util/BalanceSchema.java:
     new ranged weapon -> add a RangedWeaponSpec (role + stat block) AND its
                          ItemType classification; add its attacks to the
                          telegraph list if any hit can exceed the cap
     new enemy         -> nothing to register: EnemyType.role() is the
                          declaration; the audit picks it up automatically
                          (a new ROLE needs a TP band entry)
     new card          -> nothing: UpgradeCard.values() is iterated
     new heal/pickup   -> add a HealPickupSpec + consumable classification
     new ammo type     -> add a ScarcityRowSpec
     new status        -> ONE base definition in BalanceConfig SECTION 8
3. Run `./gradlew test` — BalanceAuditTest must be green. If a value must
   deliberately sit out of band, register a waiver (SECTION 4), never a hack.
4. Run BalanceReport and paste its output over SECTION 6 below.
5. Update this document (and docs/game-balance-knowledge.txt if the factual
   map changed) in the SAME commit.
