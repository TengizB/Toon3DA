================================================================================
GAME BALANCE AUTHORITY — SINGLE SOURCE OF TRUTH + ENFORCED, TUNABLE SCHEMA
================================================================================
This document is the balance CONTRACT for toon3D — the replacement for the
old, deleted contract doc (balance-rule-system). It is the single source of truth for HOW
balance is governed; the factual map of the current balance STATE lives in
docs/game-balance-knowledge.txt (read that first for context and the known
problems). Created by new-game-balancr order 1; orders 2-9 register their rules
into the same schema.

CONTRACT: update this document in the SAME COMMIT as any change to
util/BalanceSchema.java, any new/changed band in util/BalanceConfig.java, or any
waiver. After any BalanceConfig change, re-run BalanceReport and paste its
output over SECTION 6 below.

--------------------------------------------------------------------------------
SECTION 1 — THE THREE LAYERS
--------------------------------------------------------------------------------
LAYER 1 — VALUES (tunable):        util/BalanceConfig.java
  EVERY gameplay-affecting number lives here, organised into 17 numbered
  sections (1-14 as before, plus 15 WEAPON ABILITY MAGNITUDES and 16 SHOP
  ECONOMY, both consolidated by order 1, and 19 ROUTE ECONOMICS, added by
  order 7 — the branching MAP's numbers: node budget scales, affix multipliers,
  calm/elite/mystery/event payoffs, the audited map shape, the node-pricing
  model's knobs and every route band; shared status magnitudes joined
  SECTION 8, boss stats + boss AI tactic weights joined SECTION 14). Change a
  value -> the game gets easier/harder/more generous, and NOTHING else changes.
  The other *Constants files only RE-EXPORT these values under their old names
  (shims), so call sites never churned. EffectConstants now holds ONLY cosmetic
  values (colors, particle counts, screen shake); EnemyConstants keeps only
  cosmetic boss values (accent colors, sprites, telegraph visuals).

LAYER 2 — RULES (the schema):      util/BalanceSchema.java
  A declarative registry of every constraint the values must satisfy. Rules are
  DATA — registered subjects + bands evaluated through GameMath — never switch
  statements (the route/RouteRegistries discipline). A rule = (subject, formula
  via GameMath, band, waiver?). The schema also owns the content REGISTRIES the
  living tables print from: rangedWeapons(), telegraphAttacks(), healPickups(),
  scarcityRows(), the role-band maps, and the item classifications.

LAYER 3 — ENFORCEMENT:             core/src/test/.../util/BalanceAuditTest.java
  A plain JUnit test (pure JVM, no LibGDX) that runs every registered rule and
  FAILS THE BUILD on any unwaived violation. `./gradlew test` is the gatekeeper.
  One test method per rule kind, so a failure names the exact subject, value,
  and band. util/BalanceReport.java stays the human-readable table printer — a
  VIEW of the schema (its WEAPONS / ENEMIES / TELEGRAPH / WAIVERS tables iterate
  the schema registries), but the report can only WARN; the test GATES.

TUNABILITY IS PRESERVED BY CONSTRUCTION: designers tune LAYER 1 freely; the
schema only constrains values to their declared bands. A value that must
deliberately sit outside its band needs an explicit WAIVER (SECTION 4) —
visible, reasoned, auditable — never a silent exception.

--------------------------------------------------------------------------------
SECTION 2 — THE FOUR PRIMITIVES + DERIVED SCORES (pointers, not re-derivations)
--------------------------------------------------------------------------------
All formulas live in util/GameMath.java as pure static methods with
Formula/Derivation/Edge-case blocks. Full walkthrough: knowledge doc SECTION 2.

  eHP  effectiveHitPoints(...)         (rawHP + armor) * dodge * flat-reduction terms
  DPT  sustainedDamagePerTurn(...)     (clip * dmg) / (clip + reloadTicks)
       ammoEfficiency(...)             damagePerShot / ammoPerShot
  TTK  turnsToKill(...)                ceil(target.eHP / attacker.DPT)
  TP   threatPoints(...)               enemyDPT * survivalTurns * positionalMult

  weaponPowerScore(...)  = sustainedDPT * sqrt(ammoEff / 40)
  goldenRatio(...)       = turnsToDie / turnsToKill (TTK at the SUSTAINED
                           reference DPT — contract decision)
  depthThreatScale(...)  = healthScale^(d-1) * damageScale^(d-1)
  playerPowerAtDepth(...)= 1 + budgetPP * levelsPerDepth * (d-1) / 100  (v1 cards-only)
  playerPowerAtDepthV2(..)= cardPower * gearRamp * abilityPower (HONEST, all sources; order 4)
  depthCouplingRatio(...)= playerPowerV2 / enemyThreat
  xpRequiredForLevelGeometric(..)= base * growth^(level-1)  (order 4)
  xpRewardAtDepth(...)   = round(xpPerThreatPoint * enemyThreatAtDepth)  (order 4)
  turnsToKillBreakpointGain(..)= TTK(before) - TTK(after)  (order 4)
  survivalTurnsBought(...)= healValue / averageIncomingDamagePerTurn

  REFERENCE ANCHORS (BalanceConfig SECTION 9): REFERENCE_PLAYER_DPT = 25,
  REFERENCE_PLAYER_EHP = 205, REFERENCE_AMMO_EFFICIENCY = 40. The eHP anchor is
  THE canonical start (SECTION 7 PLAYER_START_* block, 130 HP + 75 armour) — the
  game has exactly one difficulty, so it describes every real run (R-SINGLE-DIFFICULTY).

--------------------------------------------------------------------------------
SECTION 3 — THE SCHEMA RULES (kind, band, and WHY the band is shaped so)
--------------------------------------------------------------------------------
R-WEAPON (RuleKind.WEAPON_POWER)
  Every ranged weapon is registered in BalanceSchema.rangedWeapons() with a
  ROLE; its weaponPowerScore must land in the role band:
    sidearm 8-14 | workhorse 12-18 | burst/specialist 18-26 | heavy/charge 24-32
  WHY: the bands overlap deliberately so roles form a ladder, not silos; higher
  rarity never raises a band — rarity buys ABILITIES, not raw DPT. Crediting
  notes (data on each spec): Railgun scored at full charge; Grenade Launcher on
  centre splash; Arc Cannon on the primary bolt (lateral chain uncredited);
  Incinerator as impact + one full burn application per shot (DoT is damage and
  counts toward TTK — an acknowledged muzzle-style over-credit, like falloff).

R-ENEMY (RuleKind.ENEMY_THREAT_POINTS + ENEMY_GOLDEN_RATIO)
  Every non-boss archetype (EnemyType.values(), role() as designer data) must
  land its threatPoints in the role TP band:
    chaff 16-34 | soldier 36-66 | bruiser 70-120 | mini-elite 160-310
  and (SOLDIER/BRUISER only) its golden ratio in band:
    soldier [3, 8] | bruiser [2, 4]
  WHY: TP is the currency the encounter budget spends; a mis-priced archetype
  corrupts every floor. Golden ratio below band = swingy/unfair, above =
  damage sponge. CHAFF is pack-exempt (budgeted by pack TP, a lone unit reads
  ~9-14); MINI_ELITE deliberately reads UNDER the duel band (a spike you avoid
  or spend heavies on). BOSS is exempt from both — governed by the SECTION 14
  boss ruleset instead.

R-CARD (RuleKind.CARD_BUDGET)
  Every level-up card (UpgradeCard.values(), estimatedPowerPoints()) must price
  into LEVEL_UP_BUDGET_PP (12) ± LEVEL_UP_BUDGET_TOLERANCE (15%) => [10.2,13.8].
  WHY: budget-equal cards make total player power build-independent
  (L * 12 PP at level L), which is what keeps every build on the
  depth-coupling curve.

R-HEAL (RuleKind.HEAL_PRICING)
  Every heal/armour pickup (BalanceSchema.healPickups()) is priced in SURVIVAL
  TURNS BOUGHT = value / averageIncomingDamagePerTurn on the model floor:
    small pickups ('+' stim, 'a' shard):  [2, 6] turns
    large pickups ('H' medkit, 'A' vest): [8, 16] turns
  WHY: under band = worthless filler; over band = removes the resource decision
  (a pickup should buy part of a fight, never a full reset). Current values:
  stim 5.0, shard 2.2, medkit 14.1, vest 9.7.

R-TELEGRAPH (RuleKind.TELEGRAPH)
  Registered attack list: BalanceSchema.telegraphAttacks(). No UN-readable
  (readable=NONE) attack may exceed TELEGRAPH_MAX_UNTELEGRAPHED_HIT_FRACTION
  (25% of reference eHP ~= 51 dmg) in one hit. The 35% hard cap
  (BOSS_HARD_SINGLE_HIT_FRACTION) now applies to boss verbs via R-BOSS-VERB-CAP
  (order 6) — boss verbs are DERIVED per depth, not flat, so they are checked there
  (at their derived values) rather than in this flat, depth-scaled trash-mob list.
  WHY: a death must feel like "I made a mistake", never a dice roll. Readable
  kinds: TELE (wind-up), LANE (cardinal-line tell), FACE (positional counter).
  NOTE: any NEW attack path must be added to the registered list — the audit
  only checks attacks it knows about.

R-DEPTH (RuleKind.DEPTH_COUPLING) — RE-DERIVED vs the HONEST power model (order 4)
  depthCouplingRatio must hold [0.9, 1.2] for every depth 1..15, where player
  power is now GameMath.playerPowerAtDepthV2 — the HONEST total-power model:
      playerPowerV2(d) = cardPower(d) * gearRamp(d) * abilityPower(d)
        cardPower   = the old v1 linear level-up term (1 + budgetPP*lpd*(d-1)/100)
        gearRamp    = gearRampAtDepth (order-2 gear curve, CONTINUOUS ramp form —
                      reaches the step value at each region's end, no boundary
                      jumps, because a fixed ratio band cannot absorb a x1.35 jump;
                      the STEP gearCurve stays the gate's tool)
        abilityPower= 1 + expectedAbilityPowerPointsAtDepth/100 (the priced weapon
                      ability budget the expected arsenal carries, order-2 tables)
  WHY v2: the OLD coupling counted ONLY cards, defending a FICTION of player power;
  difficulty tuned against fiction cannot feel right (order 4, problem 1). The
  honest curve is far steeper (v2(15) ~= 5.5 vs the fiction's 2.68), so the enemy
  DAMAGE compound was RE-FIT 1.032 -> 1.073 (HEALTH held at 1.042 so order-3
  scarcity is untouched; damage cancels in the heal-drain fraction and only
  interacts with the gate, which stays in band — region-2 on-curve soldier golden
  ratio = 3.0). The ratio now holds [0.9, 1.2] for 1..15 (~0.95..1.16) with NO
  under-band fudge; depths 16..20 (printed, not audited) degrade GRACEFULLY to the
  EASY side (an on-curve player pulls slightly ahead), never unfair-hard.

R-XP-PACE (RuleKind.XP_PACE) — XP pacing is a RULE, not a hope (order 4)
  For every depth 1..15: floorRosterXp(d) / xpRequired(expectedLevel(d)) in
  [XP_FLOOR_YIELD_MIN, MAX] = [1.0, 1.3] level-ups per floor. Per-enemy XP is
  DERIVED — xpReward = XP_PER_THREAT_POINT * enemyThreatAtDepth (one knob replaces
  13 hand-set constants) — and the XP curve is GEOMETRIC (base * growth^(level-1),
  growth 1.118 tied to the enemy threat compound), so roster XP and the level
  requirement grow at the SAME rate and the yield is depth-STABLE (~1.11). CATCH-UP
  (GameMath.catchUpScaledXp): a player > 1 level below expected gets XP * 1.5,
  forward-only. WHY: leveling must be FELT and PACED — a floor reliably buys ~1
  level at every depth, and a fallen-behind run can recover.

R-CARD-BREAKPOINT (RuleKind.CARD_BREAKPOINT) — a level-up must change the fight (order 4)
  Every level-up card must cross >= 1 INTEGER combat breakpoint vs the region
  soldier in some region: an OFFENCE card shaves a whole turn off the kill
  (GameMath.turnsToKillBreakpointGain), a DEFENCE card survives a whole extra hit
  (turnsToDie gain). Cards keep their equal PP budget (R-CARD); this rule proves
  the budget is spent where it FEELS different next fight, not just on the sheet.

R-SCARCITY (RuleKind.SCARCITY)
  On the model floor (BalanceConfig SECTION 10): floor-wide S = SUPPLY/DEMAND
  in [0.75, 0.95]; every single weapon's share < 0.60; heal net-drain fraction
  in [0.05, 0.15] of reference eHP. Every AmmoType must have a registered
  scarcity row (coverage).
  WHY: scarcity is what turns a shooter into a roguelike — supply lands just
  below comfort so "shoot or save?" stays a real question; the per-weapon cap
  forces diversification; the net drain keeps HP precious without starving.

R-DOT (RuleKind.DOT_UNIQUENESS)
  Exactly ONE definition per status: the unified bases are
  BalanceConfig.BURN_DAMAGE_PER_TURN (4) and POISON_DAMAGE_PER_STACK (2).
  INCENDIARY_BURN_PER_TURN_BASE must BE the unified burn base (it references
  it). Structurally, every field in a shim class (GameBalance, EffectConstants,
  EnemyConstants, WeaponConstants, ItemConstants, LevelGenConstants, Constants)
  that shares a name with a BalanceConfig field must re-export it byte-for-byte
  — reflection catches any re-introduced divergent literal.
  HISTORY: two divergent BURN definitions coexisted (ability base 3 vs applied
  4); unification kept the EffectConstants value (4) because it was the one the
  game actually applied.

R-FLAGS (RuleKind.FLAGS)
  No live test/debug flags: every static boolean whose name contains TEST or
  DEBUG (scanned by reflection across all constant files) must be false, plus
  the explicitly-named GameBalance.START_ROOM_ANY_TIER_ENABLED.
  WHY: START_ROOM_ANY_TIER_ENABLED=true shipped legendaries into the start room
  for weeks; RouteMapConstants.BOSS_TEST_ALWAYS_CLICKABLE=true let testers skip
  regions. Both were set false by order 1; this rule makes the leak class
  structurally impossible to repeat.

COVERAGE (RuleKind.COVERAGE) — the anti-"shipped unpriced" rule
  The audit iterates the game's own content enums and FAILS if any entry is
  unclassified:
    - every WEAPON ItemType is RANGED (registered spec), MELEE, or
      AMMO_FALLBACK (WEAPON_PISTOL: no weapon class exists; picking it up
      grants bullets — see PlayerController);
    - every CONSUMABLE ItemType is a priced heal or declared UTILITY
      (STIMPACK is a temporary buff, not an HP resource);
    - every non-boss EnemyRole has a registered TP band;
    - every AmmoType has a scarcity row.
  WHY: the necrotic faction shipped un-priced and silently corrupted every
  floor budget for weeks. New content that skips pricing no longer produces a
  green build.

R-GEARGATE (RuleKind.GEAR_GATE) — the expected arsenal curve (new-game-balancr order 2)
  Order 2 replaces the single fixed player anchor with a per-depth EXPECTED
  PLAYER whose weapon power steps up once per 5-floor region:
    gearCurve(d)                = GEAR_CURVE_PER_REGION ^ floor((d-1)/band)   (1.35^region)
    expectedPlayerDamagePerTurn = REFERENCE_PLAYER_DPT * gearCurve(d)
  gearCurve is 1.0 across all of region 1, so expectedPlayerDamagePerTurn(1..5)
  == REFERENCE_PLAYER_DPT EXACTLY (the run begins on the curve). The rule proves
  the GATE on a reference SOLDIER (Void Shroud) through the golden-ratio lens:
    1. START FAIR    — stagnant (never-upgraded, reference-DPT) golden ratio at
                       depth 1 is IN the soldier band [3,8];
    2. GATE FIRES    — the SAME stagnant player's golden ratio at the region-2
                       entry depth is BELOW the band (the start weapon now reads
                       underpowered — stagnation is punished);
    3. ON-CURVE FAIR — the EXPECTED player (reference * gearCurve) golden ratio
                       at that same depth is back IN band (upgrading keeps you
                       fair — the "find better gear or die" loop);
    + ANCHOR         — expectedPlayerDamagePerTurn(1..5) == REFERENCE_PLAYER_DPT.
  Region-1 fairness for the WHOLE roster is already guaranteed by R-ENEMY (same
  reference-DPT lens at depth 1); R-GEARGATE adds the depth axis. The curve is
  SUPPLIED, not just demanded: dropped weapons roll their tier from a per-region
  BAND (WEAPON_DROP_TIER_*_BY_REGION: region 1 COMMON..UNCOMMON, region 2
  UNCOMMON..RARE, ...), and THE PITY RULE (GUARANTEED_UPGRADE_PER_REGION, tracked
  in RunStats) force-spawns one in-band weapon on a region's last floor if none
  was placed. WHY: the old contract anchored every enemy to a FIXED 25 DPT
  forever, so never upgrading was viable by construction — you could beat a boss
  with the starting-room weapon. Now stagnation is FELT as mounting pressure and
  becomes lethal.

R-ABILITY (RuleKind.ABILITY_BUDGET) — tier is a priced ability budget (order 2)
  Rarity NEVER raises a weapon's POWER band (that is a role property, R-WEAPON) —
  it buys ABILITIES, and abilities are now PRICED in the SAME power points (PP =
  %-of-reference DPT/eHP) the level-up cards use (GameMath.abilityPowerPoints;
  an ability's magnitude converted to a %-of-reference, discounted by a
  utilisation weight for how often it applies). Each tier has an ability-PP
  budget: COMMON 0 | UNCOMMON 6 | RARE 12 | EPIC 20 | LEGENDARY 30 (±20%). The
  WeaponRoller fills abilities greedily and stops before the tier ceiling, so
  every roll — spawn OR shop tier-upgrade — fits its budget by construction. The
  rule asserts (a) every ability is priced to a finite, non-negative PP at every
  level and no ability's max-level PP exceeds the legendary ceiling, and (b) the
  tier budgets are monotonic with rarity; BalanceAuditTest additionally sweeps
  real rolls across seeds/levels/tiers and confirms no roll (in particular no
  legendary) exceeds its ceiling. WHY: the whole ability catalogue shipped as
  unpriced "PLACEHOLDER — flag for playtesting" magnitudes; this converts it to
  priced content in one pass. Magnitudes may still be tuned freely — the price
  recomputes from the magnitude, so tuning stays free.

R-SCARCITY-DEPTH (RuleKind.SCARCITY_DEPTH) — scarcity across the whole run (new-game-balancr order 3)
  R-SCARCITY checks the ammo economy on ONE depth-1 model floor; R-SCARCITY-DEPTH
  carries that anchor down the run and requires the scarcity ratio S in [0.75,
  0.95] at EVERY depth 1..15. The two curves it rides (deterministic, one source):
    DEMAND(d) = modelFloorDemand * healthScale^(d-1)          (enemy eHP compounds)
    SUPPLY(d) = modelFloorSupply * gearCurve(d)               (the EXPECTED arsenal,
                                  * AMMO_SUPPLY_REGION_MULTIPLIER[region]  order 2)
    S(d)      = SUPPLY(d) / DEMAND(d)               (GameMath.scarcityRatioAtDepth)
  SUPPLY is priced against the guns the player is EXPECTED to hold at d (gearCurve),
  not the starting weapons — or an upgrade would silently break the economy. Because
  gear steps ~+35%/region while eHP compounds ~+23%/region, S drifts within/across
  regions; the FIFTH lever AMMO_SUPPLY_REGION_MULTIPLIER (SECTION 5, default 1.0,
  here {1.08, 1.00, 0.94}) trims region 1's within-region dip up and the deeper
  regions' gear-outruns-eHP rise down, holding the band at all 15 depths. The slug
  reserve-banking gate stays the TIGHTEST (~1.0 floor at depth 1) — the Railgun
  power-band waiver is justified by scarcity, re-checked here.

R-HEALDRAIN-DEPTH (RuleKind.HEALDRAIN_DEPTH) — the heal economy, enforced (order 3)
  The per-floor NET HP drain holds [5%, 15%] of the player's current-difficulty eHP
  at EVERY depth 1..15 (R-SCARCITY only pins the model floor). Incoming damage, heal
  supply and eHP all ride the enemy-damage curve, so the drain FRACTION is depth-
  STABLE (GameMath.netHpDrainFractionAtDepth):
    netDrainFraction(d) = (incomingBase - healBase * HEAL_SUPPLY_REGION_MULTIPLIER[r])
                          / REFERENCE_PLAYER_EHP
  The shared depth factor cancels; with the region multipliers at their 1.0 default
  every floor costs ~11.5% of your depth-scaled eHP. WHY: HP is a slowly depleting
  run-resource — medkits are decisions ("spend now or bank"), and reaching a boss at
  full resources means you played well, not that the game is generous.

R-CREDITS (RuleKind.CREDITS) — the credit sink made real (order 3)
  Currency without a coupled sink is a score counter. The rule couples income to the
  shop: expected income per region / price of the expected purchase bundle in [0.9,
  1.4] for every region across depths 1..15.
    income(region)  = sum over the region's floors of (killBounty(d) + chipIncome)
                      (GameMath.creditIncomePerRegion; killBounty scales linearly)
    bundle(region)  = 1 significant (weapon-class, 12 PP) + 1.5 small (supply, 3 PP)
                      buys, priced through GameMath.shopPrice at the region's depth
  So a region affords roughly one significant purchase plus resupply, banking about
  one region's worth (CREDIT_BANK_TARGET_FLOORS). PRICING FROM POWER, NOT VIBES:
  every shop offer's price = valuePowerPoints * SHOP_CREDITS_PER_POWER_POINT *
  depthFactor(d) (GameMath.shopPrice) — a weapon-class upgrade on its ability/level
  PP, a consumable on its supply value converted to PP. There are ZERO hand-set per-
  offer base prices; SHOP_CREDITS_PER_POWER_POINT (36) is the single price-level knob.
  The shop is purchasable in-game end to end (stock -> price -> buy -> deduct ->
  deliver); order 3 finished the pricing half.

R-BOSS-* (RuleKind.BOSS_GATE / BOSS_FAIR / BOSS_VERB_CAP / BOSS_REWARD / BOSS_AMMO) — bosses as BUILD CHECKS (order 6)
  A boss's HP, DPT, every verb's damage, XP and credit reward are DERIVED at spawn by
  BossBalance.statsForDepth from the SECTION 14 inputs (per-boss TARGET_FIGHT_TURNS +
  survival ratio) through the GameMath BOSS BALANCE RULESET — there are ZERO flat boss
  HP/damage/reward constants left. The five rules assert the derivation upholds the
  contract at every act-boss depth (5, 10, 15, and every 5th floor in endless mode):
    R-BOSS-GATE     with the DEPTH-1 starting loadout (reference DPT), turnsToKill(boss)
                    >= BOSS_GATE_MIN_DAMAGE_MARGIN (2.0) x survivableTurns computed WITH
                    the maximum modelled heal supply (25% eHP). The start weapon cannot
                    win — a perfect-play hoarder dies at < half the damage needed. The
                    margin = (expectedDPT/refDPT)/survivalRatio, so it RISES with depth
                    (Overseer 2.08x is the tightest; Corruptor 2.56x; Hell Baron 3.04x).
    R-BOSS-FAIR     the EXPECTED loadout gets a fight in [target, 1.5*target] turns with
                    a survival ratio in [0.4, 0.7] (0.50 by construction).
    R-BOSS-VERB-CAP every DERIVED verb <= 35% eHP; any verb > 25% is telegraphed (checked
                    at the boss's canonical depth against the same caps as R-TELEGRAPH).
    R-BOSS-REWARD   credit reward >= modelled fight consumption (ammo + heal value in shop
                    units) x BOSS_REWARD_RISK_PREMIUM (1.3) — a boss floor is a net-positive
                    payday, never a loss for progressing. XP flows from boss Threat Points.
    R-BOSS-AMMO     the fight's ammo demand (eHP) is coverable by a full reserve at that
                    depth + the arena ammo budget (BOSS_ARENA_AMMO_BUDGET_FRACTION), so the
                    check tests your BUILD, not whether you arrived with full pockets.
  WHY: knowledge-doc SECTION 9 problem 4 — the three bosses were flat, eyeballed HP priced
  against the depth-1 shotgun, which is exactly why a level-1 weapon could beat them and
  every upstream progression system became optional. Derivation makes "beat the boss with
  the starting weapon" arithmetically impossible, verified by the audit. Soft ENRAGE
  (BOSS_ENRAGE_DPT_RAMP_PER_TURN, +8%/turn past 1.5*target, telegraphed "FURIOUS") enforces
  the R2 no-sponge ceiling by escalation, not a fail timer. The route generator guarantees a
  reachable SHOP or CACHE in the layer before every boss (the "sharpen your knife" beat),
  proven over 100 seeds (RouteMapGeneratorTest). Boss AI CHOREOGRAPHY is untouched — order 6
  prices the fight, not the tactic brain.

R-ROUTE-* (RuleKind.ROUTE_PRICED / RISK_PREMIUM / CALM_COST / MYSTERY_EV / PIPS_DERIVED / HONEST_SAFE /
           TRAJECTORY / ROUTE_GUARANTEES) — ROUTE ECONOMICS: the branching MAP joins the contract (order 7)
  Orders 1-6 balance FLOORS, but the player never plays "a floor" — they play a JOURNEY through the
  route map's DAG (COMBAT / ELITE / CACHE / REST / SHOP / MYSTERY / EVENT), and that macro layer is
  where run difficulty is actually decided. Order 7 prices it. Every node type, ELITE affix and MYSTERY
  outcome carries a NodeEconomics row (route/RouteEconomics — the map's twin of the weapon/enemy/heal
  registries); route/RouteEconomicsModel folds a row into one comparable EV through the SAME order-3/4
  models (supply/demand, heal economy, credit income, derived XP) in the shared POWER POINT currency:
      threatCost    = regionScaledFloorBudget(depth) * budgetScale * affixMultiplier   (GameMath.nodeThreatCost)
      resourceDelta = (supply - demand)/ammoPP + (heal - incoming)/healPP + credits/creditPP
      progress      = XP-as-levels * LEVEL_UP_BUDGET_PP + upgradeOpportunity * significant-buy PP
      EV            = resourceDelta + PERMANENT_POWER_WEIGHT * progress
                      - RISK_PP_PER_STANDARD_FLOOR * threatRatio                (GameMath.nodeExpectedValue)
  PERMANENT_POWER_WEIGHT (2.6) exists because a level or a gun applies to EVERY remaining floor while an
  ammo box is spent once; without it the model says fighting never pays, which is exactly how the
  un-priced map let a calm-chaining route out-earn a fighting one. The risk charge rides the threat
  RATIO, not raw Threat Points, so it is depth-stable.
    R-ROUTE-PRICED     COVERAGE for the map: a node type, affix or mystery outcome with NO ledger row
                       fails the build — the same anti-"shipped unpriced" rule order 5 applied to enemies.
    R-RISK-PREMIUM     (reward premium)/(threat premium) in [1.0, 1.2] for ELITE and EVERY affixed
                       variant: danger pays, slightly better than fair, never free and never a sucker
                       bet. SWARM/OVERCLOCKED raise threatCost, so they now carry VAULT PREMIUMS
                       (AFFIX_*_VAULT_AMMO_BOXES) that price up with them.
    R-CALM-COST        a calm node's EV sits [10%, 35%] BELOW a standard combat node's — the route doc's
                       "costs loot/tempo, never the clock" invariant as a number. The band's top edge is
                       0.35 rather than the idea's 0.30 because the discount necessarily WIDENS with
                       depth (a combat floor's own reward grows with the gear/ability curves while a
                       sanctuary payoff is capped by the player's own maxima) and ONE band must cover
                       depths 1..15. This rule is what RE-PRICED the order-8/9 hand-set payoffs: cache
                       supply down, med-bay heal + stock up, elite vault down, event payout up.
    R-MYSTERY-EV       the weighted outcome table within ±15% of a standard combat node at every audited
                       depth (order 9 ASSERTED this; it is audited now), and the worst outcome's expected
                       resource loss bounded by one floor's maximum modelled drain x 1.5 — "bad but
                       survivable" as arithmetic, not adjective.
    R-PIPS-DERIVED     DangerTier is DERIVED from the priced threat ratio, never hand-assigned
                       (GameMath.derivedDangerTierIndex: forced -> SET_PIECE, hidden outcome table ->
                       GAMBLE, else CALM <= 0.60x <= STANDARD <= 1.25x < DANGER), and must equal what the
                       overlay displays. The pips are the player's ONLY route information: if they drift
                       from the price the map LIES and informed choice collapses.
    R-HONEST-SAFE      CACHE/REST face <= 0.30x a combat floor's Threat Points (the HONEST-SAFE-NODE
                       design rule as an enforced bound — a "med-bay ambush" must be a MYSTERY wearing
                       its own face), and the MYSTERY scan tones partition consistently with their
                       prices: REWARD-RICH really is the richest bucket by EV, HIGH RISK really is the
                       most dangerous by threat.
    R-TRAJECTORY       the JOURNEY replaces the floor as the audited unit. 100 real maps are generated
                       headlessly and walked under three deterministic policies (SAFEST / DEADLIEST /
                       BALANCED); at every region boundary the cumulative order-3/4 quantities are
                       measured over the nodes ACTUALLY VISITED, each priced by its own row: scarcity S
                       [0.55, 1.60], per-floor net HP drain [-0.85, +0.45], XP pace [0.70, 2.30], and
                       depth coupling [0.80, 1.50] AT THE LEVEL THE ROUTE ACTUALLY BOUGHT (a route that
                       skips fights stands below the curve — GameMath.levelForCumulativeXp). All three
                       must hold: SAFEST rides the generous edge, DEADLIEST the starved edge, and those
                       ENDS are the game's real difficulty range (printed by BalanceReport).
    R-ROUTE-GUARANTEES no lane strands a run. Enforced at MAP-GEN by a deterministic no-RNG fixpoint
                       post-pass (RouteMapGenerator.repairBandGuarantees) and verified over the same 100
                       seeds: from every node with room ahead of it an UPGRADE-bearing node (ELITE/SHOP)
                       and a CALM node stay reachable inside the region; the layer before every boss
                       offers reachable provisioning (order 6's beat, which is also what covers the
                       band's tail); and every selectable layer offers >= 2 DISTINCT node types (no fake
                       choices). Order 2's "an upgrade per region" pity rule is now a graph property.
  WHY: knowledge-doc problem "the audited game and the played game diverge at the first branch". A
  player who chained caches sailed far above the order-3 supply band; one who never routed calm starved
  below it; ELITE's risk/reward and every affix multiplier were unpriced; and the risk pips were hand-set
  so the map could quietly lie. Full subsystem detail: docs/route-map-system.txt (ROUTE ECONOMICS).

R-SINGLE-DIFFICULTY (RuleKind.SINGLE_DIFFICULTY) — ONE difficulty, locked (order 8)
  DESIGN INVARIANT (owner decision, final): the game has EXACTLY ONE difficulty. There are no
  easy/normal/hard modes and there must never be. Every run starts from the one canonical
  attribute block — BalanceConfig SECTION 7: PLAYER_START_STRENGTH / _AGILITY / _TOUGHNESS /
  _MARKSMANSHIP = 2/2/2/2, which with PLAYER_MAX_HEALTH 130 + PLAYER_MAX_ARMOR 75 IS the
  REFERENCE_PLAYER_EHP = 205 anchor every band in orders 1-7 was derived against.
  Two structural checks (reflection, no gameplay values):
    1. BalanceConfig declares exactly ONE starting block — one PLAYER_START_<ATTRIBUTE>
       constant per Attribute. A second block is how a second mode starts.
    2. No constant, nested type or enum constant in any scanned class carries mode-family
       naming (RECRUIT / NIGHTMARE / ULTRA / DIFFICULTY / STAT_BASE_ / EASY_MODE / HARD_MODE) —
       the same tripwire R-FLAGS uses for live test flags. BalanceAuditTest adds the
       source-level half: it walks every file under core/src/main/java and fails on the mode
       names themselves, so a mode cannot return through a file the reflection sweep does not
       scan (a new Screen, a menu, a save field). BalanceSchema.java is the one excluded file:
       it DEFINES the banned tokens, and its own members are covered by check 2 itself.
  WHAT WAS REMOVED: four modes (the old RECRUIT/normal/NIGHTMARE/ULTRA tables in GameBalance),
  the Difficulty enum on PlayerStats, and the mode argument at run creation. StatsStore drops
  any legacy mode key on load (best-effort; a legacy record has always loaded fine because
  load() asks only for the keys it knows). There was no difficulty-selection screen to remove —
  World hard-coded the normal tier — so the mobile touch flow into a run is unchanged.
  WHY: the modes were wrong twice. They contradict the design (in this roguelike, difficulty is
  chosen INSIDE the run — route choice and the priced map, region danger, depth via the coupling
  curve, scarcity swings and loot luck — never from a menu), and even as implemented they were
  fake: modes changed ONLY starting stats while every enemy number, scarcity target and telegraph
  cap stayed anchored to the normal tier's 205 eHP, so three of the four were never actually
  balanced. Deleting three makes the contract EXACT for the one real game instead of exact for
  one mode out of four, and the telegraph fairness caps (25% un-telegraphed, 35% boss single hit)
  now provably protect the actual player pool in every run. No value was re-derived by this
  order — it removes an assumption, not numbers.
  TUNING: difficulty moves by moving THE dials — the scarcity band, the heal-drain band, the
  boss survival ratios, the region danger multipliers. One set, one game. If accessibility
  options are ever wanted they must be framed as exactly that (e.g. animation speed) and never
  as balance-touching modes; this rule is the tripwire.

NEVER-SOFTLOCK (GameMath.emergencySupplyTriggers, not a schema band — a floor guard)
  A player who wastes ammo must never die to an empty inventory screen. When total
  remaining potential damage (all reserves * per-shot damage + one melee swing) falls
  below remainingFloorDemand * EMERGENCY_SUPPLY_FRACTION (0.25), the next enemy drop
  is forced to be ammo for an equipped weapon, capped ONCE PER FLOOR (EnemyManager).
  0.25 sits far below the scarcity band, so a hoarder never trips it — it only turns
  "standing empty-handed" deaths into fighting-retreat deaths; melee (fist, no ammo)
  is the true backstop. Proven by a synthetic-inventory unit test (fires when starved,
  never when supplied, honours the once-per-floor cap). RunStats records ammo picked
  up, credits earned/spent, heals used and emergency triggers as order-9 telemetry.

S-GATE / S-FAIR / S-SKILL / S-ROUTE / S-ECONOMY / S-SOFTLOCK (RuleKind.SIM_*, order 9)
  THE BEHAVIOURAL BANDS — the only rules in this document that are checked against PLAY
  rather than against arithmetic. Everything above proves the numbers are self-consistent;
  it cannot prove the game plays the way they claim (knowledge-doc problem 1: "verified by
  harness only — NEVER playtested"). Because the game is strictly turn-based, a whole run is
  SIMULABLE: sim/BalanceSimulator plays SIM_SEED_COUNT (200) runs per policy through the REAL
  systems — real LevelGenerator floors via the real route pipeline, real EncounterBudgetPlanner
  rosters, real EnemyManager turns, the real damage/drop/XP/economy path, and the real
  PlayerController action entry points — with a scripted PlayerPolicy instead of touch input.
  Values live in BalanceConfig SECTION 18; the bands are evaluated in sim/BehavioralBands and
  gated by `./gradlew balanceSim` (BalanceSimTest), NOT by the fast `./gradlew test`.

  THE POLICIES (deliberately simple heuristics, not AI — the gap between them IS the game's
  difficulty range, since the game ships exactly one difficulty):
    NAIVE                 attacks the nearest enemy, never guards, ignores hazards and cardinal
                          lines, heals at <30% vitality, never switches weapons, walks the
                          shortest route, picks route nodes at random.
    TACTICAL              keeps range, breaks the cardinal line vs ranged, guards a telegraphed
                          spike (never twice running), manages ammo across weapons, heals early,
                          buys the shop backstop, takes upgrades, routes by the order-7 node EV.
    HOARDER-START-WEAPON  TACTICAL, but NEVER equips a weapon it finds or buys — the user's
                          boss-cheese reproduction, kept as a permanent regression case.

  S-GATE      HOARDER-START-WEAPON clears the FIRST boss on 0% of seeds. The headline
              guarantee: R-BOSS-GATE proves the starting loadout cannot win on paper; this
              proves it in play. WHY zero and not "rarely": the original bug WAS the starting
              shotgun grinding a boss down, and a band with slack invites it back.
  S-FAIR      TACTICAL median death depth in [SIM_TARGET_DEPTH_MIN, MAX] = [8, 14], and >= 90%
              of deaths preceded either by a COMMITTED enemy intent (the hit was shown before it
              landed) or by a sub-25% resource state (the player walked in weak). WHY: a death
              must feel like "I made a mistake", never a dice roll.
  S-SKILL     TACTICAL's median depth exceeds NAIVE's by >= SIM_SKILL_DEPTH_GAP_MIN (3). WHY:
              one fixed difficulty (order 8) only works if SKILL decides depth; if this gap
              collapses the game stopped rewarding play and became a wall.
  S-ROUTE     The played per-floor net HP drain sits inside the order-7 modelled trajectory
              band, widened by SIM_ROUTE_TRAJECTORY_TOLERANCE (play dodges fights the ledger
              charges for). WHY: the priced map must survive contact with play.
  S-ECONOMY   The experienced scarcity ratio S is within SIM_ECONOMY_SCARCITY_TOLERANCE (0.08)
              of the modelled S per depth, and the never-softlock lifeline fires on < 5% of
              floors. WHY: if the played S drifts, the model describes a different game.
  S-SOFTLOCK  Zero seeds end unable to damage anything. Structurally guaranteed rather than
              tuned: the Fist is wired at run start and never removed, so "no ranged ammo" is a
              fighting retreat, not a dead end. The band exists to keep that structural
              guarantee from being quietly removed.

  DETERMINISM is part of the contract: every stream is seeded from the run seed (level
  generation, route map, weapon roller, card deck, and — since order 9 — the enemy
  spawn/drop/effect rolls, weapon accuracy rolls, hazard rolls and the AGILITY dodge roll,
  all of which used to be unseeded). Same seed + same policy => byte-identical ledger;
  BalanceSimTest asserts it. Unseeded randomness in a gameplay path is now a determinism bug.

             the bands enforced against the real numbers.

SECTION 7 — THE CHANGE PROTOCOL (new-game-balancr order 9) — MANDATORY
--------------------------------------------------------------------------------
This section SUPERSEDES the workflow in docs/game-balance-knowledge.txt SECTION 21
(that section now points here). It is the whole series' closing move: values in one
place, rules enforced, and PROOF that the game plays the way the math says.

EVERY change to util/BalanceConfig.java ships with all four of these:

  1. GREEN AUDIT      `./gradlew test`
     Fast (seconds), runs on every commit. BalanceAuditTest evaluates every rule in
     BalanceSchema and fails the build on any unwaived violation. This is the
     gatekeeper for the NUMBERS.

  2. GREEN SIM        `./gradlew balanceSim`
     Slow (whole simulated runs), run on balance changes and nightly in CI.
     BalanceSimTest plays SIM_SEED_COUNT runs per policy through the real systems and
     checks the six behavioural bands. This is the gatekeeper for the BEHAVIOUR.
     Its plain-text summary lands in core/build/reports/balance-sim/summary.txt —
     read it even when it is green: "median death depth moved 9 -> 6" is a sentence
     you can act on long before a band breaks.

  3. UPDATED LIVING TABLES
     Re-run BalanceReport and paste its output over SECTION 6. The tables are a VIEW
     of the schema; a stale view is worse than none, because it reads as current.

  4. ONE CHANGELOG LINE (below)
     Which dial moved, and WHY. One sentence. The reason is the part that cannot be
     recovered from the diff six months later.

WHEN THE SIM AND THE MODEL DISAGREE, the sim wins — but only after you check WHICH
is wrong. A band can fail because the game got worse, or because the harness got
better (a policy that now finishes floors it used to stall on will move every depth
statistic). The report's per-policy columns (median depth, stalled, readable,
bossClear, softlock, level gap) are there to tell those two apart.

THE TUNING LOOP the whole series was built to enable:
     telemetry says it FEELS wrong (the RUN AUTOPSY on the death screen, and the
     same block logged at run end)
  -> adjust the BAND or the TARGET in BalanceConfig, never the call site
  -> the derived dials re-derive themselves
  -> `./gradlew test` confirms the model is still self-consistent
  -> `./gradlew balanceSim` confirms it still PLAYS that way
  -> humans confirm the feel.
  Numbers chase feel; the schema keeps them honest.

CHANGELOG
  encounter density (this commit) — the floor budget now converts into BODIES instead
    of stranding a quarter of itself: the anchor gained a real ceiling
    (ENCOUNTER_ANCHOR_BUDGET_CEILING_FRACTION, replacing a fallback that let one
    bruiser eat 76% of a small floor) and a REMAINDER PASS spends the leftover, so a
    CALM/CACHE floor went from EXACTLY 1 enemy on a ~1,100-tile dungeon to ~5.5 on the
    SAME Threat-Point budget. EVENT_BUDGET_SCALE / GATE_BUDGET_SCALE dropped 0.15/0.10
    -> 0 because they were DEAD (their generators emit no spawns and the ledger already
    priced them at 0), and EnemyBudgetOverride.empty() makes zero expressible at last —
    a non-positive scale used to be read as "unset" and silently became the FULL budget.
    WHY: floors read as abandoned; the budget was authorised but never delivered.
    NOTE: the change is TP-neutral but not eHP-neutral (cheap bodies carry more eHP per
    Threat Point than one bruiser), so SIM_ECONOMY emergency-lifeline floors moved
    0.04 -> 0.06, just past its 0.05 band and inside the existing waiver. Watch it.

  order 9 — added BalanceConfig SECTION 18 (simulation harness
    parameters + the six behavioural bands) and seeded every gameplay RNG stream off
    the run seed. No existing balance VALUE was changed: order 9 is proof
    infrastructure, not a tuning pass. Six bands ship WAIVED (SECTION 4) because the
    scripted navigation, not the balance, is what they currently measure.
