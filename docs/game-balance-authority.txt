================================================================================
GAME BALANCE AUTHORITY — SINGLE SOURCE OF TRUTH + ENFORCED, TUNABLE SCHEMA
================================================================================
This document is the balance CONTRACT for toon3D — the replacement for the
old, deleted contract doc (balance-rule-system). It is the single source of truth for HOW
balance is governed; the factual map of the current balance STATE lives in
docs/game-balance-knowledge.txt (read that first for context and the known
problems). Created by new-game-balancr order 1; orders 2-9 register their rules
into the same schema.

CONTRACT: update this document in the SAME COMMIT as any change to
util/BalanceSchema.java, any new/changed band in util/BalanceConfig.java, or any
waiver. After any BalanceConfig change, re-run BalanceReport and paste its
output over SECTION 6 below.

--------------------------------------------------------------------------------
SECTION 1 — THE THREE LAYERS
--------------------------------------------------------------------------------
LAYER 1 — VALUES (tunable):        util/BalanceConfig.java
  EVERY gameplay-affecting number lives here, organised into 17 numbered
  sections (1-14 as before, plus 15 WEAPON ABILITY MAGNITUDES and 16 SHOP
  ECONOMY, both consolidated by order 1, and 19 ROUTE ECONOMICS, added by
  order 7 — the branching MAP's numbers: node budget scales, affix multipliers,
  calm/elite/mystery/event payoffs, the audited map shape, the node-pricing
  model's knobs and every route band; shared status magnitudes joined
  SECTION 8, boss stats + boss AI tactic weights joined SECTION 14). Change a
  value -> the game gets easier/harder/more generous, and NOTHING else changes.
  The other *Constants files only RE-EXPORT these values under their old names
  (shims), so call sites never churned. EffectConstants now holds ONLY cosmetic
  values (colors, particle counts, screen shake); EnemyConstants keeps only
  cosmetic boss values (accent colors, sprites, telegraph visuals).

LAYER 2 — RULES (the schema):      util/BalanceSchema.java
  A declarative registry of every constraint the values must satisfy. Rules are
  DATA — registered subjects + bands evaluated through GameMath — never switch
  statements (the route/RouteRegistries discipline). A rule = (subject, formula
  via GameMath, band, waiver?). The schema also owns the content REGISTRIES the
  living tables print from: rangedWeapons(), telegraphAttacks(), healPickups(),
  scarcityRows(), the role-band maps, and the item classifications.

LAYER 3 — ENFORCEMENT:             core/src/test/.../util/BalanceAuditTest.java
  A plain JUnit test (pure JVM, no LibGDX) that runs every registered rule and
  FAILS THE BUILD on any unwaived violation. `./gradlew test` is the gatekeeper.
  One test method per rule kind, so a failure names the exact subject, value,
  and band. util/BalanceReport.java stays the human-readable table printer — a
  VIEW of the schema (its WEAPONS / ENEMIES / TELEGRAPH / WAIVERS tables iterate
  the schema registries), but the report can only WARN; the test GATES.

TUNABILITY IS PRESERVED BY CONSTRUCTION: designers tune LAYER 1 freely; the
schema only constrains values to their declared bands. A value that must
deliberately sit outside its band needs an explicit WAIVER (SECTION 4) —
visible, reasoned, auditable — never a silent exception.

--------------------------------------------------------------------------------
SECTION 2 — THE FOUR PRIMITIVES + DERIVED SCORES (pointers, not re-derivations)
--------------------------------------------------------------------------------
All formulas live in util/GameMath.java as pure static methods with
Formula/Derivation/Edge-case blocks. Full walkthrough: knowledge doc SECTION 2.

  eHP  effectiveHitPoints(...)         (rawHP + armor) * dodge * flat-reduction terms
  DPT  sustainedDamagePerTurn(...)     (clip * dmg) / (clip + reloadTicks)
       ammoEfficiency(...)             damagePerShot / ammoPerShot
  TTK  turnsToKill(...)                ceil(target.eHP / attacker.DPT)
  TP   threatPoints(...)               enemyDPT * survivalTurns * positionalMult

  roleScenarioClear(...) = fractional turns to clear an R-ROLE scenario (balance-overhaul
                           order 3; replaced weaponPowerScore, deleted with R-WEAPON)
  goldenRatio(...)       = turnsToDie / turnsToKill (TTK at the SUSTAINED
                           reference DPT — contract decision)
  depthThreatScale(...)  = healthScale^(d-1) * damageScale^(d-1)
  playerPowerAtDepth(...)= 1 + budgetPP * levelsPerDepth * (d-1) / 100  (v1 cards-only)
  playerPowerAtDepthV2(..)= cardPower * gearRamp * abilityPower (HONEST, all sources; order 4)
  depthCouplingRatio(...)= playerPowerV2 / enemyThreat
  xpRequiredForLevelGeometric(..)= base * growth^(level-1)  (order 4)
  xpRewardAtDepth(...)   = round(xpPerThreatPoint * enemyThreatAtDepth)  (order 4)
  turnsToKillBreakpointGain(..)= TTK(before) - TTK(after)  (order 4)
  survivalTurnsBought(...)= healValue / averageIncomingDamagePerTurn

  REFERENCE ANCHORS (BalanceConfig SECTION 9): REFERENCE_PLAYER_DPT = 25,
  REFERENCE_PLAYER_EHP = 205, REFERENCE_AMMO_EFFICIENCY = 40. The eHP anchor is
  THE canonical start (SECTION 7 PLAYER_START_* block, 130 HP + 75 armour) — the
  game has exactly one difficulty, so it describes every real run (R-SINGLE-DIFFICULTY).

SECTION 3 — THE SCHEMA RULES (kind, band, and WHY the band is shaped so)
--------------------------------------------------------------------------------
R-ROLE (RuleKind.WEAPON_ROLE) — balance-overhaul order 3 — every weapon is the
best answer SOMEWHERE and never everywhere.
  The registry is util/WeaponRoleModel: one row per ranged weapon, whose
  DamageClass, ammo type, clip, reload, range and accuracy are read from a FRESH
  INSTANCE of the weapon (one source of truth), plus its scenario shape (hits and
  ammo per action, SINGLE / PIERCE / CONE / SPLASH / CHAIN, charge, burn stacks,
  knockback / stagger, self-damage). Eight REFERENCE SCENARIOS (archetype = the
  representative of the trait and role, BalanceConfig SECTION 22 geometry):
    S1 FLESH single 3-5 (Plague Hulk)       S5 BURNABLE x3 1-3 (Ghoul)
    S2 FLESH x3 1-3 (Gore Biter, the A6     S6 CHITIN single 1-2 (Shell Brute)
       "on-curve chaff")                    S7 INFERNAL single 3-5 (Void Shroud)
    S3 SHIELDED single 3-5 (Acid Drone)     S8 a BRUISER charging from 3 tiles
    S4 PLATED single 3-6 (Cinderforge          (Shell Brute) — scored in HITS it
       Colossus, the PLATED tank)              lands before it dies
  evaluated for the ON-CURVE player (GameMath.expectedPlayerAtDepth; hits scale
  by its ladder factor, enemies by the NEUTRAL eHP at the depth) at depths 5 and
  15. GameMath.roleScenarioClear walks the fight turn by turn (reload, Railgun
  charge, fire, then burn ticks) and reports FRACTIONAL turns to clear (the last
  turn counts only the share the killing blow needed), actions and ammo;
  GameMath.roleScenarioBruiserHitsTaken plays S8, crediting the SPREAD knockback
  (one tile) and stagger (one cancelled action, never two turns running).
  MODEL ASSUMPTIONS: expected-value accuracy on every hit; no crits, abilities or
  cards; a group is clustered in the band (a cone or splash reaches all of it, a
  pierce ROLE_GROUP_TARGETS_IN_LANE = 2 of it, the Arc's chain up to its jumps at
  never-resisted damage); the Railgun always fires at FULL charge (one charge
  turn, then the shot). "Best" = fewest turns among ammo-FEASIBLE clears (ties:
  every tied class is best).
    R-ROLE-1 NICHE      every ranged class but BALLISTIC is best in >= 1 scenario
                        by >= 1.20x over the best BALLISTIC weapon (S8: on hits+1).
                        Melee (BLADE / BLUNT) is EXEMPT: no ammo, adjacent only,
                        the fallback — not modelled (recorded decision).
    R-ROLE-2 GENERALIST BALLISTIC within 1.30x of the best in S1; never best in
                        S3 or S4.
    R-ROLE-3 NO DOMINANCE no class best in more than 2 scenarios (per depth).
    R-ROLE-4 RISK PAYS  every SPREAD weapon's SUSTAINED per-turn damage at 1-2
                        tiles (accuracy-weighted, reload counted) >= 2.0x the
                        Assault Rifle's at 3 tiles. The reference is the Assault
                        Rifle — W1's own wording and R-LADDER's generalist — not the
                        Chaingun (whose three-round action sustains ~2x the rifle).
    R-ROLE-5 AMMO FEASIBLE every class clears its DECLARED niche scenario
                        (ROLE_DECLARED_NICHE_BY_CLASS: BALLISTIC S1, SPREAD S6,
                        ENERGY S3, RAIL S4, FIRE S5, EXPLOSIVE S2 — reviewer fix:
                        it read the first scenario the class was closest to the best
                        in, which for RAIL was S1, so AS8's PLATED slug check never
                        ran) with <= one AVERAGE COMBAT floor's planned supply of its
                        ammo type (the CURRENT SupplyPlanner over 20 rosters, the
                        player carrying BULLETS + that type).
    A6                  the Incinerator clears S2 in <= 2 sprays at both depths.
  FITTED (CP3b): Shotgun 44 -> 66, Double-Barrel 32 -> 59 (0.9x per barrel,
  W2), Arc Cannon 28 -> 40, Railgun full charge 90 -> 75, Grenade centre/
  neighbour 42/22 -> 36/32, Incinerator burn fraction 0.5 -> 0.6 (impact 12 / 8
  kept), shell box 4 -> 3 and shell cap 17 -> 11 (same damage per box / banked).
  Assault Rifle and Chaingun unchanged; R-LADDER untouched. Resulting niches:
  RAIL S1 + S4, EXPLOSIVE S2, ENERGY S3 + S7, FIRE S5, SPREAD S6 + S8; BALLISTIC
  best nowhere, within 1.23x of S1's best.
  OVERRIDE RECORD (balance-overhaul order 3 OVERRIDE CLAUSE):
    R-WEAPON (RuleKind.WEAPON_POWER) — RETIRED. It required every ranged weapon's
    weaponPowerScore (sustained DPT x sqrt(ammo efficiency / 40)) to land in its
    role band: sidearm 8-14 | workhorse 12-18 | burst/specialist 18-26 |
    heavy/charge 24-32, with crediting notes (Railgun at full charge; Grenade on
    centre splash; Arc on the primary bolt; Incinerator as impact + one burn).
    It was blind to WHAT a weapon is good against — the reason every gun felt
    the same and the Chaingun (scored per bullet, not per three-round action)
    read as a mid-band workhorse. REPLACED by R-ROLE-1..5 above.
    WAIVER [WEAPON_POWER] Railgun (full charge) 45.0 vs heavy 24-32 — DELETED
    (AS8): the Railgun is governed by R-ROLE (the PLATED niche + R-ROLE-5).
    REFERENCE_AMMO_EFFICIENCY, the WEAPON_POWER_* bands and
    GameMath.weaponPowerScore are deleted with it.

R-ENEMY (RuleKind.ENEMY_THREAT_POINTS + ENEMY_HITS) — RE-BANDED by balance-overhaul order 1 (R8)
  Part 2 — THE R8 HIT BANDS (replace the golden-ratio bands): every non-boss
  archetype's depth-1 fight length lands in its role's targets, measured against
  the on-curve reference — the Assault Rifle, COMMON L1, at 3 tiles (15.2 per hit)
  — and the 205-eHP start player:
                 hits to kill   ordinary hits the player survives
    CHAFF          1-2            >= 10
    SOLDIER        3-4            7-9
    BRUISER        5-7            4-6
    MINI_ELITE     8-12           3-5
  (BalanceSchema.enemyHitResults / enemyHitsToKill / enemyHitsToDie). There are no
  exemptions any more: the chaff pack exemption and the mini-elite spike exemption
  of the golden ratio are gone — every role has a target.
  Part 1 — TP BANDS, RE-DERIVED from R8: each role's band is COMPUTED from the
  centre of its R8 box (centre eHP = mean hits-to-kill x 15.2; centre hit =
  205 / mean hits-to-die, an open-ended band using 1.5 x its floor; TP at melee
  positional, cadence 1) spread by LADDER_TP_BAND_LOW/HIGH_FACTOR (0.5 / 1.6) —
  wide enough for ranged/status positional (<= 1.55) and cadence-2 archetypes.
  WHY: the owner's "no more sponges": fights are short and hits land hard, and
  the TP currency stays priced against the same box the fight is.
  OVERRIDE RECORD: GOLDEN_RATIO_* bands and the hand-set ENEMY_TP_* bands (chaff
  16-34 | soldier 36-66 | bruiser 70-120 | mini-elite 160-310) -> the rules above.
  Every archetype's depth-1 HP/damage was rebased (BalanceConfig SECTION 2 note);
  damage sits at the LOW end of each band because the heal economy absorbs it.
  RE-STATED by balance-overhaul order 3 (CP2) — MATCHUPS. Two eHP readings now exist:
    NEUTRAL eHP (EnemyType.neutralEffectiveHitPoints) — the matchup-free survivability
      primitive. Part 2 (the R8 hit bands), R-LADDER and R-CARD-BREAKPOINT read it: the
      box describes the fight with an answer that is NOT resisted, and R-LADDER's
      reference stays the Assault Rifle vs a neutral target.
    PRICED eHP (EnemyType.effectiveHitPoints) — neutral eHP / referenceMultiplier, with
      referenceMultiplier = 1 + w x (MatchupTable.multiplier(BALLISTIC, trait) - 1) and
      w = BalanceConfig.MATCHUP_TP_REFERENCE_WEIGHT (GameMath.matchupReferenceMultiplier /
      traitAdjustedEnemyEffectiveHitPoints). Part 1 (the TP bands), XP and the encounter
      budget read it: an armoured archetype costs what it takes the reference
      generalist to kill, blended toward neutral because the on-curve player usually
      carries a second gun. Every archetype stays inside its role TP band for any
      w in [0, 0.83] (the Verdant Spiresower, PLATED, is the binding row).
      w SHIPS AT 0 — a DECISION (balance-overhaul order 3, CP7), so priced eHP ==
      neutral eHP. Re-fit with TACTICAL switching by matchup and the CP7 planned-heal
      re-fit: w = 0.25 -> S-SUPPLY 0.83, w = 0.5 -> 0.81, both over the 0.80 cap (w = 0
      -> 0.78). Pricing the rifle's armour penalty makes the planner trade armoured
      bodies for unresisted ones, which the sim's two-gun kit beats more easily. Revisit
      in the order-7 feel pass, with S-SUPPLY, once played kits carry more classes.
  OVERRIDE RECORD: "enemy eHP == raw HP / no mitigation" in TP pricing -> the priced
  eHP above; the R8 hit bands' eHP -> explicitly the NEUTRAL eHP (unchanged numbers).

R-HEAL (RuleKind.HEAL_PRICING) — RE-STATED by balance-overhaul order 1 (R10)
  Every heal/armour pickup restores a FRACTION of the max it refills, resolved at
  the moment of use (GameMath.fractionOfMaximum): 'H' medkit 0.45 max HP, '+' stim
  0.18, 'a' shard 0.15 max armour, 'A' vest 0.60. The rule bands that fraction:
    small pickups ('+', 'a'):  [0.10, 0.25] of max
    large pickups ('H', 'A'):  [0.40, 0.70] of max
  Survival turns bought on the model floor stay in the rule detail as information.
  WHY: a heal must keep its meaning at every depth while max HP grows with
  character level (R9) — a flat 90 HP was a full reset at level 1 and a sip at 20.
  OVERRIDE RECORD: flat MEDKIT_STIM_HEAL 32 / MEDKIT_FULL_HEAL 90 /
  ARMOUR_SHARD_VALUE 14 / ARMOUR_VEST_VALUE 62 and the survival-turns bands
  (small [2,6], large [8,16]) -> the fractions and fraction bands above.

R-TELEGRAPH (RuleKind.TELEGRAPH)
  Registered attack list: BalanceSchema.telegraphAttacks(). No UN-readable
  (readable=NONE) attack may exceed TELEGRAPH_MAX_UNTELEGRAPHED_HIT_FRACTION
  (25% of reference eHP ~= 51 dmg) in one hit. The 35% hard cap
  (BOSS_HARD_SINGLE_HIT_FRACTION) now applies to boss verbs via R-BOSS-VERB-CAP
  (order 6) — boss verbs are DERIVED per depth, not flat, so they are checked there
  (at their derived values) rather than in this flat, depth-scaled trash-mob list.
  WHY: a death must feel like "I made a mistake", never a dice roll. Readable
  kinds: TELE (wind-up), LANE (cardinal-line tell), FACE (positional counter).
  NOTE: any NEW attack path must be added to the registered list — the audit
  only checks attacks it knows about.
  OVERRIDE RECORD (balance-overhaul order 4, CP1): the "Shell Brute CHARGE" and
  "Plague Hulk blast" rows are REMOVED from the list — heavies are R-HEAVY's domain
  (below), sized as a fraction of on-curve max HP, and those rows read constants that
  no longer exist. Every other row and the 25% un-telegraphed cap are unchanged.

  Registered data: enemy/HeavyAttack (CHARGE, LANCE, AREA_STRIKE, SELF_DESTRUCT) — the
  HEAVY flag is per-constant data (damageFraction, minimumCommitTurns, displayName);
  EnemyType.heavyWindUp() and SpecialAbility.heavyAttack() say which archetype / verb
  resolves which heavy. BalanceSchema.heavyResults(), every HeavyAttack x depth 1..25:
    (a) DAMAGE   heavyDamageAtDepth(fraction, expectedPlayerAtDepth(d).maxHealth,
                 HEAVY_DAMAGE_SCALE) / on-curve max HP in [HEAVY_DAMAGE_FRACTION_MIN 0.40,
                 HEAVY_DAMAGE_FRACTION_MAX 0.60]. Defaults: CHARGE/LANCE 0.50, AREA_STRIKE
                 0.45, SELF_DESTRUCT 0.55.
    (b) COMMIT   minimumCommitTurns() >= 1 (what the code guarantees: 1 for charge/lance/
                 slam, the brace countdown for the self-destruct).
    (c) GUARD    fraction x GUARD_FRONT_HEAVY (0.20) <= HEAVY_GUARDED_MAX_FRACTION (0.12).
                 (Wired by CP3: Player.applyDirectionalDamage(.., heavy) applies GUARD_FRONT_HEAVY.)
  GUARD + ARMOUR (CP3 — OVERRIDE RECORD): GUARD_FRONT_MULTIPLIER 0.35 is DELETED (BalanceConfig +
  GameBalance shim) -> GUARD_FRONT_ORDINARY 0.50 (ordinary front-arc hits) / GUARD_FRONT_HEAVY 0.20
  (heavy). A heavy front-guarded hit RIPOSTES: attacker stunned next turn + VULNERABLE
  VULNERABLE_DURATION turns (none vs bosses / the dying self-destruct). ARMOUR_ABSORB_FRACTION 0.50 ->
  0.67; a heavy costs armour absorbed x ARMOUR_HEAVY_SHRED_MULTIPLIER 1.5 (GameMath.armorShredCost);
  STATUS SHIELD: armour > 0 blocks enemy WEAK/SLOWED/BLINDED/POISONED at ARMOUR_STATUS_COST_FRACTION
  0.10 x max armour (GameMath.armorStatusShieldCost); hazard tiles unblocked.

  the ordinary order-7 feel knob. TP pricing: GameMath.heavyExpectedDamageForPricing(

  WHY: nothing in combat was big enough to demand a response; a heavy must be avoided,

  Hazards stay meaningful at every depth because their damage is a FRACTION, and barrels sit where the
  groups are so the player reads the room before charging in.
  Numbers (BalanceConfig SECTION 23 unless noted):
    HAZARD_BARREL_CENTRE_FRACTION 1.2 / HAZARD_BARREL_RING_FRACTION 0.6 — of the floor's REFERENCE SOLDIER
      max HP at that depth: GameMath.enemyHealthAtDepth(HAZARD_BARREL_REFERENCE_SOLDIER_BASE_HEALTH, depth),
      base = VOID_SHROUD_MAX_HEALTH 50 (the R-LADDER SOLDIER archetype; a rule line asserts they agree).
      The float HP is NOT rounded before the fraction, so the ring lands exactly on a Ghoul's own HP.
    HAZARD_BARREL_PLAYER_CENTRE_FRACTION 0.30 / HAZARD_BARREL_PLAYER_RING_FRACTION 0.15 — of the PLAYER's
      max HP (the existing barrel -> player path, only the number changed).
    GameMath.barrelBlastDamage(fraction, referenceMaxHealth) = max(1, round(fraction x reference)).
    HAZARD_FIRE_ENEMY_DAMAGE_MULTIPLIER (SECTION 12) 1.5 -> 2.5 (x FIRE matchup); HAZARD_TOXIC_ENEMY_STACKS_PER_TURN 2
      — toxic tiles AND the Plague Hulk cloud poison enemies at the enemy's own max HP.
    Placement: HAZARD_GROUP_ROOM_SHARE 0.40, HAZARD_GROUP_MIN_SIZE 3, HAZARD_GROUP_BARRELS_MIN 1 / _MAX 2,
      HAZARD_GROUP_BARREL_RADIUS_TILES 2 (see procedural-level-generation.txt).
  Rules asserted (BalanceSchema.hazardResults + hazardPlacementResults; BalanceAuditTest
  barrelsStayMeaningfulAtEveryDepthAndSitBesideGroups):
    - depths 1..25: a RING blast kills every CHAFF archetype (ring >= its scaled max HP) and never one-shots the
      reference soldier; the player's centre blast stays <= HEAVY_DAMAGE_FRACTION_MIN (0.40) of on-curve max HP;
    - the sweep: on every COMBAT / ELITE floor >= ceil(0.40 x hostable group rooms) hold barrels, and no other
      node type ever gets one.
  A6 ARITHMETIC (BalanceReport "BARREL BLAST", neutral matchup): at depth 10 the soldier has 161 HP, ring 97,
  centre 194. One ring hit leaves the soldier at 64 HP = 40%; two overlapping rings (two barrels) kill it
  (0%); every chaff dies to one ring (Ghoul 97 vs 97 is the tight one). The fractions are depth-flat, so the

  ring (it would need ~0.8) — reported to the owner, not retuned.

R-XP-PACE (RuleKind.XP_PACE) — XP pacing is a RULE, not a hope (order 4; horizon 1..25 since balance-overhaul order 1)
  RE-FIT (balance-overhaul order 1): horizon 1..RUN_FINAL_DEPTH (25), and the
  geometric XP growth follows the NEW threat compound: 1.118 -> 1.2495
  (= ENEMY_HEALTH_GROWTH 1.139 x ENEMY_DAMAGE_GROWTH 1.097), so the yield stays
  depth-stable at ~1.11. For every depth: floorRosterXp(d) / xpRequired(expectedLevel(d)) in
  [XP_FLOOR_YIELD_MIN, MAX] = [1.0, 1.3] level-ups per floor. Per-enemy XP is
  DERIVED — xpReward = XP_PER_THREAT_POINT * enemyThreatAtDepth (one knob replaces
  13 hand-set constants) — and the XP curve is GEOMETRIC (base * growth^(level-1),
  growth 1.118 tied to the enemy threat compound), so roster XP and the level
  requirement grow at the SAME rate and the yield is depth-STABLE (~1.11). CATCH-UP
  (GameMath.catchUpScaledXp): a player > 1 level below expected gets XP * 1.5,
  forward-only. WHY: leveling must be FELT and PACED — a floor reliably buys ~1
  level at every depth, and a fallen-behind run can recover.

R-CARD-BREAKPOINT (RuleKind.CARD_BREAKPOINT) — RETIRED by balance-overhaul order 5 (CP2)
  OVERRIDE RECORD: folded into R-PERK PK1 (every perk's max rank crosses >= 1 whole
  TTK / TTD step on its niche, or its D4 resource step). RuleKind.CARD_BREAKPOINT and
  the card breakpoint helpers are deleted; BalanceAuditTest's card-breakpoint test
  asserts BalanceSchema.perkBreakpointResults(). The retired rule, for the record:
  Every level-up card must cross >= 1 INTEGER combat breakpoint vs the region
  soldier in some region: an OFFENCE card shaves a whole turn off the kill
  (GameMath.turnsToKillBreakpointGain), a DEFENCE card survives a whole extra hit
  (turnsToDie gain). Cards keep their equal PP budget (R-CARD); this rule proves
  the budget is spent where it FEELS different next fight, not just on the sheet.

      threatCost    = regionScaledFloorBudget(depth) * budgetScale * affixMultiplier   (GameMath.nodeThreatCost)

R-SINGLE-DIFFICULTY (RuleKind.SINGLE_DIFFICULTY) — ONE difficulty, locked (order 8)
  DESIGN INVARIANT (owner decision, final): the game has EXACTLY ONE difficulty. There are no
  easy/normal/hard modes and there must never be. Every run starts from the one canonical
  attribute block — BalanceConfig SECTION 7: PLAYER_START_STRENGTH / _AGILITY / _TOUGHNESS /
  _MARKSMANSHIP = 2/2/2/2, which with PLAYER_MAX_HEALTH 130 + PLAYER_MAX_ARMOR 75 IS the
  REFERENCE_PLAYER_EHP = 205 anchor every band in orders 1-7 was derived against.
  Two structural checks (reflection, no gameplay values):
    1. BalanceConfig declares exactly ONE starting block — one PLAYER_START_<ATTRIBUTE>
       constant per Attribute. A second block is how a second mode starts.
    2. No constant, nested type or enum constant in any scanned class carries mode-family
       naming (RECRUIT / NIGHTMARE / ULTRA / DIFFICULTY / STAT_BASE_ / EASY_MODE / HARD_MODE) —
       the same tripwire R-FLAGS uses for live test flags. BalanceAuditTest adds the
       source-level half: it walks every file under core/src/main/java and fails on the mode
       names themselves, so a mode cannot return through a file the reflection sweep does not
       scan (a new Screen, a menu, a save field). BalanceSchema.java is the one excluded file:
       it DEFINES the banned tokens, and its own members are covered by check 2 itself.
  WHAT WAS REMOVED: four modes (the old RECRUIT/normal/NIGHTMARE/ULTRA tables in GameBalance),
  the Difficulty enum on PlayerStats, and the mode argument at run creation. StatsStore drops
  any legacy mode key on load (best-effort; a legacy record has always loaded fine because
  load() asks only for the keys it knows). There was no difficulty-selection screen to remove —
  World hard-coded the normal tier — so the mobile touch flow into a run is unchanged.
  WHY: the modes were wrong twice. They contradict the design (in this roguelike, difficulty is
  chosen INSIDE the run — route choice and the priced map, region danger, depth via the coupling
  curve, scarcity swings and loot luck — never from a menu), and even as implemented they were
  fake: modes changed ONLY starting stats while every enemy number, scarcity target and telegraph
  cap stayed anchored to the normal tier's 205 eHP, so three of the four were never actually
  balanced. Deleting three makes the contract EXACT for the one real game instead of exact for
  one mode out of four, and the telegraph fairness caps (25% un-telegraphed, 35% boss single hit)
  now provably protect the actual player pool in every run. No value was re-derived by this
  order — it removes an assumption, not numbers.
  TUNING: difficulty moves by moving THE dials — the scarcity band, the heal-drain band, the
  boss survival ratios, the region danger multipliers. One set, one game. If accessibility
  options are ever wanted they must be framed as exactly that (e.g. animation speed) and never
  as balance-touching modes; this rule is the tripwire.

R-LADDER (RuleKind.LADDER) — THE POWER LADDER (balance-overhaul order 1)
  Every floor has a THREAT LEVEL equal to its depth. Weapon damage climbs a compound ladder
  (base * LADDER_GROWTH^(L-1) * rarity * levelGapMultiplier(L - d)); enemy HP and damage climb
  FITTED compound curves (ENEMY_HEALTH_GROWTH / ENEMY_DAMAGE_GROWTH); max HP/armour climb
  PLAYER_VITALITY_GROWTH per character level. A weapon BELOW the floor's level takes
  LEVEL_GAP_PENALTY_BASE^levels (floor LEVEL_GAP_FLOOR, scaled by LEVEL_GAP_STEEPNESS); one
  ABOVE gains LEVEL_GAP_BONUS_PER_LEVEL (capped). All values: BalanceConfig SECTION 20.
  THE ONE EXPECTED PLAYER: GameMath.expectedPlayerAtDepth(d) -> util/ExpectedPlayer — weapon
  level d, the region's expected rarity (mean of the WEAPON_DROP_TIER band ends), character
  level 1 + EXPECTED_LEVELS_PER_DEPTH*(d-1), offence cards as a PP %-lift (50% of the level
  budget), defence cards as flat eHP (50%), vitality-scaled max HP/armour. Its depth-1 DPT is
  REFERENCE_PLAYER_DPT and its depth-1 eHP REFERENCE_PLAYER_EHP (the anchors stay the depth-1
  anchors). The audit, the simulator and the boss derivation read this one model.
  Six sub-checks, for every depth 1..RUN_FINAL_DEPTH (25) and every non-boss role's reference
  archetype (CHAFF Gore Biter, SOLDIER Void Shroud, BRUISER Shell Brute, MINI_ELITE Iron
  Stalker). Turns are CONTINUOUS (eHP / per-hit damage) so one-hit rounding hides nothing:
    L1 ON-CURVE FLAT  on-curve TTK and TTD within +/-15% of their depth-1 values.
    L2 LAG PUNISHED   weapon level d-2 -> TTK >= 1.5x on-curve; d-4 -> >= 2.5x; the start
                      weapon (L1 COMMON) at d >= 5 -> >= 3.0x.
    L3 AHEAD BOUNDED  weapon level d+2 -> TTK >= 0.75x on-curve.
    L4 LEVEL FELT     on floor d, level d vs level d-1: DPT gain >= +25%.
    L5 RARITY FELT    each tier step >= +8% DPT; LEGENDARY >= +40% vs COMMON (equal level,
                      abilities excluded).
    L6 VITALITY FELT  character level d-3 -> TTD <= 0.80x on-curve.
  THE FIT: ENEMY_HEALTH_GROWTH 1.139 is the least-max-deviation compound rate over 1..25
  against the expected player's per-hit growth (ladder x rarity x offence lift); on-curve TTK
  wobbles within +/-13% (the residual is the per-region rarity step). ENEMY_DAMAGE_GROWTH
  1.103 is fitted the same way against vitality 1.09 + flat defence-card eHP (+/-14%).
  With the defaults L4 = 1.08/0.82 = 1.32, L2 = 1.73 at d-2 and 3.01 at d-4, L3 = 0.78,
  L6 = 0.79 at worst. Enemy HP at depth 25 is ~23x depth 1 (fraction-based health bars; AS10).
  WHY: a weapon level used to be +10% linear, enemy HP grew 4.2%/floor, rarity could not raise
  power and max HP never grew — so a lazy and a prepared player differed by a rounding error
  (the owner: "I can play with a level-1 weapon very confidently even on higher levels").
  REPLACES R-DEPTH and R-GEARGATE (override record: balance-overhaul order 1 OVERRIDE CLAUSE;
  retired when the ladder goes live in gameplay, CP2).

R-LADDER-AFFORD (RuleKind.LADDER_AFFORD) — the shop rung is always in reach (balance-overhaul order 1)
  At every depth 1..RUN_FINAL_DEPTH the Fabricator's LEVEL UP rung (priced through
  GameMath.shopPrice at LADDER_LEVEL_UP_POWER_POINTS = 1.5 PP) costs <= LADDER_AFFORD_FRACTION
  (0.5) of one COMBAT floor's modelled credit income (model-floor kill bounties scaled by
  CREDIT_DEPTH_SCALE + expected credit chips). Measured: 54 of 159 credits at depth 1 (0.34),
  184 of 389 at depth 25 (0.47). WHY: keeping a favourite gun on the ladder must be a real
  trade against supplies (about half a floor's credits), never out of reach.

NEVER-SOFTLOCK (GameMath.emergencySupplyTriggers, not a schema band — a floor guard)
  A player who wastes ammo must never die to an empty inventory screen. When total
  remaining potential damage (all reserves * per-shot damage + one melee swing) falls
  below remainingFloorDemand * EMERGENCY_SUPPLY_FRACTION (0.25), the next enemy drop
  is forced to be ammo for an equipped weapon, capped ONCE PER FLOOR (EnemyManager).
  0.25 sits far below the scarcity band, so a hoarder never trips it — it only turns
  "standing empty-handed" deaths into fighting-retreat deaths; melee (fist, no ammo)
  is the true backstop. Proven by a synthetic-inventory unit test (fires when starved,
  never when supplied, honours the once-per-floor cap). RunStats records ammo picked
  up, credits earned/spent, heals used and emergency triggers as order-9 telemetry.

S-LAG (RuleKind.SIM_LAG) + THE LADDER REPORT (balance-overhaul order 1)
  S-LAG: HOARDER-START-WEAPON's median death depth <= SIM_LAG_MAX_MEDIAN_DEPTH (6) — a weapon
  that never climbs the ladder ends the run early. Reported every balanceSim run; WAIVED under
  the navigation-limited waiver (SECTION 4), whose expiry it inherits.
  THE LADDER REPORT (sim/LadderReport, printed under the bands, OUTPUT not an assertion): the
  ordinary matrix stalls on the first floors, so the report plays one-floor PROBES started at
  every depth 1..25 (SimSettings.ladderProbe, SIM_LADDER_PROBE_SEEDS_PER_DEPTH seeds per kit):
  TACTICAL with the ON-CURVE kit (guns at the floor's level, the region's lowest drop tier) and
  HOARDER-START-WEAPON with the START kit (L1 COMMON), both on the on-curve character (vitality
  + the model's card lifts), so the ratio is the weapon ladder alone. Every hit dealt records
  enemy max HP / hit (EnemyManager.PlayerHitListener, sim-only); every attributed hit taken
  records full pool / hit. Per role and depth band it prints the median of each and lag/on.
  First read-out: played on-curve hits-to-kill stay flat 1..25 (SOLDIER 3.3 -> 3.4, CHAFF 1.9 ->
  2.1); the start kit's ratio climbs 1.7x (1-5) -> ~24x (21-25); A2's SOLDIER depths 3-5 read-

  HOARDER-START-WEAPON never does.

S-GATE / S-FAIR / S-SKILL / S-ROUTE / S-ECONOMY / S-SUPPLY / S-SWITCH / S-HEAVY / S-BUILD / S-SOFTLOCK (+ S-LAG above) (RuleKind.SIM_*, order 9)
  THE BEHAVIOURAL BANDS — the only rules in this document that are checked against PLAY
  rather than against arithmetic. Everything above proves the numbers are self-consistent;
  it cannot prove the game plays the way they claim (knowledge-doc problem 1: "verified by
  harness only — NEVER playtested"). Because the game is strictly turn-based, a whole run is
  SIMULABLE: sim/BalanceSimulator plays SIM_SEED_COUNT (200) runs per policy through the REAL
  systems — real LevelGenerator floors via the real route pipeline, real EncounterBudgetPlanner
  rosters, real EnemyManager turns, the real damage/drop/XP/economy path, and the real
  PlayerController action entry points — with a scripted PlayerPolicy instead of touch input.
  Values live in BalanceConfig SECTION 18; the bands are evaluated in sim/BehavioralBands and
  gated by `./gradlew balanceSim` (BalanceSimTest), NOT by the fast `./gradlew test`.

  THE POLICIES (deliberately simple heuristics, not AI — the gap between them IS the game's
  difficulty range, since the game ships exactly one difficulty):
    NAIVE                 attacks the nearest enemy, never guards, ignores hazards and cardinal
                          lines, heals at <30% vitality, never switches weapons, walks the
                          shortest route, picks route nodes at random.
    TACTICAL              keeps range, breaks the cardinal line vs ranged, READS THE RED FLOOR (a heavy
                          committed at it: stagger it with a close spread blast, else GUARD it when
                          faced, else step off the marked tiles, else guard — balance-overhaul order 4
                          CP7b, see S-HEAVY), manages ammo across weapons, heals early,
                          buys the shop backstop, takes upgrades, routes by the order-7 node EV.
                          Balance-overhaul order 3 (CP7): takes the C4 SWITCH hint whenever it is up
                          (SimWorld computes it exactly as World.updateMatchupHint does — the real
                          MatchupAdvisor + PlayerController jump), and keeps its kit DIVERSE: a found
                          gun of a DamageClass the loadout lacks replaces the redundant / emptiest
                          slot (never the last gun with ammo; PlayerPolicy.slotToReplaceForGroundWeapon).
    HOARDER-START-WEAPON  TACTICAL (it delegates chooseAction, so it INHERITS the heavy answer), but NEVER equips a weapon it finds or buys — the user's
                          boss-cheese reproduction, kept as a permanent regression case.
    TACTICAL-CLOSE / -MARKSMAN / -PYRO-DEMO / -BULWARK  (balance-overhaul order 5, S-BUILD) TACTICAL with a
                          BUILD BIAS (sim/BuildBias): perk picks prefer the bias tags, then synergy, then the
                          most-ranked tag; keystone picks take the bias tag's keystone when offered. The bias

--------------------------------------------------------------------------------
SECTION 7 — THE CHANGE PROTOCOL (new-game-balancr order 9) — MANDATORY
--------------------------------------------------------------------------------
This section SUPERSEDES the workflow in docs/game-balance-knowledge.txt SECTION 21
(that section now points here). It is the whole series' closing move: values in one
place, rules enforced, and PROOF that the game plays the way the math says.

EVERY change to util/BalanceConfig.java ships with all four of these:

  1. GREEN AUDIT      `./gradlew test`
     Fast (seconds), runs on every commit. BalanceAuditTest evaluates every rule in
     BalanceSchema and fails the build on any unwaived violation. This is the
     gatekeeper for the NUMBERS.

  2. GREEN SIM        `./gradlew balanceSim`
     Slow (whole simulated runs), run on balance changes and nightly in CI.
     BalanceSimTest plays SIM_SEED_COUNT runs per policy through the real systems and
     checks the behavioural bands (S-GATE ... S-BUILD). This is the gatekeeper for the BEHAVIOUR.
     Its plain-text summary lands in core/build/reports/balance-sim/summary.txt —
     read it even when it is green: "median death depth moved 9 -> 6" is a sentence
     you can act on long before a band breaks.

  3. UPDATED LIVING TABLES
     Re-run BalanceReport and paste its output over SECTION 6. The tables are a VIEW
     of the schema; a stale view is worse than none, because it reads as current.

  4. ONE CHANGELOG LINE (below)
     Which dial moved, and WHY. One sentence. The reason is the part that cannot be
     recovered from the diff six months later.

WHEN THE SIM AND THE MODEL DISAGREE, the sim wins — but only after you check WHICH
is wrong. A band can fail because the game got worse, or because the harness got
better (a policy that now finishes floors it used to stall on will move every depth
statistic). The report's per-policy columns (median depth, stalled, readable,
bossClear, softlock, level gap) are there to tell those two apart.

THE TUNING LOOP the whole series was built to enable:
     telemetry says it FEELS wrong (the RUN AUTOPSY on the death screen, and the
     same block logged at run end)
  -> adjust the BAND or the TARGET in BalanceConfig, never the call site
  -> the derived dials re-derive themselves
  -> `./gradlew test` confirms the model is still self-consistent
  -> `./gradlew balanceSim` confirms it still PLAYS that way
  -> humans confirm the feel.
  Numbers chase feel; the schema keeps them honest.
