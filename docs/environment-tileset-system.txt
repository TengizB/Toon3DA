ENVIRONMENT TILESET SYSTEM — Symbol/Sprite Reuse
================================================
STATUS: MIGRATION IN PROGRESS

Single source of truth for the symbol/sprite decoupling refactor. This doc is FORWARD-LOOKING:
it describes the TARGET model the migration is building toward. It was created in order-0 (before
any code changed) and is filled section-by-section, in-commit, by each subsequent order. The ORDER
STATUS TABLE below is the honest record of which parts are actually built yet.

Series design docs: .claude/agents/ideas/symbol-sprite-reuse-system.txt (master index) and
.claude/agents/ideas/symbol-sprite-reuse-system-order-0.txt .. order-9.txt.


TARGET MODEL (one paragraph)
============================
A level-file SYMBOL is not a fixed piece of art — it is a SLOT in a fixed CATEGORY (WALL, COLUMN,
SOLID_PROP, FLOOR_DECAL, ...). A symbol's category/gameplay meaning never changes, but WHICH sprite
fills that slot is chosen PER LEVEL from a large registered POOL. Symbols come in two tiers: FIXED
symbols (player start 'p', exit '>', doors, keycards, pickups, ammo, enemy spawns, hazards) keep a
permanent meaning AND sprite and are never reassigned; FLEXIBLE symbols (the wall/decor visual
symbols) keep a fixed category but get their sprite assigned per level by a deterministic,
rule-governed allocator. No level loads the whole art library: each level draws a small palette
(as many distinct sprites as it has free symbols) from the pool, so per level the palette is small
but across all levels the variety is huge. Adding a new wall/prop/column sprite — or a whole new
room — is ONE registration line, never an edit to the generator, the renderers, or Level (the same
"never a switch statement" discipline as route/RouteRegistries.bootstrap()).


LEGACY vs TARGET — WHICH IS LIVE
================================
Until this migration completes, the LEGACY 1:1 symbol->sprite mapping is what actually RENDERS
(via the legacy LevelPalette default, order-3). Where THIS doc and an older doc or class comment
disagree, THIS doc describes the TARGET; the transition banner stamped on the older doc/comment
(">>> TILESET MIGRATION IN PROGRESS <<<") tells the reader to consult the ORDER STATUS TABLE below
for which parts are actually live. Do not treat "one symbol = one fixed sprite" as permanent truth
while that banner is present anywhere in the tree.

1. ART CATALOG & REGISTRIES  [DONE — order-1]
   The `…toon3d.tileset` package (headless, no LibGDX imports) is the data-driven ART CATALOG: the
   fixed set of tile CATEGORIES and a registry of every environment SPRITE the game can draw. order-1
   is pure data + registration — NO per-level binding, NO allocator, NO renderer change. The legacy
   WallRenderer texture table and PropRenderer switch stay the runtime authority; the registry exists
   in parallel so later orders can enumerate the inventory instead of hardcoding a sprite list.

   CLASSES (all in …toon3d.tileset):
     * TileCategory (enum) — the FIXED semantic class a symbol MEANS; never varies per level. Four
       FLEXIBLE-eligible visual members, one per existing Level predicate group:
         WALL       (Level.isWall)      rendersAsStripe=true,  blocksMovement=true
         COLUMN     (Level.isColumn)    rendersAsStripe=true,  blocksMovement=true
         SOLID_PROP (Level.isPropSolid) rendersAsStripe=false, blocksMovement=true
         FLOOR_DECAL(Level.isPropDecal, non-pickup) rendersAsStripe=false, blocksMovement=false
       Metadata only (id, rendersAsStripe, blocksMovement) — consumers route a sprite to the wall vs
       billboard pipeline by reading rendersAsStripe(), never a hardcoded char check. Doors, pickups,
       keycards, ammo, hazards, enemy spawns, player-start, and exit are FIXED symbols and are NOT in
       this enum or the sprite registry (order-2 formalises the FIXED/FLEXIBLE split).
     * EnvironmentSpriteDefinition (immutable value; Builder) — one concrete piece of art. Fields:
       id (STABLE string), category, displayName (tooling/logging only), heightMultiplier
       (billboard height fraction; 1.0 for WALL/COLUMN), occluder (writes z-buffer; mirrors
       Level.isPropOccluder), textureGeneratorId (= id for v1; kept separate so sprites can share a
       generator later), themeTags (Set<String> coherence hints; empty allowed). No LibGDX types; no
       colours (those live in the texture generators, order-6). Builder defaults: heightMultiplier 1.0,
       occluder true, textureGeneratorId = id.
     * EnvironmentSpriteRegistry — register(def) / get(id) (never null for a registered id) /
       allInCategory(category) (the allocator's variety pool, unmodifiable) / contains(id) / size().
       Duplicate id throws IllegalStateException (route-registry discipline); get(unknown) throws
       IllegalArgumentException. Insertion-ordered so counts/order are reproducible.
     * TilesetRegistries — bootstrap hub, the twin of route/RouteRegistries. sprites() returns the
       shared singleton; bootstrap() is idempotent and registers ALL v1 sprites via private
       registerWalls()/registerColumns()/registerSolidProps()/registerDecals() helpers. Called once
       from World.create() next to RouteRegistries.bootstrap().

   v1 INVENTORY (exactly today's art — no additions): 21 walls (x c v t w h j G k N Q S M Z U X D F
   + observatory " ' `), 1 column (P → "column_round"), 17 solid props (g E T L C # % & = @ I J W +
   observatory ; \ | <), 8 floor decals (m s . O e + observatory ? ] -). STELLAR_OBSERVATORY art is
   tagged themeTag "observatory" (TilesetRegistries.THEME_TAG_OBSERVATORY) so the catalog is complete
   yet a later allocator only pulls it for that room, preserving today's containment rule. Heights are
   copied from the SAME RenderConstants the renderer reads (inline PropRenderer literals for g/E/T/L/C/
   m/s/./O were first hoisted into RenderConstants.PROP_HEIGHT_* and referenced from both places — no
   re-hardcoded values, no behaviour change).

   STABLE SPRITE-ID SCHEME: category prefix + descriptor, e.g. "wall_plain", "wall_cryo",
   "column_round", "prop_locker", "decal_blood". Ids are the key palettes/seeds use to stay
   reproducible across code changes and MUST NOT be renamed once shipped.

   RECIPE (add a wall/prop/column/decal sprite): build one EnvironmentSpriteDefinition + one
   register() line in the matching TilesetRegistries helper. Nothing else in this order references a
   specific char; nothing downstream switches on a hardcoded sprite/category list — it asks a registry.

   TESTS (headless, core/src/test/.../tileset/TilesetRegistriesTest): get() never null for a
   registered id; per-category counts equal the count of chars Level's predicates accept today (guards
   the inventory is complete and nothing was dropped); duplicate-id throws; bootstrap() idempotent;
   height/occluder metadata matches legacy values; observatory art carries the containment tag.

2. SYMBOL BUDGET (FIXED vs FLEXIBLE)  [DONE — order-2]
   The SAFETY BOUNDARY of the whole series: the authoritative declaration of which level-file symbols
   the per-level allocator (order-4) MAY reassign a sprite to (FLEXIBLE) and which it must NEVER touch
   (FIXED). Isolated as one small, heavily-tested config so the allocator can trust it and a reviewer
   can see, in one place, exactly what is safe to vary. Pure config + a small value object — NO
   allocation logic (order-4), NO per-level binding (order-3). Headless, no LibGDX.

   WHY THE SPLIT EXISTS: get it wrong and a level could repaint the exit '>' or a keycard 'r' as a
   wall, breaking gameplay. The dangerous direction is OVER-declaring flexibility (marking a gameplay
   symbol reassignable); UNDER-declaring is merely less variety. So flexibility is declared EXPLICITLY
   and everything else is FIXED by default (fail-safe): any char not listed as flexible — including
   unknown chars — resolves to FIXED without being enumerated.

   SymbolClass (enum, …toon3d.tileset): FIXED (permanent meaning AND sprite) / FLEXIBLE (fixed
   category/meaning, sprite chosen per level from the category pool).

   AUTHORITATIVE FIXED / FLEXIBLE PARTITION (v1):
     FIXED — permanent meaning AND sprite; NEVER reassigned. These keep exactly their current handling
       and (except the two sprite-bound exceptions below) are NOT in the sprite registry:
         * Special: player start 'p', exit '>'.
         * Doors: d R Y B.  Floor lighting: (space) l u f  (brightness multipliers, not sprites).
         * Pickups: r y b + H a A  and ammo 6 7 8 9 0.  Hazards: i (fire) q (toxic).
         * Enemy spawns: 1 2 3 4 5 ! $ ^ ~ z K V * n.
       FIXED symbols that DO map to a sprite (the only entries in fixedAssignments):
         * 'x' plain wall -> "wall_plain" (see PLAIN-WALL RULE below).
         * shop '@' -> "prop_vendor" (World.placeMachine stamps it solid; it must always render as the
           vendor machine, so although '@' sits in the SOLID_PROP category it stays FIXED).
     FLEXIBLE — category fixed, sprite assigned per level:
         * WALL:       c v t w h j G k N Q S M Z U X D F " ' `  (every isWall char except 'x').
         * COLUMN:     P  (meaning "column" is permanent; the filling sprite is flexible — round today,
                          square after order-9).
         * SOLID_PROP: g E T L C # % & = I J W ; \ | <  (every isPropSolid char except the shop '@').
         * FLOOR_DECAL: m s . O e ? ] -  (the "pure" decals; pickup/hazard/stairs decals are FIXED).
       The STELLAR_OBSERVATORY room art (" ' ` ; \ | < ? ] -) is FLEXIBLE by category; its room
       containment is preserved by the allocator via the order-1 "observatory" sprite theme tag, NOT by
       the budget.

   PLAIN-WALL RULE: 'x' is the 80-90% default wall and hand-crafted levels lean on it heavily, so it
   stays a FIXED WALL slot permanently bound to "wall_plain". Flexibility applies to the ACCENT walls,
   where variety actually reads; this keeps generic corridors legible and every existing hand level's
   bulk walls unchanged.

   SymbolBudget (immutable value object, …toon3d.tileset):
     * fixedAssignments(): Map<Character,String> — char -> permanently-bound sprite id (only the
       sprite-bound FIXED symbols: 'x'->"wall_plain", '@'->"prop_vendor"). Non-sprite FIXED symbols are
       simply absent.
     * flexibleSlots(): Map<TileCategory,List<Character>> — the reassignable symbols per category.
     * symbolClassOf(char) -> SymbolClass (fast lookup; FIXED for anything not declared flexible).
     * categoryOfFlexibleSymbol(char) -> TileCategory (null if the char is not flexible).
     * fixedSpriteId(char) / isFixed(char) / isFlexible(char) — convenience readers.
     * static SymbolBudget.standard() — builds the canonical v1 partition above from TilesetConstants;
       the single source the allocator consumes. Stores STRUCTURE only (which char is which
       class/category) — it does NOT choose which sprite fills a flexible slot (order-4's job).
   Both returned maps and their lists are unmodifiable.

   TilesetConstants.java (…toon3d.util, a NEW split-constants file): holds the partition as named string
   tables so changing it is a one-constant edit, never a code change:
     FIXED_WALL_SYMBOL="x", FIXED_WALL_SPRITE_ID="wall_plain",
     FLEXIBLE_WALL_SYMBOLS, FLEXIBLE_COLUMN_SYMBOLS, FLEXIBLE_SOLIDPROP_SYMBOLS, FLEXIBLE_DECAL_SYMBOLS,
     FIXED_SPRITE_SYMBOLS / FIXED_SPRITE_IDS (index-aligned; the shop '@'->"prop_vendor" exception),
     PALETTE_SEED_SALT (long; reserved here for order-4's palette-seed derivation, unused until then).

   REVISED tile-symbols.txt RULE (transitional; order-9 does the full STRICT-RULE rewrite): a FIXED
   symbol is permanent (meaning AND sprite); a FLEXIBLE symbol now carries a CATEGORY, not a fixed
   sprite — its art is assigned per level within that category. Adding environment art becomes
   "register a new SPRITE in the category pool" (order-1 RECIPE), not "consume a scarce symbol"; new
   symbols become rare. The tile-symbols.txt banner is tightened this commit to say flexible symbols
   carry a category, not a fixed sprite.

   TESTS (core/src/test/.../tileset/SymbolBudgetTest): fixed and flexible sets disjoint; no char in two
   flexible categories; every gameplay symbol (doors, pickups, ammo, hazards, enemy spawns, start, exit,
   shop) resolves to FIXED via the fail-safe default; 'x' FIXED and bound to "wall_plain"; '@' FIXED and
   bound to "prop_vendor"; every flexible symbol maps to a real order-1 category with a non-empty pool;
   unknown char defaults to FIXED; returned maps/lists unmodifiable.

3. PER-LEVEL BINDING (LevelPalette)  [DONE — order-3]
   The PER-LEVEL BINDING object: for ONE level, which sprite each environment symbol renders and which
   category each symbol belongs to. order-3 builds this data structure and threads it onto Level with a
   LEGACY default; it does NOT generate palettes from a seed (order-4) and changes NO renderer (order-7).
   Because Level defaults to the legacy palette, order-3 attaches a palette to every level with zero
   visible change — the "ship the identity transform first, then vary it" discipline the route series used.

   CLASSES (all in …toon3d.tileset, headless — strings/enums only, no LibGDX, no textures):
     * LevelPalette (immutable value object) — the binding for one level. Resolution methods:
         - categoryOf(char) -> TileCategory, or null if the symbol is not an environment symbol
           (doors/pickups/ammo/hazards/enemy-spawns/start/exit return null — the existing fixed paths
           handle them, not the palette).
         - spriteIdOf(char) -> String (the stable EnvironmentSpriteDefinition id this level renders for
           the symbol); null for non-environment symbols. FIXED symbols return their permanent binding
           ('x' -> "wall_plain", '@' -> "prop_vendor"); FLEXIBLE symbols return whatever was assigned (the
           legacy palette returns today's fixed art).
         - hasBinding(char) -> boolean.
       Built via a package-private Builder (the only builders are LevelPalettes and the order-4
       allocator). bind() validates category+spriteId non-null BEFORE mutating either map, keeping the
       invariant "a symbol is in both the category and sprite maps, or neither." IMMUTABLE once built, so
       it is safe to read from WallRenderer's worker threads (order-7) via happens-before from level
       construction. ID-ONLY: it holds no textures — the render layer turns ids into textures in order-6.
     * LevelPalettes (static factory) — LevelPalettes.legacy() builds the palette reproducing today's
       exact global mapping. It is the ONLY place that still encodes the historic 1:1 symbol->sprite
       table, and it does so MECHANICALLY: for each category it zips a registration-ordered symbol string
       against that category's EnvironmentSpriteRegistry pool (allInCategory), so char[i] renders pool[i].
       A length mismatch throws loudly, so registry drift cannot silently corrupt the mapping. The result
       is memoised as one shared immutable singleton (hand levels pay no per-level cost) via
       double-checked locking. legacy() calls TilesetRegistries.bootstrap() first so the shared registry
       is populated before it is read.

   WHY A LEGACY DEFAULT (the migration lever): the renderers and Level predicates stay the runtime
   authority until order-7. To switch them safely we need a palette that yields EXACTLY today's mapping
   ('Z' -> wall_cryo, 'M' -> wall_medical, 'P' -> column_round, ...). That is the legacy palette. With it
   as Level's default: order-3 attaches a palette everywhere with zero visible change; hand-crafted
   assets/levels/*.txt keep legacy forever (fixed symbols, never change appearance); order-7 can flip
   renderers to "read the palette" and nothing changes until order-4/8 produce varied palettes for
   generated levels.

   LEVEL WIRING (the only change outside the tileset package this order):
     * Level gains an immutable `LevelPalette palette` field. A NEW package-private constructor takes an
       explicit palette; the EXISTING 3-arg constructor delegates to it with LevelPalettes.legacy(), so
       every LevelLoader / LevelGenerator / *Generator call site compiles unchanged and renders identically.
     * public LevelPalette getPalette() — never null; the getter order-7's renderers will call.
     * Level's static category predicates (isWall/isColumn/isPropSolid/...) are UNCHANGED and remain the
       category authority until order-7; order-3 only ADDS the palette, it routes no read through it.

   TESTS (headless): LevelPaletteTest (tileset pkg) — legacy().spriteIdOf across every category
   ('Z'->wall_cryo, 'x'->wall_plain, 'P'->column_round, '@'->prop_vendor, '.'->decal_blood, ...); each
   symbol maps to its correct TileCategory; the legacy palette covers the whole registry 1:1 (every
   registered sprite id is some symbol's binding, and every bound id is registered); non-environment
   symbols (doors/pickups/ammo/hazards/enemy-spawns/start/exit) resolve to null; legacy() is a memoised
   singleton. LevelPaletteWiringTest (level pkg, for the package-private constructor) — a Level built with
   no palette defaults to legacy; an explicit palette is carried through unchanged.

4. ALLOCATION (SymbolAllocator)  [DONE — order-4]
   THE HEART of the series: the deterministic, headless engine (`…toon3d.tileset`, no LibGDX) that turns
   a floor's seed + the rooms actually placed into a concrete LevelPalette. This is where symbol reuse,
   freed-symbol reclamation, and rule-governed (never random) variety happen. SymbolAllocator.allocate()
   is a PURE FUNCTION of its request — no static mutable state, no clock, no iteration-order dependence —
   so the same request always yields a byte-identical palette. It does NOT run the generator (order-8
   calls it); order-4 only produces the palette.

   THE INPUT — SymbolAllocationRequest (immutable; builder):
     * long levelSeed   — the floor's master seed (same source World.floorSeed feeds LevelGenerator);
                          every per-symbol roll derives from it.
     * int  depth       — dungeon depth, used only for the mild depth-influence rule (R5). Optional
                          flavour, defaults to 0.
     * SymbolBudget budget            — the FIXED/FLEXIBLE partition (order-2); the allocator binds FIXED
                          symbols verbatim and only assigns sprites to FLEXIBLE ones.
     * List<RoomSymbolDemand> placedRoomDemands — ONE demand PER SIGNATURE ROOM ACTUALLY PLACED. Rooms
                          NOT placed contribute NO demand, so their symbols are never reserved and fall
                          through to the free variety pool. THAT is the "freed symbols" mechanic — it is
                          emergent from the request shape, not a special case.
     * EnvironmentSpriteRegistry registry — the art pool (order-1) variety is drawn from.
   RoomSymbolDemand (immutable; defined in `tileset` so the pure allocator has no level/render dependency;
   order-5's RoomBlueprint produces it): requiredSprites Map<Character,String> (symbol -> the sprite id
   the room MUST render, e.g. a CRYO room reserves 'Z' -> "wall_cryo") + optional categoryCounts
   Map<TileCategory,Integer> (how many GENERIC slots per category the room also wants — carried for
   order-8; order-4's reservation keys only off requiredSprites).

   THE OUTPUT: a LevelPalette (order-3), built via its package-private Builder, fully bound for every
   symbol this level uses.

   THE ALGORITHM (deterministic; step by step):
     Step 0 — SEED: each FLEXIBLE symbol's variety roll comes from a per-symbol RNG stream seeded by
              GameMath.paletteSymbolSeed(levelSeed, symbol) (see MATH). Keying by the SYMBOL (not by loop
              position) makes the assignment independent of iteration order and reproducible.
     Step 1 — FIXED bindings: every entry in budget.fixedAssignments ('x' -> "wall_plain",
              '@' -> "prop_vendor") is bound verbatim (category read from the sprite). Never rolled.
     Step 2 — RESERVE for placed rooms: for each placed RoomSymbolDemand, each required symbol is bound to
              its required sprite and marked consumed so variety can never overwrite it. CLASH RESOLUTION:
              if two placed rooms demand the SAME symbol for DIFFERENT sprites, the first keeps the symbol
              and the second's sprite is rehomed onto the first UNBOUND flexible symbol of the same
              category (declaration order) — capacity exists because absent rooms freed symbols. If a
              category's flexible symbols are ALL bound (capacity exhausted), the deterministic fallback
              is to drop the duplicate reservation; with current room caps this is unreachable and the
              test suite asserts it never triggers.
     Step 3 — VARIETY fill: for every still-unbound FLEXIBLE symbol (iterated in TileCategory enum order,
              then budget declaration order — a fixed, reproducible order), pick a sprite from
              registry.allInCategory(category) with the seeded RNG under the RULES below. This is where
              generic rooms/halls get their per-level look and where freed room symbols become
              new-generated-room art (order-8 decides which freed symbols a new room uses).
     Step 4 — return the immutable LevelPalette.

   THE RULES (variety is SEEDED and CONSTRAINED, never a raw random grab):
     R1 COHERENCE — a per-level THEME (ONE tag) is chosen deterministically from the tags the catalog
        actually carries across the flexible categories (containment tags excluded), via a PaletteRng
        seeded by paletteSymbolSeed(levelSeed, NUL) (the reserved NUL key — not a real level char, so
        its stream never collides with a symbol's roll). A candidate sprite whose theme tags overlap the
        level theme is weighted up by GameBalance.PALETTE_COHERENCE_WEIGHT_MULTIPLIER, so a level reads as
        one place. When the catalog carries no coherence tags the theme set is empty and coherence is a
        no-op (a plain seeded pick).
     R2 CONTAINMENT — room-contained sprites (the order-1 "observatory" tag,
        TilesetRegistries.THEME_TAG_OBSERVATORY) are EXCLUDED from the generic variety pool; they are only
        ever bound when their owning room reserves them in Step 2. So a freed observatory SYMBOL gets
        generic art, while observatory SPRITES stay in-room — preserving today's containment rule.
     R3 ANTI-REPETITION — within one category on one level, two symbols avoid the same sprite id: variety
        prefers sprites not yet spent in that category (fixed + reserved + earlier variety all count).
        Only when the eligible pool is smaller than the slot count (all already used) are repeats allowed,
        deterministically.
     R4 PLAIN-WALL FLOOR — 'x' is FIXED to "wall_plain" in Step 1, so variety only ever decorates accent
        walls and corridors stay legible (order-2 PLAIN-WALL RULE).
     R5 DEPTH INFLUENCE (mild) — a candidate carrying a GameBalance.PALETTE_HARSH_THEME_TAGS tag
        ("gore"/"rust"/"radiation") gets an additive weight of depth ×
        GameBalance.PALETTE_DEPTH_HARSH_WEIGHT_PER_DEPTH, so deeper floors trend grittier. All weighting
        is data-driven through GameBalance — the allocator never switches on a specific char or sprite.
   Weights feed GameMath.weightedChoiceIndex (the SHARED route/tileset roulette picker — no duplicate
   implementation) with the seeded roll. Coherence and depth only bite once catalog sprites carry the
   matching theme tags; the production catalog is largely untagged today (only observatory is tagged), so
   in-game these rules currently collapse to a plain seeded pick — they activate as content adds tags.
   Nothing renders varied yet regardless: order-4 changes NO runtime behaviour (renderers still read the
   legacy palette until order-7).

   MATH — GameMath.paletteSymbolSeed(long levelSeed, char symbol) -> long (with the mandatory
   Formula/Derivation/Edge-cases comment block):
       mixed = levelSeed ^ (TilesetConstants.PALETTE_SEED_SALT * (symbol + 1))
       mixed = mixed * 0x9E3779B97F4A7C15 + symbol           // same golden-ratio mix as routeNodeSeed
   The salt is scaled by (symbol + 1) so palette rolls form an INDEPENDENT stream from World.floorSeed and
   routeNodeSeed at the same seed, and so the NUL theme key (symbol 0) still produces a salt-dependent
   seed rather than collapsing to levelSeed. Java 'char' is unsigned 16-bit, so there are no negative
   chars; the (symbol + 1L) long promotion also prevents int overflow at the top of the char range. The
   result seeds tileset PaletteRng (the twin of route/RouteRng: advance by the golden increment, finalise
   each draw through GameMath.splitMix64), the side-effecting cursor that cannot live in pure GameMath.
   NEVER inline this formula in the allocator. PALETTE_SEED_SALT lives in TilesetConstants (order-2).

   DETERMINISM (the fairness promise): same levelSeed + same placedRoomDemands => byte-identical
   LevelPalette (required for permadeath fairness and seed sharing). Step 2 depends on WHICH rooms were
   placed, and room placement is itself seeded upstream in LevelGenerator, so the whole chain stays
   reproducible. The allocator is a pure function of its request — no static mutable state, no time, no
   iteration-order dependence.

   CLASSES (all in `…toon3d.tileset`): SymbolAllocationRequest, RoomSymbolDemand (immutable inputs),
   SymbolAllocator (the pure engine), PaletteRng (package-private per-symbol RNG). Weighting knobs live in
   GameBalance (PALETTE_VARIETY_BASE_WEIGHT, PALETTE_COHERENCE_WEIGHT_MULTIPLIER,
   PALETTE_DEPTH_HARSH_WEIGHT_PER_DEPTH, PALETTE_HARSH_THEME_TAGS) so designers tune variety without
   touching allocator logic.

   TESTS (headless, core/src/test/.../tileset/SymbolAllocatorTest): determinism (same request => equal
   palettes, deep-equals); fixed integrity ('x'->"wall_plain", '@'->"prop_vendor" for every seed, never
   rolled); reservation + freed symbols (a placed CRYO demand binds its symbol to the room sprite; an
   ABSENT room's symbol becomes generic variety; a reserved sprite never leaks to a second symbol);
   containment R2 (no observatory sprite ever appears in a generic slot, across seeds, on the production
   catalog); anti-repetition R3 (with a themed registry whose pool exceeds the slot count, all accent
   walls are distinct); coherence R1 (statistical over 400 seeds on a themed registry: the majority of a
   level's accent walls share the level theme's tag); capacity (all signature rooms placed at once
   allocate with no clash; a deliberate same-symbol clash reroutes to a distinct free symbol without
   dropping either sprite).

5. ROOM BLUEPRINTS  [DONE — order-5]
   The ROOM extensibility layer: a room is now a REGISTERED, self-describing object (RoomBlueprint) in a
   RoomBlueprintRegistry the generator can select from, instead of a private `enum RoomType` referenced by
   ~4 hardcoded switches. This is the route/GeneratorRegistry pattern applied to rooms ("never a switch
   statement"). order-5 is a PURE STRUCTURAL REFACTOR PLUS THE REGISTRY SEAM: same seed => byte-identical
   level (guarded by LevelGeneratorSnapshotTest); it does NOT change room selection or rewire generate()
   (that is order-8).

   PACKAGE PLACEMENT (decision (a) from the order-5 design): the blueprints live in `…toon3d.level`, next
   to LevelGenerator, because build() writes into the char[][] grid through the generator's per-room
   helpers. The `tileset` package stays purely about categories/sprites/budget/allocator; only the demand
   type it consumes (RoomSymbolDemand, order-4) lives there.

   SIGNATURE vs GENERIC (RoomKind):
     * SIGNATURE — fixed identity (architecture AND look): MEDICAL_BAY, ARMORY, CRYO_CHAMBER, SERVER_ROOM,
       POWER_PLANT, COMMAND_CENTER, CONTAINMENT_BLOCK, RESEARCH_LAB, STELLAR_OBSERVATORY. Each CLAIMS a set
       of sprites when placed (its symbolDemand); absent, it frees them.
     * GENERIC — allocator-driven filler with an EMPTY demand: ENTRANCE, STANDARD, LARGE. Their walls/props
       get per-level variety from the order-4 allocator, not a fixed claim.

   CLASSES (all in …toon3d.level, headless — no LibGDX):
     * RoomKind — SIGNATURE | GENERIC.
     * RoomContext — the immutable query struct eligible()/selectionWeight() read: candidate interior
       width/height, the floor's dungeonDepth, and alreadyPlacedOfThisKind (for per-level hard caps). It
       mirrors exactly the facts LevelGenerator.assignRoomTypes()'s gates read today.
     * RoomBlueprint (interface) — id() (stable registry key, never renamed), kind(), eligible(RoomContext)
       (the LevelGenConstants min-size / depth-window / hard-cap gates), selectionWeight(RoomContext) (the
       *_CHANCE roll weight; consumed by order-8, declared here), symbolDemand() (RoomSymbolDemand — the
       sprite ids reserved when placed), and build(RoomBuildContext) (stamps the room's architecture).
     * RoomBuildContext — the build facade: wraps a LevelGenerator + the target grid + the one Room, and
       exposes that room type's architecture steps as thin package-private delegators to the generator's
       EXISTING per-room helpers (a per-type pass scoped to a single-room list, or a `*ForRoom` helper for
       the two index-1 STANDARD passes). So build() stamps with the identical code (and identical RNG draw
       sequence) the generator's own passes use — no copy that could drift.
     * RoomBlueprintRegistry — register / get / contains / size / all / allSignature / allGeneric /
       selectable(RoomContext). Insertion-ordered (reproducible), duplicate id throws, get(unknown) throws.
     * RoomBlueprints — the bootstrap hub (twin of TilesetRegistries.bootstrap()). bootstrap() is
       idempotent and registers all 12 v1 blueprints; called once from World.create() next to
       TilesetRegistries.bootstrap().

   THE DEMAND MODEL (order-4 interaction): a SIGNATURE blueprint's symbolDemand().requiredSprites() maps
   each flexible symbol its build() stamps to that symbol's LEGACY sprite id (verified equal to
   LevelPalettes.legacy() per symbol). Example: cryo_chamber demands 'Z'->"wall_cryo" (+ 'N'->"wall_glass"
   accent, '&'->"prop_biopod", ...). The STELLAR_OBSERVATORY demand is exactly the "observatory"
   theme-tagged sprites, so order-4 binds them ONLY when the room is placed — realising order-4 R2
   containment through the demand, not a special case. When a signature room is NOT placed it contributes
   no demand, so its symbols fall through to the free variety pool (the freed-symbol mechanic). order-8
   collects each placed blueprint's symbolDemand into SymbolAllocationRequest.placedRoomDemands.

   ORDER-5 REFACTOR DISCIPLINE (what changed in LevelGenerator, behaviour held constant):
     * `enum RoomType` and its constructor stay as an INTERNAL TAG (now package-private) — placeRooms()/
       assignRoomTypes() still select with it, and themeNewRoomWallsForRoom() still switches on it. order-8
       removes the switch and the enum when it flips generate() to iterate the registry.
     * The room-type passes were made reusable per-room WITHOUT touching their RNG: the type-guarded
       for-each passes (floor lighting, themeServerRoomWalls, all *Props, placeLargeRoomColumns) were made
       package-private and are invoked by RoomBuildContext on a single-room list; themeNewRoomWalls and the
       two index-1 STANDARD passes (placeProps, placeColumns) were split into `*ForRoom` helpers that both
       the generate() pass and RoomBuildContext call. Every qualifying perimeter tile still consumes one
       random.nextFloat() for EVERY room type — do not skip the roll for unthemed types.
     * Pickups, weapon spawns, and enemy placement are NOT owned by build() in order-5: they place FIXED
       symbols (not part of any symbolDemand) and remain generator passes until order-8 rewires generate().

   THE RECIPE (add a room, once order-8 lands the selection wiring): write one RoomBlueprint (id, kind,
   eligible, selectionWeight, symbolDemand, build) + one register() line in RoomBlueprints.registerAll().
   No LevelGenerator switch edits. order-5 makes rooms REGISTERED; order-8 makes the generator SELECT from
   the registry; order-9 documents the full end-to-end RECIPE B.

6. TEXTURE REALIZATION (per level)  [DONE — order-6]
   The RENDER-SIDE foundation that makes "each level uses a subset of a large pool" real IN MEMORY. Today
   WallRenderer generates EVERY wall texture in its constructor and holds them all forever; that does not
   scale to the large pool this series enables. order-6 splits GENERATION (data-driven, registered per
   sprite id) from REALIZATION (per level, lazy): a level builds textures only for the handful of sprite
   ids in its palette and frees them when the level ends. Small GPU footprint per level; unbounded library
   overall. This is the ONLY render-layer order in the series' first half and introduces the new render
   sub-package. It does NOT change what WallRenderer/PropRenderer DRAW — that is order-7; order-6 builds
   the texture-supply mechanism and proves it disposes correctly, with both paths coexisting.

   NEW PACKAGE `…toon3d.render.tilesetgfx` (render layer — MAY import LibGDX; it produces Textures). This
   is the boundary where headless sprite ids become pixels; the `tileset` package stays headless.

   CLASSES (all in …toon3d.render.tilesetgfx):
     * EnvironmentTextureGenerator (functional interface) — Texture generate(): produces the Texture for
       ONE sprite. Its BODY is the EXISTING procedural code, reached by DELEGATION: the constructors'
       generate*Texture() routines stay in WallRenderer/PropRenderer (byte-identical pixels — the art does
       not change), and each renderer contributes its own generators via a public static
       registerTextureGenerators(registry) that method-references those routines. Intrinsic width/height
       are NOT carried on the generator; EnvironmentTextureSet reads them off the realized Texture.
     * TextureGeneratorRegistry — register(spriteId, generator) / has(spriteId) / generate(spriteId)->
       Texture / ids(). Duplicate id throws (route-registry discipline); generate() on an unknown id throws
       BEFORE invoking any generator (so the check is testable headlessly). Insertion-ordered ids().
     * TilesetGfxBootstrap — the render-side twin of TilesetRegistries.bootstrap() and sibling of
       RouteIconBootstrap. Holds the process-wide generator singleton (generators()); bootstrap() is
       idempotent and (a) registers every v1 sprite id's generator — walls + round column from
       WallRenderer, solid props + floor decals from PropRenderer — and (b) runs the STARTUP ASSERTION:
       the generator id set MUST EQUAL the sprite-catalog id set (TilesetRegistries.sprites().ids()), so a
       sprite added without a generator (or vice-versa) fails loudly at startup, not mid-level. Called once
       from World.create(), after TilesetRegistries.bootstrap() (the assertion cross-checks against it).
     * EnvironmentTextureSet (per-level, Disposable) — realize(LevelPalette palette, TextureGeneratorRegistry
       gens) collects the DISTINCT sprite ids the palette references (LevelPalette.distinctSpriteIds(),
       de-duplicated so two symbols on the same sprite id share ONE texture), generates each once, and
       stores id -> Texture (+ intrinsic width/height). textureFor/widthFor/heightFor throw for a sprite the
       level never referenced (asking outside the subset is a bug, not silent null). dispose() frees every
       realized texture and MUST run on level teardown. It routes disposal through
       PropRenderer.disposeGeneratedTexture so prop/decal textures also drop their entry in PropRenderer's
       static opacity-mask cache (a harmless no-op for wall/column textures) — otherwise that cache would
       leak one mask per prop per transition. On realize() it logs the count (Gdx.app.debug) to confirm
       subset sizing during development.

   MEMORY STORY (the payoff): the resident texture set is EXACTLY the level's palette sprites — subset per
   level, not whole-library per level. A legacy-palette level realizes today's full wall/prop set because
   the legacy palette references the whole catalog (distinctSpriteIds() == the catalog id set), so order-6
   lands with ZERO visual change; a future varied palette realizes only its own small subset.

   LIFECYCLE WIRING (World): buildLevelDependentResources() realizes the set from targetLevel.getPalette()
   right after building WallRenderer/PropRenderer, and hands it to both via setEnvironmentTextureSet()
   (per-level setter, like setPlayerState but once per level). rebuildForLevel() disposes the OLD set
   before the next floor rebuilds its subset; World.dispose() frees the current set at shutdown; both null
   the reference after disposing. order-6 wires this plumbing + dispose path only — the renderers STORE the
   set but still draw from their constructor-built tables until order-7 reads from it. Leak safety: the set
   is the new owner of per-level wall/prop textures and is in World's dispose chain, so repeated level
   transitions hold a stable texture count.

   TRANSITION SAFETY: WallRenderer/PropRenderer keep their existing constructor-built textures during
   order-6 (both paths coexist) so the game keeps running; the legacy default guarantees the set contains
   the same textures the renderers used to hold. order-7 removes the old tables once draws read the set.

   RECIPE (extends order-1's add-a-sprite recipe): register the sprite in TilesetRegistries AND its
   generator in the matching renderer's registerTextureGenerators() — the startup id-set assertion enforces
   you did both. (Full end-to-end add-a-sprite recipe consolidated in section 9 / order-9.)

   TESTS (headless — generators are registered as method refs, never INVOKED, so no GL context is needed):
   render/tilesetgfx/TextureGeneratorRegistryTest — the generator id set EQUALS the sprite catalog id set;
   bootstrap() idempotent and passes the assertion; the legacy palette references the whole catalog;
   duplicate/unknown ids throw; ids() preserves registration order. tileset/LevelPaletteDistinctSpriteIdsTest
   — several symbols on one sprite id collapse to one distinct id (the subset-sizing core); a small palette's
   distinct set is far smaller than the catalog; the legacy palette's distinct set IS the whole catalog. The
   actual pixel realization (realize()) needs a GL context and is verified in-game (stable texture count
   across repeated floor transitions).

7. RENDER INTEGRATION  [DONE — order-7]
   THE FLIP: the renderers stop reading their own constructor-built per-char texture tables and instead
   resolve each environment symbol through the level's LevelPalette + EnvironmentTextureSet (order-6). After
   this order, changing a level's palette VISIBLY changes what its walls / columns / props look like.
   Because every level still defaults to the LEGACY palette (order-3) — which maps each symbol to the SAME
   sprite id the old tables used, realized by the SAME generators — THE GAME LOOKS IDENTICAL after order-7;
   variety only appears once order-8 feeds generated levels a varied palette. "Swap the engine under the
   hood without changing the ride."

   SYMBOL -> SPRITE -> TEXTURE (each frame, per hit):
     spriteId = levelPalette.spriteIdOf(symbol);            // headless id, per level
     texture  = environmentTextureSet.textureFor(spriteId); // the pixels, realized per level (order-6)
   Widths/heights come from the same set (widthFor/heightFor); billboard prop HEIGHTS come from the sprite
   DEFINITION (EnvironmentSpriteRegistry.get(spriteId).heightMultiplier()), copied literal-for-literal from
   the RenderConstants the old switch used — so the look is unchanged.

   WALLRENDERER (walls + columns):
     * HOT-PATH SHAPE PRESERVED. The per-column DDA workers must not do a map lookup per column. So at level
       load — in the per-level setter setEnvironmentTextureSet(), on the GL thread BEFORE any render() —
       WallRenderer PRE-RESOLVES the palette+set into small char-indexed arrays (levelWallTextures /
       levelWallWidths / levelWallHeights, ASCII 0–127) and dedicated column fields (levelColumnTexture /
       Width / Height). The draw loop still does ONE O(1) array read per column, exactly as the old static
       wallTextureTable did. The arrays are immutable for the level's life; the workers read them via the
       happens-before edge from the setter running before the executor dispatch, so no synchronisation is
       needed (same publication contract as setPlayerState's cached fields). No per-frame allocation: all
       resolution happens once per level in the setter, never in render().
     * Every non-wall slot defaults to "wall_plain" (a FIXED binding present in every palette, hence every
       realized set) so an unrecognised char can never NPE — the same NPE-safety the old Arrays.fill gave.
     * The column path resolves 'P' via spriteIdOf('P') -> the round (today) OR square (order-8) column
       texture. This is the mechanism that lets 'P' render either column per level.
     * OWNERSHIP MOVED. WallRenderer NO LONGER owns wall/column textures — the per-level EnvironmentTextureSet
       does (World's dispose chain). WallRenderer's constructor no longer builds them and dispose() no longer
       frees them (freeing them here would double-free the set's textures). WallRenderer still owns only the
       door textures (FIXED gameplay symbols, not tileset sprites, so not in any set) and its 1×1 white pixel.
       The per-char generate*WallTexture()/generateColumnTexture() routines stay in the class but are reached
       only through the TextureGeneratorRegistry (order-6 registerTextureGenerators), which the set uses.

   PROPRENDERER (solid props + floor decals):
     * resolvePropTexture() resolves ENVIRONMENT props (SOLID_PROP + FLOOR_DECAL) via
       spriteIdOf(char) -> environmentTextureSet.textureFor(spriteId); FIXED gameplay props (keycards,
       medical, armour, portal, ammo) keep their own owned textures (buildTextures now builds ONLY those),
       and the animated hazards 'i'/'q' keep their frame cycles. propHeightMultiplier() reads the sprite
       definition's heightMultiplier for environment props and a trimmed switch (fixed gameplay props only)
       otherwise.
     * The shop '@' -> "prop_vendor" is a FIXED-sprite exception but still an environment sprite, so it
       resolves through the set like any other prop (identical vendor art).
     * Opacity masks (enemy occlusion) still work: the set's prop textures are produced by the same
       generate* routines, which register a COLUMN_OPACITY mask via finalize(); EnvironmentTextureSet.dispose()
       routes through PropRenderer.disposeGeneratedTexture() to prune those masks (order-6), so no leak.

   LEVEL CATEGORY PREDICATES (isWall / isColumn / isPropSolid / isPropDecal / isPropOccluder):
     * FIXED vs FLEXIBLE, still STATIC and PALETTE-FREE. A symbol's CATEGORY is symbol-intrinsic — a flexible
       WALL symbol is ALWAYS a wall regardless of which wall sprite fills it — so category membership does
       NOT depend on the per-level sprite; only the sprite does. The predicates therefore keep answering
       correctly for both fixed and flexible symbols WITHOUT taking a LevelPalette argument, so they stay
       callable from hot movement / AI / collision / LOS code with no render dependency.
     * ONE SOURCE OF TRUTH. They are now backed by tileset/SymbolCategories.categoryOf(char) instead of
       hand-maintained char lists. SymbolCategories derives the char->category map ONCE from the SymbolBudget
       partition (order-2, the flexible category tables) plus, for the two fixed-sprite exceptions
       ('x' -> "wall_plain", '@' -> "prop_vendor"), the category recorded on their sprite definitions in the
       registry (order-1). isWall == WALL, isColumn == COLUMN, isPropSolid == SOLID_PROP; isPropDecal ==
       FLOOR_DECAL OR the fixed gameplay decals (hazards/keycards/medical/armour/ammo/stairs, which are not
       tileset sprites and keep their own checks); isProp == isPropSolid || isPropDecal; isPropOccluder ==
       isPropSolid (SOLID_PROP occludes; FLOOR_DECAL does not — mirroring the sprite definitions' occluder
       flag) plus the fixed gameplay occluders. Adding a flexible symbol to a category is now a data edit in
       TilesetConstants, not a predicate edit.

   THE INVARIANT: fixed symbols still resolve statically; only flexible ART is palette-driven. Category is
   symbol-intrinsic and never needs the palette; the sprite (and thus the texture) is the only per-level part.

   TESTS: SymbolCategoriesTest (headless) asserts categoryOf agrees with Level's predicate membership across
   the printable ASCII range and returns null for gameplay symbols; the existing LevelPaletteTest /
   TilesetRegistriesTest / LevelGeneratorSnapshotTest continue to pass unchanged (identical membership,
   byte-identical generation). Legacy-palette look parity + no double-free / no leak across floor transitions
   are verified in-game (stable texture count).
