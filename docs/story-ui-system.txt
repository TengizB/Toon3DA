STORY UI SYSTEM
===============
The game's narrative delivery layer: how a linear, five-region story is told to a player who is
playing a permadeath roguelike on a phone, in small doses, without ever being trapped in text.

This is the SINGLE SOURCE OF TRUTH for the story UI subsystem (`…toon3d.narrative`, the story
renderers in `…toon3d.render`, `util/StoryUiConstants`, `util/StoryStore`). It documents SHIPPED
behaviour: where an order changed its design during implementation, this doc reflects how the code
actually works today. The original intent lives in `.claude/agents/ideas/story-ui-order-N.txt`
(orders 1-7), and the fiction itself lives in `story/00..08` and `story/dialog/*`.

THIS DOC GOVERNS THE MACHINE, NOT THE WORDS. What a line is allowed to SAY — the three jobs a line
must do, the plain-before-proper rule, the joke policy, ORA's voice charter, and what the player must
be able to answer by when — is the CONTENT contract in **docs/narrative-authority.txt**. Read it
before writing or cutting any narrative row; a row that satisfies the recipes below and fails that
document does not ship.


UPDATE CONTRACT (mandatory — mirrors docs/route-map-system.txt)
==============================================================
Any change to the story UI MUST update THIS document in the SAME commit:
   - new channel / renderer            -> THE FIVE CHANNELS + the render order section;
   - new persisted narrative fact      -> PART B: PERSISTED STATE (schema table + version history);
   - new string id family / new locale -> PART C: LOCALISATION;
   - new sound                         -> PART D: AUDIO (cue table);
   - new overlay that can own the screen -> PART E: PRECEDENCE;
   - new framing screen / menu row     -> THE FRAMING SCREENS + its recipe below;
   - new gameplay moment that fires a beat -> THE MOMENT SCHEDULE table;
   - new spine beat / new pacing ceiling -> THE LORE DRIP (the region beat maps + the per-floor
     budget). A beat that a region's map names must ride a channel a player cannot route around.
Any change to what the lines SAY additionally runs the change protocol in
docs/narrative-authority.txt (SECTION 9) and updates that document where it says so.
The governing invariant behind every recipe below: "if you had to edit a switch statement to add a
line, the registries are being bypassed — fix that instead." Adding narrative content is always ONE
`register()` call plus one string-table row.


OVERVIEW — WHAT THE PLAYER EXPERIENCES
======================================
Almost nobody reads optional text on a phone. So the story is delivered in five channels, ordered by
how hard they are to avoid, and the plot spine rides only the ones a skimmer cannot skip:

  BOOT CARD    every run starts here (it is a reprint — you died). Full-screen, blocking, waits for
               a tap. SYSTEM status lines, the quiet instance counter, one ORA wake-up line.
  BARKS        ~80% of the story. One-line panels during play; non-blocking, choice-less, and they
               NEVER auto-dismiss — the player closes them with the X or a swipe.
  EXCHANGES    the blocking half: a prompt and 2-3 big tappable answers. Rare and deliberate; the
               tap is the point, because answering is what makes a non-reader read.
  CODEX        the opt-in archive. The only screen where long text is allowed. Never required.
  CONTROL HINTS  the entire tutorial, delivered as barks by ORA, one line per control at the moment
               that control first matters. There is no tutorial screen and there must never be one.
  FRAMING      the screens that BOOK-END play: the launch screen (which opens on the game telling
               the player they are already dead), the death -> reprint transition, the pause and
               settings menus, and the way off an ending. See THE FRAMING SCREENS below.

Four SPEAKERS carry all of it — ORA (the AI), the Planet, the Organization, SYSTEM — each with a
name chip, an icon, a type style, an accent colour and an audio sting, so identity never rests on
colour alone.


ARCHITECTURE — HEADLESS BRAIN, DUMB RENDERER
============================================
    …toon3d.narrative     NO LibGDX imports. Data + decisions: which line, when, for how long,
                          what an answer does, what is unlocked. Unit-tested headlessly.
    …toon3d.render        Draws whatever the brain reports. Owns GPU/audio handles. Decides nothing.
    util/StoryUiConstants Every number and every localisation id used by either half.
    util/StoryStore       The Preferences-backed persistence adapter (the engine half of the port).

Per channel:

  | Channel   | Headless brain    | Catalog (content)  | Renderer                |
  |-----------|-------------------|--------------------|-------------------------|
  | Bark      | BarkSystem        | BarkCatalog        | StoryBarkRenderer       |
  | Boot card | BootCardSystem    | BootCardCatalog    | BootCardRenderer        |
  | Exchange  | ExchangeSystem    | ExchangeCatalog    | StoryExchangeRenderer   |
  | Codex     | CodexSystem       | CodexCatalog       | CodexOverlayRenderer    |
  | Framing   | TitleScreenSystem | FramingStrings     | FramingScreenRenderer   |
  |           | + FramingMenu     | (chrome only)      | + InstanceReportRenderer|

Shared render pieces: `StoryPanelRenderer` (the one panel primitive every channel draws with),
`StoryAudio` (all seven sounds, ONE world-owned instance), `StoryStringsLoader` (the one place the
string asset is read).

Render order (World.render, after the HUD): bark -> exchange -> codex -> pause/settings menu ->
boot card (or its REPORT page, or an ending's RETURN plate) -> fade -> the death stroke (which is
drawn ON the finished fade, and is the only thing on the screen while it is up).
Each modal brings its own dim/scrim, so nothing behind it needs to know it is there. The LAUNCH
screen is the exception: it replaces the frame entirely (World.render returns before the 3D view),
because while it owns the app there is no run to look at.


PART A — ROGUELIKE STORY-GATING (the critical reconciliation)
============================================================
THE PROBLEM: the story is a linear descent through five regions; the game is a permadeath roguelike
with a branching route map, played across dozens of runs. Tying beats to the current run would make
death rewind the plot and replay every beat, every attempt.

THE RULE: **story progress is gated by the DEEPEST STORY REGION EVER REACHED, which is PERSISTENT.
Death never rewinds the story.**

  - `StoryRegion` is the gating axis: HABITATION_RINGS -> HARVESTING_GALLERIES -> RELIQUARY ->
    WOUND -> CORE. Route regions map onto it via `StoryRegion.fromRouteRegionIndex()`.
  - `StoryProgress.getDeepestRegion()` only ever climbs (`reachRegion` keeps the deeper of the two),
    so an out-of-order branch can only deepen the story and a fresh run at the surface cannot
    rewind it.
  - Every one-shot beat is keyed by id in `StoryProgress.hasSeen()/markSeen()`, persisted. Re-entering
    a region on a later run does not replay its intro.
  - ORA's tone, the planet's voice stage and the Organization's escalation are expressed PURELY by
    which region band a row is registered in — never by an `if (region == …)` in game code.
  - The boot card is the one beat that fires every death by design; its ORA line is chosen by the
    same deepest-region gate, so it also only moves forward.

DIEGETIC FIT: this is the premise, not a hand-wave. The clone remembers every run, ORA is never
wiped, the planet never forgets you (story/02-player-and-cloning.md, 03-the-planet.md).

EDGE CASES
  - Branching route: gate strictly by depth; every region's beats are self-contained so any path
    reads correctly.
  - The Core is many floors (the route map is endless), so the ENDING exchange is guarded twice:
    deepest region == CORE **and** the Core's boss is down. That convergence is what makes one Core
    floor final.

TESTS: `StoryPersistenceTest` (Part A section), `StoryBarkTest`.


PART B — PERSISTED NARRATIVE STATE
==================================
Port: `narrative/StoryProgressStore` (headless interface).
Implementations: `util/StoryStore` (LibGDX Preferences — the game) and
`narrative/InMemoryStoryProgressStore` (tests).
All narrative keys share the `StatsStore` preferences file under a `story.` prefix, so a single-save
"new game" can clear meta-progression and story together.

  | Persisted fact          | Key                       | Written when                        |
  |-------------------------|---------------------------|-------------------------------------|
  | deepest region reached  | story.deepestRegion       | a region is entered for the 1st time|
  | one-shot beat flags     | story.beat.<id>           | a one-shot beat fires               |
  | reprint (instance) count| story.reprintCount        | a boot card is presented            |
  | hidden stance leanings  | story.stance.<STANCE>     | an exchange option is answered      |
  | consequential outcomes  | story.outcome.<exchangeId>| a CONSEQUENTIAL option is answered  |
  | codex unlocks           | story.codex.<id>          | a line is delivered / a PROBE pays  |
  | codex read-flags        | story.codexRead.<id>      | an entry is opened                  |
  | accessibility settings  | story.setting.<key>       | the player changes a setting        |
  | the ending committed to | story.outcome.ending      | an ending choice commits (order-8)  |
  | schema version          | story.schemaVersion       | stamped on every write              |

The ENDING (order-8) rides the order-4 consequential-outcome mechanism rather than a key of its own —
an ending IS the ultimate consequential outcome — so it needed no schema bump, and a "new game"
clears it with everything else. `StoryProgress.recordEndingReached/getEndingReached` are the typed
accessors; the value is a `BootCardVariant` name, and the launch screen reads it back to decide which
card's status lines it prints.

RULES
  - Write on meaningful change only — never per frame. A whole run is a handful of writes.
  - Treat as SINGLE-SAVE meta-progression that survives permadeath.
  - Reads/writes degrade to no-ops with no LibGDX app present, so narrative logic never depends on a
    live Preferences backend.

SCHEMA VERSION (`StoryProgressStore.SCHEMA_VERSION`, currently 4)
  v1 order-2/3 (region, beat flags, reprint count) -> v2 order-4 (stance, outcomes, codex unlocks)
  -> v3 order-6 (codex read-flags, settings) -> v4 order-7 (story-audio setting).
  Every version so far has only ADDED keys, and every key reads a default when absent, so no data
  migration has ever been needed: `StoryStore.migrateIfNeeded()` (run in its constructor) re-stamps
  an older save and leaves a NEWER-than-this-build save completely untouched. Bump the constant and
  add the migration beside it whenever the persisted shape actually changes.

"NEW GAME" (the only thing that moves the story backwards)
  `World.wipeAllPersistentProgress()` -> `StatsStore.wipeAllPersistentProgress()` clears the whole
  preferences file (records + tips + story keys), then the world re-reads everything it cached:
  `StoryProgress.reloadFromStore()`, `StorySettings.reloadFromStore()`, `CodexSystem.refresh()`,
  `PersistentStats.reset()`. `StoryProgress.wipeAllNarrativeState()` is the narrative-only variant.
  Everything clears TOGETHER: a save with the region reset but the one-shot flags spent would start a
  story that can never be told. Death does not call this; nothing in a run calls this. It exists for
  order-8's title/settings screen, behind a confirmation.

TESTS: `StoryPersistenceTest` (round-trip, versioning, wipe, reload).


PART C — LOCALISATION / STRING EXTERNALISATION
=============================================
**No story string is hardcoded in Java.** Every line — barks, exchange prompts, the player's own
answers, replies, boot-card status lines, codex entries, and all screen chrome — is referenced by a
stable STRING ID and resolved through `StoryStrings`.

  - Shipped table: `assets/story/story-strings.properties` (`StoryUiConstants.STORY_STRINGS_ASSET_PATH`).
  - Loaded once by `render/StoryStringsLoader.load()`, which falls back to `StoryStrings.defaults()`
    (the per-order Java tables: BarkStrings, BootCardStrings, ExchangeStrings, CodexStrings) when the
    asset is missing or unreadable. The game must never fail to boot over a text file.
  - A missing id resolves to a VISIBLE `!id!` marker, never to blank — a hole you can read is a hole
    you fix in playtest.
  - Ids are stable once shipped (translations key off them): lower case, dotted, `story.`-namespaced,
    no whitespace.
  - An id family per channel: `story.bark.*`, `story.boot.*`, `story.exchange.*`, `story.codex.*`,
    plus `story.speaker.*` for the name chips, and order-8's framing chrome: `story.title.*`,
    `story.pause.*`, `story.settings.*`, `story.frame.*`, `story.report.*`. ORA's one-line TAKE on a
    log and the log's full codex text are deliberately separate ids (bark vs archive).
  - The launch screen has NO status-line ids of its own: it prints `story.boot.system.*`, the reprint
    card's own strings. That sharing is the point, not an optimisation (see THE FRAMING SCREENS).
  - THE TABLE HOLDS ONLY DELIVERABLE CONTENT. If no channel can ever deliver an id, it does not
    belong in the file a translator receives, and it does not belong in `StoryStrings.defaults()`
    either. `story.sample.*` — the four order-1 one-line-per-speaker showcase rows — is the one such
    family and it lives in `narrative/StorySampleLines.registerShowcaseText()`, folded in by hand by
    the two dev callers (`lwjgl3/StoryUiShowcase`, `StoryUiFoundationTest`) and by nothing in the
    game (narrative-rework order-6 B).

TESTS: `StoryLocalizationTest` sweeps EVERY id from every catalog and every piece of chrome against
the shipped asset, checks the Java fallback agrees with it, and rejects duplicate keys.


PART D — AUDIO CUES
===================
There is no voice acting. There are seven short procedural tones, and every one of them is redundant
polish: **the game must be fully understandable with audio off.** Nothing is ever conveyed by sound
alone.

  - `render/StoryAudio` — ONE world-owned `Disposable` that owns every story sound and is injected
    into the bark, exchange and boot-card renderers (`setStoryAudio`). Renderers never build their
    own: four channels each synthesising the same seven sounds is four times the voices for
    identical audio.
  - Synthesised at construction with `GameMath.storyStingSample()` into a minimal 16-bit mono WAV
    (no asset files). If the audio backend is unavailable, synthesis is skipped and every play call
    is a silent no-op.
  - Played from the UPDATE path, never from render — audio is a simulation side effect.

  SPEAKER STINGS (`STORY_STING_*`, indexed by `Speaker.ordinal()`)
    ORA soft blip · Planet low organic tone · Organization cold square-wave beep · SYSTEM neutral click

  INTERFACE CUES (`StoryCue`, `STORY_CUE_*`)
    | Cue           | Fires when                                    |
    |---------------|-----------------------------------------------|
    | PANEL_OPEN    | an exchange takes the screen                  |
    | CHOICE_PICKED | an answer is committed (firm, low, square)     |
    | REVEAL_TICK   | one more boot-card status line prints          |

  THE SWITCH: the codex's accessibility strip carries a SOUND knob
  (`StorySettings.isStoryAudioEnabled()`, persisted as `story.setting.storyAudio`, default ON) which
  `World.applyStoryAccessibilitySettings()` pushes into `StoryAudio.setEnabled()`. One switch for the
  whole layer, not a per-cue submenu.


PART E — OVERLAY PRECEDENCE & INTERRUPTS
========================================
The story UI shares the screen with the inventory, level-up card, shop, weapon inspect, event choice,
nav console, death screen and boot card. Three promises:

Order-8 adds four phases to that list — TITLE, PAUSE_MENU, SETTINGS_MENU and ENDING_HOLD — and they
obey the same three promises: each is a hard-pause overlay, none draws the thumb clusters, and none
lets a story panel open behind it.

1. A HARD-PAUSE OVERLAY WINS. `World.update` runs `barkSystem.setSuppressed(runPhase != PLAYING)`
   every frame: while any modal is open, bark requests still QUEUE, nothing is delivered, and queue
   ageing is FROZEN so a long menu visit cannot silently eat a line. An EXCHANGE never opens outside
   PLAYING — it is held PENDING until the player is idle, alive, not mid-fade, with no bark on
   screen (`World.openPendingStoryExchange`).
2. NEVER TWO STORY PANELS. One story element is visible at a time, ever — enforced in the systems
   themselves (`ExchangeSystem.request/openPending` refuse while one is active, and the active row
   is excluded from its own candidate pool).
3. COMBAT SPIKE. `BarkSystem.setCombatSpike()` (fed by `EnemyManager.countAwakeEnemies()`) holds
   non-critical lines until the lull; a `STORY_CRITICAL` beat still lands mid-fight, because a
   dropped control hint is a stuck player.

APP LIFECYCLE (Android): `Main.pause()/resume()` -> `World.onApplicationPause()/onApplicationResume()`.
Nothing story-side is torn down, and that is deliberate — a modal owns `runPhase`, so an exchange, a
boot card or the codex is exactly where it was when the app returns; "re-open on resume" costs
nothing because the layer never left. What IS dropped is transient TOUCH state (a pressed answer
plate, a codex drag, a bark swipe, held buttons), because the finger that left never sends its
release, and a tap that merely restored the app must not also answer the prompt it restored into.
On resume the accessibility settings are re-pushed, since Android may have lost the GL context.

INTERRUPTION SAFETY: a one-shot exchange is marked seen when it is ANSWERED, not when it opens. If
the OS kills the process mid-prompt, the beat is asked again on the next run instead of being spent
on a conversation nobody read.

TESTS: `StoryOverlayPrecedenceTest`.


THE FRAMING SCREENS (order-8) — what surrounds play
==================================================
Orders 2-7 built what happens DURING a run. Order-8 owns the screens on either side of it: the app
launch, the death -> reprint transition, the pause and settings menus, and the resolution of an
ending. They all speak the boot card's visual language (the same near-black backdrop, the same amber
plates), because the launch screen and the reprint card are the SAME machine talking.

A. THE LAUNCH SCREEN (`narrative/TitleScreenSystem`, `render/FramingScreenRenderer`)
   **There is no cheerful title screen.** The app opens on black and the first line anybody reads is
   the game telling them they are already dead — in words a stranger can parse cold
   (narrative-rework order-2 A, which replaced "PREVIOUS INSTANCE - TERMINATED / SOUL RESERVE
   .......... SUFFICIENT": two undefined nouns and a status readout for a system nobody has heard of,
   spending the Region-3 reveal on screen one):
        OPERATOR ............. DECEASED
        BODY RECOVERY ........ NOT POSSIBLE
        BACKUP COPY .......... ON FILE
        PRINTING NEW BODY .... STAND BY
   ...then a beat, then the title resolves quietly beneath it, then a cold menu fades in under that.
   The lines are the BOOT CARD's own string ids, borrowed from `BootCardRegistry` — one machine, one
   voice, one string (story/dialog/system-cards.md). WHICH card it borrows from is the save's own
   state, and nothing else: FIRST_PRINT while the reprint count is zero, REPRINT after that (deeper
   band once the story has earned it), and an ending's card once one has been recorded.
   How many lines it borrows is per card (`BootCardDefinition.getLaunchStatusLineCount`): the
   first-print block prints whole, because on an empty save those four lines are the only explanation
   the player has; every other card stops before its closing "PRINTING NEW BODY", which is a promise
   about a run that has not started. The block is bottom-anchored, so short and long notices both end
   just above the title.
   The reveal is MOOD, never a gate: a tap prints the whole screen at once, and nothing on it ever
   advances itself.

   THE MENU — the way down is ALWAYS the first row; what changes is what it is called. It reads
   BEGIN DESCENT (`story.title.begin`) until the player has actually been printed, and CONTINUE
   DESCENT after, because "continue" with nothing to continue is a lie the first launch must not
   tell. Then NEW OPERATOR (the wipe, behind a confirmation whenever there is anything to lose),
   ARCHIVE (order-6, readable before a run exists), SETTINGS, QUIT. Big plates, high contrast, no
   feature list. One extra string id, no extra row, no extra confirmation — and NEW OPERATOR stops
   being the row a first-timer has to press to start the game.

   FIRST-LAUNCH -> COLD OPEN HANDOFF: picking a descent hands straight to the in-run cold open —
   the reprint boot card first (order-3, where ORA's wake line and the instance counter live), then
   the floor. The counter now climbs when a RUN STARTS rather than when a World is constructed, so a
   player who opens the app and quits from the title is not charged an instance.

B. DEATH -> REPRINT (restaged by narrative-rework order-2)
   The most repeated framing in the game, and it is deliberately calm: the player just died and may
   already be frustrated.

   THE STROKE AND THE CARD ARE TWO DIFFERENT MOMENTS, and merging them was the bug. One reports a
   DEATH; the other reports a BIRTH. Printed together — which is what the game used to do — the
   death arrived buried under a status block, a counter, two buttons and a line of dialogue: thirty
   words at the moment Dark Souls uses two, and neither beat landed.
     1. a slow fade to black (`FadeOverlayRenderer`, the existing death beat). No gory splash.
     2. THE STROKE: three words on the black and NOTHING else — no counter, no status block, no
        button, and no ORA (`story.death.stroke` = "THIS BODY DIED",
        `FramingScreenRenderer.renderDeathStroke`). Her absence is the point and costs nothing: she
        does not get printed, she reloads, so for one second the only voice in the game is missing.
        The words NEVER change, at any depth, in any region — that constancy is the design, and the
        escalation lives on the card instead. Note that the machine files a BODY, as an asset it
        owns, and ORA's first-death line calls it "you": the gap between those two sentences is the
        whole relationship (doctrine D6).
        It holds `STORY_DEATH_STROKE_HOLD_SECONDS` and hands over by itself (the fade at this seam
        always has), and a tap after the screen is black skips straight to the card — nobody is
        held, nobody is rushed, and nothing is lost either way because the card says all of it
        again, at length. The one-second lockout before a tap counts is deliberate: a player mashing
        fire as they die must not blow through their own death.
     3. the reprint card (order-3) — status lines, the quiet instance counter, ORA's wake line, and
        she is the first warm thing on it. It is printed by the world that DIED; the next World
        opens already faded up.
     4. one tap on CONTINUE, and the descent starts again.
   ORA'S DEATH ARC rides step 3 and nothing else: deaths 1-3 have RESERVED wake lines (what the copy
   is for / what did and did not come back / where the REPORT plate is), and then the region pools
   take over, so death 40 sounds nothing like death 2 without a single extra screen.
   The old full-screen death report is FOLDED into that card's screen as a PAGE
   (`render/InstanceReportRenderer`, opened by a small REPORT plate, closed by any tap), so the run's
   numbers — including the six-line RUN AUTOPSY that new-game-balancr order 9 put there for
   playtesters — are one tap away without a second screen competing for the same moment.
   `render/DeathOverlayRenderer` and the `HudConstants.DEATH_OVERLAY_*` block are GONE; the report's
   geometry lives with the other framing screens as `STORY_REPORT_*`.

C. THE PAUSE MENU (`PauseMenuItem`, drawn over the frozen floor)
   RESUME, ARCHIVE, SETTINGS, ABANDON RUN (confirmed). Reached from the PAUSE touch button in the
   top-right corner — far from both thumb clusters, because pausing is never something to do by
   accident mid-fight. It is a hard-pause overlay like every other, so barks queue and no exchange
   can open behind it (Part E). It SPOILS NOTHING: no plot summary, no objective recap — the archive
   is one row down for whoever wants it. Abandoning files the run's records exactly as a death does.

D. THE ENDINGS RESOLVE ON THE FRAMING THEY SUBVERT (story/06-endings.md)
   `World.commitPendingStoryEnding` records the ending permanently, and from then on the LAUNCH
   screen prints that ending's card instead of the ordinary death notice. The framing the player has
   read on every single launch is the payload.
     FREE / KILL — a terminal card: a depleted reserve, no authorized checkpoint, and NO CONTINUE.
                   Once it has finished printing, order-8 draws a dim RETURN plate where the button
                   the player has tapped a hundred times deliberately is not; it stands the game down
                   to a title screen the ending has changed.
     OBEY        — the card continues, into a fresh print of the same descent. That is the horror.
     MERGE       — no card at all. The frozen view the player was standing in holds, fading, for
                   `STORY_ENDING_MERGE_HOLD_SECONDS`, and then stands down. There is no input,
                   because the interface has stopped being theirs.
   Nothing is scored, ranked or labelled, and NEW OPERATOR / CONTINUE DESCENT both stay available:
   the descent is endless, and an ending is a thing the save remembers, not a door it closes.

E. THE WORLD LIFECYCLE SEAM (`world/StartMode`)
   A run is one `World`, so ending one means building the next. `World.isResetRequested()` +
   `getNextStartMode()` tell `Main` which: RESPAWN (drop straight into a fresh run, fading up from
   black — the card was already read) or TITLE (an abandoned run or a finished story). That handshake
   is the whole of what makes the death transition read as one continuous screen.

TESTS: `StoryFramingTest` (launch lines, the ending subversion, the menus, the confirmations, the
anti-skip promise, and the geometry: on screen and thumb-sized).


PART F — FIRST BOOT / COLD OPEN (rebuilt by narrative-rework order-2)
====================================================================
THE FIRST TEN MINUTES ARE ONE CONTINUOUS SEQUENCE: launch screen -> boot card -> ORA's
introduction -> the memory gap -> the first orders. The bar it is written against is
docs/narrative-authority.txt SECTION 5: sixty seconds in, a cold player can say WHO IS TALKING TO
THEM and WHAT HAPPENED TO THEM.

  - THE FIRST-PRINT CARD (`BootCardVariant.FIRST_PRINT`). A save that has never printed anybody
    gets its own card, resolved from the reprint counter by `BootCardVariant.forReprintCount()` —
    never a special case in the system, and every call site still just asks for the REPRINT card.
    It prints four plain lines with no proper noun of this fiction in any of them (OPERATOR
    DECEASED / BODY RECOVERY NOT POSSIBLE / BACKUP COPY ON FILE / PRINTING NEW BODY STAND BY):
    a person died, that person is you, there is a copy, the copy is being made. The counter is NOT
    hidden on run 1 — ORA explains the number herself, later, on the floor.
  - THE COLD OPEN is `IntroBeat`: three one-shot STORY_CRITICAL barks at `RUN_START` on run 1 — who
    is talking (and WHAT she is), what happened to this body, and THE GAP — then the MOVE hint as
    the fourth panel. Two more land on run 2 (she is not printed, so she is the only one who
    remembers the last body), and then she never introduces herself again. Each beat is keyed by its
    own subject, which is what makes the order guaranteed: the pool cannot hand back "you died about
    an hour ago" before "I'm ORA".
  - THE GAP IS THE LICENSE (doctrine D3). "Your memory came back short. Normal. I'll fill in the
    gaps as we go." — one sentence, on run 1, that turns every later explanation from a tutorial
    voice into something the CHARACTER needs. See the deviation recorded in
    story/02-player-and-cloning.md.
  - THE REST OF THE INTRODUCTION IS DISTRIBUTED, not front-loaded: the remaining `IntroBeat` rows
    hang off the first door opened, the first pickup, the first quiet stretch and the first terminal
    read, so the player meets her by watching her be useful.
  - THE FIRST REAL DEATH is where the loop gets EXPLAINED rather than joked about. Three wake lines
    are RESERVED by instance number (2, 3, 4) — what the copy is for, what did and did not come
    back, and where the REPORT plate is — so the most repeated screen in the game teaches the
    permadeath contract once, in order, in plain words.
  - `ControlHint` teaches each control as a single bark the first time it matters (MOVE, FIRE,
    RELOAD, HEAL, SWITCH_WEAPON, INVENTORY) — one-shot for the life of the save and STORY_CRITICAL;
  - the Region-1 `QUIET_MOMENT` teaching exchange is the first choice ever offered and deliberately
    decides nothing, so the blocking layer is learned with no enemy in the room. It is still ABOUT
    something: order-6 pointed it at the memory gap ORA named a minute earlier ("do you actually
    remember doing this before? Because your file says you have"), so the player's first answer is a
    thought about their own situation rather than a mood check with three shades of "fine".

"SOUL RESERVE" is a deep reveal and is not on screen anywhere — card or launch screen — until the
player has reached the Harvesting Galleries, which is where ORA starts asking what the printers run
on. It is expressed as DATA: the reprint card registers a second, deeper status block
(`BootCardDefinition.systemLinesFrom`), gated by the same persistent deepest-region the wake lines
use. There is no `if` for it in game code.


PART G — THE VOCABULARY LADDER (narrative-rework order-3)
========================================================
Doctrine D2 (docs/narrative-authority.txt) is PLAIN BEFORE PROPER: no proper noun of this fiction
appears on any channel before its plain-language introduction has been delivered, at a moment the
player can SEE the thing being named. Order-3 makes that a mechanical property of the catalog rather
than a thing a writer has to remember. It fixes failure F2 — the game used to say "instance",
"reprint", "soul reserve", "checkpoint", "operator", "contaminant", "cradle", "pattern" and "yield"
inside the first five minutes, all undefined, on channels that cannot be re-read.

THREE STEPS, always in this order, never more than one term per step:
  1. PLAIN   the thing is described in ordinary words, when it first matters (mostly order-2's work:
             the cold open states the cloning premise outright, the first-print card opens on
             "BACKUP COPY ON FILE / PRINTING NEW BODY").
  2. NAMED   the word arrives attached to that description, ONCE — one line, one new word.
  3. USED    from then on the word is free on every channel, including as jargon.

THE DATA. `narrative/StoryTerm` is one row per proper noun this fiction owns, carrying: the tokens
that count as "the word appeared", the naming line's string id, the earliest `StoryRegion` a catalog
row may CONTAIN the word (`freeFrom`), the existing trigger the naming hangs off, and the codex entry
the naming also archives. `narrative/StoryTermCatalog` registers one one-shot STORY_CRITICAL bark per
term into `BarkCatalog`'s registry, in a loop — so adding a proper noun is ONE enum row plus its
string, and never a catalog edit, a switch, or a new trigger.

  | Term                | Named at                        | Free from |
  |---------------------|---------------------------------|-----------|
  | reprint / print     | run start, print 2              | R1        |
  | operator            | the Organization's briefing     | R1        |
  | the Deepworks       | floor arrival (floor 1)         | R1        |
  | Erebus              | floor arrival (floor 2)         | R1        |
  | contaminant         | region entry, the Rings         | R1        |
  | the Organization    | the Organization's briefing     | R1        |
  | Overseer            | the first gate order            | R1        |
  | instance            | the first quiet stretch         | R1        |
  | serial              | the first undead sighted        | R1        |
  | checkpoint          | run start, print 3              | R1        |
  | yield               | region entry, the Galleries     | R2        |
  | reserve             | floor arrival, the Galleries    | R2        |
  | Cradle              | region entry, the Reliquary     | R3        |
  | pattern             | the Reliquary's gate order      | R3        |
  | the Wound           | region entry, the Wound         | R4        |

Two rows have no naming line of their own: `OPERATOR` and `ORGANIZATION` are introduced by USE, on
the Region-1 briefing exchange, which is the Organization talking and addressing the player as the
thing their file says they are. They borrow that line's string id and register no bark.

ONE NEW IDEA PER PANEL. `StoryTermCatalog.requestNextIntro()` asks for AT MOST ONE naming per
gameplay moment — the shallowest term still unnamed whose word is already free at the depth the story
has reached. That is a property of the SCHEDULE, not of the writing: it is why "the Deepworks" lands
on floor one and "Erebus" waits for floor two, with no counter, no timer and no conditional. It stops
at the first UNNAMED term rather than the first accepted request, so a naming the bark layer declines
for a pacing reason is offered again next time instead of being skipped.

FIRING SITES (all existing moments, all one line each):
  `World.requestFloorArrivalBarks`   FLOOR_ARRIVAL — and it now calls `requestColdOpenBarks()` first,
                                     so ORA introduces herself before she starts naming the place.
  `World.detectRegionEntry`          REGION_ENTERED and REGION_GATE_ORDER, each after its own beat,
                                     so the description always precedes the name.
  `World.requestColdOpenBarks`       RUN_START (gated by the reprint counter).
  `StoryBarkTickSubscriber`          CONTROL_HINT at the quiet moment; ENEMY_FAMILY_FIRST_SEEN, whose
                                     subject the term itself declares (only the undead wear serials).
                                     The naming is asked BEFORE the family line and before the
                                     archetype line, so "what a serial is" always precedes ORA
                                     reading one off a dead crew member.

THE GATE IS A BUILD CHECK, NOT A RUNTIME ONE. Gating text at delivery would mean lines silently
vanishing in play — a comprehension bug traded for an invisible-content bug. Nothing filters anything
at runtime; the term's region band on its own naming row is the only live behaviour.
`StoryTermCatalog.firstDisallowedTerm(text, earliestRegion)` scans RESOLVED TEXT (case-insensitive,
word-boundary anchored, possessives handled) and names the offending term, so the rule can be run
against the SHIPPED `story-strings.properties` — which is what catches a writer, or a translator,
putting "Cradle" back into a Region-1 bark. `StoryTermCatalog.isExempt(id)` holds the allow list: the
naming lines themselves, the whole codex (long text is exactly where terms get explained, and it is
opt-in and re-readable), the game's own title and tagline (a title cannot wait for a region gate),
and the endgame status cards (only ever reached from the Core). Order-10 owns the test file
(`VocabularyLadderTest`); order-3 owns the rule and the API it calls.

THE COST. Floor one of run one now asks for ten mandatory panels in two frames — the region-entry
beat, the gate order, ORA's aside on it (order-7), the two namings behind them, the facility's
naming, ORA's three introduction lines and the MOVE hint. They arrive one at a time, on the player's
own taps, spaced by the ordinary
rate limit. `STORY_BARK_QUEUE_CAPACITY` is sized for that burst (12) and is NOT a pacing knob: a
STORY_CRITICAL beat that finds the queue full of other criticals is dropped outright, and a dropped
control hint is a stuck player.

THE LORE DRIP (narrative-rework order-8) — how much, from where, and what must land
==================================================================================
The schedule above says WHEN a beat may fire. This section says HOW MUCH may fire, which CHANNEL
each kind of fact is allowed to come from, and — the part the schedule could not express — the short
list of things that MUST land in each region for the story to be followable at all.

A. FOUR CHANNELS, FOUR KINDS OF FACT
   Each source gives a DIFFERENT KIND of information. Overlap is the main cause of "the game keeps
   telling me things and none of them stick", so a fact arriving from the wrong channel is a FAULT,
   not a harmless duplicate: if ORA reads a whole document aloud the terminals stop mattering, and if
   the planet explains something it stops being the planet.
     TERMINALS (SYSTEM)  what the facility DID, in its own words. Dates, quotas, tickets, sign-offs.
                         Never interpretation.
     ORA (AI)            what the paperwork MEANS, one sentence, and what to do about the room you
                         are standing in. Never a document read aloud.
     THE PLANET          what it FEELS like from underneath. Never facts, never instructions, never
                         more than a fragment.
     THE ORGANIZATION    what you are SUPPOSED to believe. Never true detail, never twice on a floor.

B. THE PER-FLOOR BUDGET
   An ordinary floor may deliver ONE terminal take (`STORY_LOG_TAKES_PER_FLOOR`), TWO flavour barks
   (`STORY_BARK_FLOOR_BUDGET`) and ZERO exchanges — an ordinary floor never blocks. A REGION-GATE
   floor may add the region-entry bark, the gate order and ONE exchange; a floor never carries two
   exchanges, and never an exchange within one floor of another.
   On top of all of it, any number of STORY_CRITICAL beats (teaching, region entry, gate orders,
   reveal logs), which do NOT count against the budget: a stuck or lost player costs more than a
   talkative one.
   `BarkSystem.beginFloor()` (called once per arrival, from `World.requestFloorArrivalBarks`) resets
   the count; `isDeliverableNow` enforces it at DELIVERY, so a line the budget declines is held,
   goes stale and is dropped rather than arriving late. The counter counts what REACHED the screen,
   for the same reason the archive and the telemetry do.
   THE PLANET HAS A CAP OF ITS OWN: `STORY_PLANET_LINES_PER_FLOOR` = 1, in any region, on any
   trigger, whatever the priority. Its power is entirely scarcity and it is the one voice with no
   rate limit of its own. Nothing on the spine rides its channel, so the cap can never hold a
   mandatory beat.

C. THE FIVE REGION BEAT MAPS
   Three things per region must land, on channels the player cannot route around. If a beat cannot
   be placed on a region entry, a gate order, a reveal log, a control-flow moment or a BLOCKING
   exchange, it is not a spine beat and must be demoted. `StorySkimmerPathTest
   .everyRegionsThreeSpineBeatsRideAnUnavoidableChannel` is that table, asserted.

   R1 HABITATION RINGS — belief.       texture: fluorescent, ordinary, nothing visibly wrong.
      1. a workplace, and everyone in it is gone      `bark.region.rings`, `bark.gate.rings`
      2. you have a job, a file, and a history you
         do not remember                             `bark.gate.rings`, `bark.intro.the_gap`
      3. dying is normal here, and it is not free    `bark.intro.carried_items`, and the RESERVED
                                                     wake lines on the reprint card (order-2)
      + WHY THE DESCENT REPEATS                      `bark.intro.loop_restart` / `.loop_refill`

   R2 HARVESTING GALLERIES — first doubt.  texture: wet, warm, the same note under everything.
      1. this place was cutting something living,
         by weight, on a quota                       `bark.log.galleries.yield` (one-shot reveal)
      2. the paperwork knew, and had a form for it   `bark.gate.galleries`
      3. the Organization corrects your SENSES
         rather than the record                      `exchange.galleries.demand` (blocking)

   R3 THE RELIQUARY — the inversion.       texture: clinical, bright, humming.
      1. this is where bodies are printed —
         yours and ORA's                             `bark.region.reliquary`
      2. what they are printed FROM is the thing
         being cut                                   `bark.log.reliquary.cradle` (one-shot reveal)
      3. ORA cannot un-know it, and starts hiding
         things for you                              `exchange.reliquary.log` (blocking)

   R4 THE WOUND — grief.                   texture: warm, red, a slow beat felt more than heard.
      1. the facility stops; the walls are a body    `bark.region.wound`
      2. it has been awake and sedated for forty
         years                                       `bark.log.wound.4` (one-shot reveal — order-8
                                                     PROMOTED it out of the repeatable pool, where a
                                                     player could finish the region never drawing it;
                                                     `bark.log.wound.5` replaces it in that pool)
      3. the order changes from "purge" to "restore
         the restraints"                             `bark.gate.wound`

   R5 THE CORE — recognition.              texture: vast, intimate, almost tender.
      1. you were here before, you opened it, and
         you died doing it                           the ending exchange's own prompt
      2. the "contaminant" is what was DONE to it,
         not what it is                              `BestiaryCatalog.deepFamilyBarkId(...)`, the
                                                     family reframes from the Wound down
      3. the choice, and what each option costs      `exchange.core.ending` (blocking)

D. THE TWO STRUCTURAL HOLES ORDER-8 CLOSED
   WHY DOES THE DESCENT REPEAT? A roguelike player accepts a reset; a story player asks, and nothing
   in the build answered. Two one-shot rows on run 2 (`IntroBeat.LOOP_RESTART` / `LOOP_REFILL`): they
   rebuild the stored you rather than the one that fell, and the works do not stay cleared. Run 2 is
   the earliest either can land — the question is only asked once the player has died — and neither
   line may say "checkpoint", because that word is not free until run 3 (order-3's ladder).
   WHAT IS THE MAP, AND WHY IS THERE A CHOICE? Five one-shot LORE rows on `BarkTrigger.MAP_OPENED`,
   one per region band, and the route map stops being a menu bolted onto a story. The console is a
   hard-pause overlay, so the line is queued at the map and delivered in the lull on the floor the
   player picked — which is the right moment for it: they have just used the thing being explained.

E. THE PLANET'S SCHEDULE (the easiest voice to overuse)
   R1  silent. No rows at all, and the absence is PROTECTED — the first time anything speaks that is
       not ORA or the company, it should be alarming.
   R2  single words. Never a sentence. Never a response: up there it has not noticed the player, and
       a line addressed to them belongs a region deeper. (Order-8 re-banded the two Galleries rows
       that broke this into the Reliquary as `bark.strata.reliquary.5/.6`.)
   R3  it addresses you. First full sentences, present tense.
   R4  it speaks plainly, and it grieves. This is where it gets its exchanges.
   R5  it and ORA are the only voices left.

F. STALENESS AND SILENCE
   A queued non-critical line older than `STORY_BARK_QUEUE_STALE_SECONDS` is DROPPED, never delivered
   late: a line that arrives after its moment teaches the player that the voice is not about the
   room they are in, which is worse than saying nothing.
   SILENCE IS A LEGITIMATE RESULT. Every repeatable moment must be able to produce nothing at all,
   and roughly a third of them should. From the Wound down, floor arrival additionally rolls
   `STORY_BARK_DEEP_FLOOR_SILENCE_CHANCE` (0.40) to say nothing on purpose — ORA going quiet in a bad
   room is the cheapest horror effect in the game, and it is unavailable while something always
   fires.


THE BESTIARY VOICE (narrative-rework order-5)
=============================================
ORA introduces the things trying to kill the player, and every introduction does TWO jobs at once:
what it IS (the story — the moral geometry of the bestiary is the whole premise,
`story/00-premise.md`) and how to survive it (the reason the player reads it). All of it is data in
`narrative/BestiaryCatalog`, registered into the one bark registry by `BarkCatalog.bootstrap`.

FOUR KINDS OF ROW, all one-shot for the life of the save:
  FAMILY, early    one per `EnemyFamily`, Habitation Rings -> Reliquary. Names the thing AND says how
                   it kills you, in one line. One-shot STORY_CRITICAL: "what am I fighting" is a
                   comprehension-bar row (docs/narrative-authority.txt SECTION 5).
  FAMILY, reframe  one per `EnemyFamily`, from the Wound down; id suffix `.deep`. Drops the tactical
                   half — by Region 4 the player knows how to fight — and carries that family's
                   column of the premise's system-as-story table: undead + insect are the human cost,
                   machine is the Organization's own immune system, demon + golem are the planet
                   defending itself. Which of the two a player gets is the REGION GATE, not a
                   conditional; the ids differ, so meeting a family early and again at the bottom
                   yields both, in that order.
  ARCHETYPE        one per `EnemyType`, same trigger, subject key = `EnemyType.name()`. ORA's
                   translation of that archetype's `tacticalVerb()` — the designer sentence stays the
                   SOURCE OF TRUTH for what the line must convey and is read at bootstrap, so a type
                   that lost its verb fails the build rather than shipping a line about nothing. A row
                   names ONE behaviour: where an archetype does two things she says the one that kills
                   players, and the rest is the archive's problem. REACTIVE, so a combat spike HOLDS
                   it until the lull — except a BOSS, whose fight IS the floor and has no lull coming.
  ABILITY          one per `SpecialAbility`, on `ENEMY_ABILITY_RESOLVED` — fired when the ability
                   RESOLVES, never when it is telegraphed. All five are STORY_CRITICAL: these are the
                   rules that kill a player who does not know them, and mid-fight is the only moment
                   they are any use.
  BOSS PAIR        `bark.boss.first` walking into the first arena (a BARK, deliberately never an
                   exchange — a modal in front of a fight is cruel) and `bark.boss.first.dead` on the
                   kill, which is a REVEAL riding a moment every player who gets that far reaches.

COVERAGE IS STRUCTURAL. Every row is registered by looping the game's own enums, so a new family,
archetype or ability cannot ship without a voice: it arrives with an unresolved string id, which
`StoryLocalizationTest` fails on, and the mandatory rows are additionally swept by
`StorySkimmerPathTest`. There is no separate bestiary coverage test and none is needed.

NO LINE MAY STATE A NUMBER. She says slow, thick, fast, armoured; the HUD owns numbers, and a line
that quotes one goes stale the next time the balance moves. Equally out of scope, permanently: a
bestiary screen, an enemy-inspect panel and a "scan" verb — the delivery channel here is ORA.

ENGINE HOOKS: `EnemyManager.setSpecialResolvedListener` (fired from `executeSpecial`, before
dispatch, so a `SELF_DESTRUCT` is explained while its countdown still has turns left);
`World.requestBossDefeatedBark` (polled, so `BossFloorController` never learns about the story
layer); the arena line rides `World.requestFloorArrivalBarks` on a boss floor.


THE ORGANIZATION (narrative-rework order-7) — a mission, a rationale, and lies you can catch
============================================================================================
Doctrine D7 (docs/narrative-authority.txt): **the Organization is understood before it is hated.** A
voice that only threatens is scenery — a player cannot be betrayed by a briefing they were never
given. Order-7 gave it a job to hand out, a case a reasonable person accepts, and a set of specific
claims about the WORLD that objects in rooms disprove, so the turn is something the player CATCHES
rather than something ORA announces.

THE FIVE TRANSMISSIONS (`BarkCatalog.registerGateOrders`, one-shot STORY_CRITICAL, drawn ALL-CAPS):
  R1 Habitation Rings   THE BRIEFING     ten weeks of silence, a dead crew, restore the site. Cold
                                         and procedural, never cruel. The exchange behind it
                                         (`exchange.rings.briefing`) carries the rationale and the
                                         three planted claims.
  R2 Harvesting Galleries THE CORRECTION the player is standing in an abattoir, and it does not
                                         escalate — it CORRECTS THE RECORD, which is worse:
                                         "extraction is routine and within tolerance".
  R3 The Reliquary      THE OWNERSHIP    the leash, delivered as HR rather than as a threat:
                                         "reprint authorization is a benefit".
  R4 The Wound          THE INSTRUCTION  the mask comes off, and the tell is that the order stops
                       NOBODY WILL SIGN  being about a contaminant at all: "restore the restraints.
                                         This supersedes the purge order." The single most important
                                         transmission in the game.
  R5 The Core           THE WRITE-OFF    "pattern under write-off review. Return the asset to
                                         restraint." *The asset* is the being; the word choice is
                                         the whole characterisation.

ORA'S ASIDES ride the SAME moment behind `BarkCatalog.GATE_ASIDE_SUBJECT_KEY`, requested by `World`
immediately after the order so her comment lands behind the words rather than in front of them. Two
only — she comments when the paperwork has something to point at (R1: the brief is one paragraph
long; R4: the order changed and the reference number did not). She reports; she never explains what
it means. A gate order asked for with NO subject can therefore still only ever select the
Organization's own row, which is what keeps an aside from displacing the transmission it is about.

THE OVERSEER IS A DESK. The best idea in the Organization's material used to live only in
`codex.overseer`: the voice is not a person, it is a role in rotation reading from a script. It is on
a channel now, in two halves — the EVIDENCE unprompted (`bark.org.desk`, Reliquary down: "six
different people have said the same paragraph to you") and the MECHANISM on demand, as the reply to
the Core order's PROBE ("the routing headers change every transmission. The phrasing never does.").

THE RULES THAT KEEP IT COLD (content rules; they are not enforced by code and must not be):
  - it NEVER speaks twice on the same floor, and never during a fight;
  - it NEVER answers a question about itself — its probe replies are procedural non-answers, which
    is characterisation rather than evasion by the writer;
  - it NEVER uses ORA's name and never addresses her. She is equipment;
  - it NEVER insults the player. Every line is correct, filed and defensible, which is the horror
    story/04-the-organization.md asks for;
  - NOTHING it says is corrected on screen by narration. If a claim is false the player must be able
    to walk into the room that proves it — and if no such room exists, THE CLAIM DOES NOT SHIP.

stances is a demand nobody can interrogate. The R5 last order asks the player to confirm the
RESTRAINTS — the same subject as the R4 gate order and the same subject as the ending — so the choice
at the bottom answers the question the game actually asked.


PACING, ANTI-SKIP, ACCESSIBILITY, TELEMETRY
===========================================
  - PACING: rate limits, per-trigger cooldowns (minutes, not seconds), no-repeat memory, probability
    rolls on frequent moments, and the combat-spike hold. **If in doubt, CUT** — the fix for "too
    much story" is deleting rows, never adding a skip toggle.
  - ANTI-SKIP: one tap always advances, and NO channel advances itself or runs on a timer. The spine
    therefore rides the boot card, one-shot STORY_CRITICAL barks and the blocking ending exchange;
    `StorySkimmerPathTest` asserts a skimmer still gets the whole plot.
  - ACCESSIBILITY (`StorySettings`, four knobs): text size (wrap sooner, never overflow), boot-card
    reveal pacing, reduced motion, story audio. Every default is the comfortable end of its scale.
    There is no "disable timers" toggle because there are no timers.
  - TELEMETRY (`StoryTelemetry`): in-memory counters only — no identifiers, no I/O, no PII. The
    number that matters is the fast-dismiss fraction: a line closed inside
    `STORY_TELEMETRY_FAST_DISMISS_SECONDS` was skipped, not read.


WRITING RULES (narrative-rework order-6) — what a shipped ROW may not do
========================================================================
Order-6 was the cleanup pass over every string that already shipped: nine cuts, six replacement rows
and fourteen rewrites. These are the rules it derived from the faults it found, and every one of them
is a rule about a row rather than about the machine. They apply to every channel, forever.

  1. NO LINE DESCRIBES A MECHANIC THE GAME DOES NOT HAVE. A cut kill line said "let's pretend nothing
     else heard it", implying noise aggro; a cut backtrack line said "it moves the rooms". A player
     who believes a line plays around a rule that is not there and is punished for listening, which
     is strictly worse than silence. The inverse is the best kind of flavour row: `idle.mid.3` rides
     a rule the game really has (the world is turn-based, so nothing moves while you do not).
  2. NO LINE USES A SENSE ORA DOES NOT HAVE. She has the suit's sensors — no smell, no taste, no
     pain. "The smell in here is a war crime" became "the air reads wrong in here."
  3. NO LINE CELEBRATES OR SCORES THE PLAYER'S DEATH, in any region, ever (doctrine D6). The reprint
     counter still climbs; "New record" is gone from the screen whose job is to tell them they died.
  4. NO LINE STATES A NUMBER THE HUD ALREADY STATES (this is also the bestiary rule above).
  5. A JOKE IS THE DELIVERY OF AN OBSERVATION, NEVER THE PAYLOAD. "Soup. Bold." was the whole line;
     "Nobody came to collect it" is the observation, and it is drier for it. Full checklist:
     docs/narrative-authority.txt SECTION 4.
  6. A LINE MAY NOT ASSUME A FACT THE PLAYER — OR ORA — HAS NOT BEEN TOLD. This is why
     `lowhealth.mid.2` ("I know what a print costs now") is banded to the Reliquary and below: in the
     Galleries she has not read the cradle log yet. The audit for the WORD half of this is order-3's
     ladder (`StoryTermCatalog.firstDisallowedTerm`); the FACT half is still review.
  7. NO TWO SHIPPED ROWS SAY THE SAME THING (D5). When a rewrite makes two rows of one pool collide,
     the pool's repeatable row moves and the one-shot REVEAL keeps the sentence.
  8. WHEN A CUT DROPS A POOL BELOW ITS BAND'S DEPTH, REPLACE THE ROW OR DEMOTE THE MOMENT — never
     leave a moment able to go silent. `BarkSystem`'s no-repeat memory (`STORY_BARK_RECENT_MEMORY`)
     silences a moment ENTIRELY once its pool is empty, so a one-row band is a moment that fires
     once per save and then never again. The floor is four rows per region for the deep pools
     (FLOOR_ARRIVAL / KILL / LOG_FOUND, asserted by `StoryBarkTest`) and two for the banded flavour
     pools (LOW_HEALTH / IDLE / BACKTRACK, whose triggers are on the longest cooldowns in the table).

Two of these are mechanically audited today and the rest are review: rule 7 and the word half of
rule 6 can be run over the SHIPPED table with `StoryTermCatalog.firstDisallowedTerm`, which is what
order-10 wires to the build as `VocabularyLadderTest` / `NoRepeatVerbatimTest`.


RECIPES
=======
Every recipe below is the MECHANICAL half. Before writing the `register()` call, run the content
checklist in docs/narrative-authority.txt SECTION 9 (which job? which channel? which words? is it
funny? is it a repeat? could it be cut instead?) and the WRITING RULES above.

ADD A BARK               one `register()` in `BarkCatalog` (trigger, region band, speaker, tone,
                         priority, one-shot?) + one row in `story-strings.properties` and its
                         `BarkStrings` default. No switch, anywhere. Then ask which side of THE LORE
                         DRIP it lands on: an ordinary row spends part of a floor's two-line budget,
                         so if the floor already says enough, cut something instead.
CUT A BARK               delete the `register()` line and BOTH string rows, then check the pool it
                         came out of against WRITING RULE 8 above: a band left below its depth needs a
                         replacement row in the same commit. Leave a comment where the row was saying
                         what was cut and why — the next writer must not re-add it.
ADD AN ENEMY             nothing to write by hand: `BestiaryCatalog` loops the enemy enums, so a new
                         `EnemyFamily` / `EnemyType` / `SpecialAbility` already HAS its row. Supply
                         its lines — `story.bark.family.<family>` (+ `.deep`),
                         `story.bark.enemy.<type>`, `story.bark.ability.<ability>` — in
                         `story-strings.properties` AND `BarkStrings`. A new archetype's line is the
                         plain-words translation of its `tacticalVerb()`; one behaviour, no numbers.
ADD AN EXCHANGE          one `register()` in `ExchangeCatalog` (trigger, region, 2-3 options, each
                         STANCE / PROBE / CONSEQUENTIAL) + its string rows. Remember: exchanges BLOCK,
                         so if they start to feel frequent, delete rows.
ADD AN ORGANIZATION      first find the ROOM that disproves it. A claim with no counter-artefact
CLAIM                    already in the build does not ship — that is the whole of D7, and it is the
                         only recipe here that starts somewhere other than a `register()` call. Then:
                         write the claim into the transmission (a gate order in `BarkCatalog` or an
                         Organization exchange prompt), and add its row to THE LIE LEDGER above with
                         the artefact's string id and the region it is found in. The claim must be
                         correct, filed and defensible — never cruel — and nothing on screen may
                         correct it. If ORA must speak, she reports what she can see and stops there:
                         her asides ride `BarkCatalog.GATE_ASIDE_SUBJECT_KEY` on the same moment, and
                         there are two of them for a reason.
ADD AN ORA REPRINT LINE  one `registerWakeLine()` in `BootCardCatalog` (+ string rows).  A line for
                         ONE particular card — the first print, a specific death — adds
                         `.onlyOnVariant(...)` or `.onlyAtReprintCount(...)`; reserved rows beat the
                         region pool and are excluded from its depth.
ADD A BANDED STATUS LINE one extra `.systemLinesFrom(StoryRegion, …)` on the card in
                         `BootCardCatalog` (+ string rows).  This is how a word waits for the beat
                         that earns it — the whole band prints, so give it the same line count.
ADD A PROPER NOUN        one value on `StoryTerm` (its match tokens, its `freeFrom` region, the
                         existing trigger its naming hangs off, optionally the codex entry it
                         archives) + its `story.term.*` row and `BarkStrings` default.
                         `StoryTermCatalog` registers the bark in a loop and the firing sites already
                         ask for "the next naming due", so nothing else changes. The naming line says
                         ONE new word and describes nothing the player cannot see yet. A word with no
                         row here may not appear on ANY channel — it lives in the codex or it does
                         not exist.
ADD AN INTRO BEAT        one value on `IntroBeat` (its trigger, its earliest reprint count) + its
                         string row.  `BarkCatalog` registers every value in a loop, so the row
                         appears with no catalog edit; a cold-open beat needs nothing in `World` (the
                         loop asks for all of them, in order), a distributed one needs its firing
                         site to ask for its trigger + subject key.
ADD A CODEX ENTRY        one `register()` in `CodexCatalog` (category, unlockedByLine or a PROBE that
                         names it) + its string rows. Locked entries are never listed.
ADD A CONTROL HINT       one `ControlHint` value + its bark row + the firing condition in `World`.
ADD A PERSISTED FACT     a port method on `StoryProgressStore`, both implementations, a `story.` key,
                         a bump of `SCHEMA_VERSION` + migration note, and the schema table above.
ADD A SOUND              one `StoryCue` value + its four numbers in `StoryUiConstants` (same order)
                         + the play site in the update path. Never make it load-bearing.
ADD A SETTING            a `story.setting.*` key, a knob on `StorySettings`, a bump of
                         `STORY_CODEX_SETTING_COUNT`, and its name/value string ids. It appears on
                         BOTH the codex strip and order-8's settings screen automatically.
ADD A FRAMING MENU ROW   one value on `TitleMenuItem` / `PauseMenuItem` (label id + optional confirm
                         id) + its string rows + one case in `World.applyTitleMenuItem` /
                         `updatePauseMenu`. A row that carries consequences MUST carry a confirm id.
ADD AN ENDING SCREEN     order-3's recipe still applies (one `registerCard` in `BootCardCatalog`);
                         order-8 needs nothing, because the launch screen prints whatever card the
                         recorded ending names and the terminal RETURN plate is variant-agnostic.
